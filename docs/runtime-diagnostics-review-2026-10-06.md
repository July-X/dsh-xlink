# 运行诊断功能实现审查意见

日期：2026-10-06  
审查对象：当前 main 分支上的运行诊断实现，主要覆盖 fc7393a 至 374a330  
对照文档：[运行诊断与内核控制塔设计](runtime-diagnostics-design.md)

## 1. 结论

当前实现已经覆盖了运行记录、启动诊断、插件预检诊断、内核状态诊断，以及 restore / bisect 两类操作记录。后端守卫、三态预检结果、来源与完整性字段、只读运行记录命令也已经接上。

自动门禁没有发现编译或测试回归。npm run check 已通过，包括 Rust 格式检查、Clippy、release 编译、UI 测试和 UI 产物预算。

但实现还不能直接按设计文档宣称“全部完成”。目前有几处会让用户看不到正确页面、打开错误证据，或在没有确认的情况下改变插件状态的问题。建议先处理 P1 项，再进行 480×800 人工验收。

本次只记录修改意见，没有改动产品代码。

优先级说明：

- P1：影响功能闭环、证据可信度或安全边界，合并前应处理。
- P2：不一定阻断当前流程，但会造成设计漂移、维护风险或后续验收失败。

## 2. 已确认符合设计的部分

以下内容与设计文档基本一致，本轮不建议重复改造：

- 运行记录已经支持 startup、plugin-precheck、restore、bisect 四种 kind；DiagnosisShell 也有对应路由。
- 插件预检保留了 pass、fail、inconclusive 三态，并在报告中补充来源、版本钉、完整性、物化方式和目标实例。
- 插件预检、恢复和二分排查都增加了实例级运行守卫，不再只看当前 Shell 的工作台状态。
- 长任务仍复用进度浮层，失败后不自动关闭；运行记录写入失败也不会覆盖启动或预检主流程。
- 诊断层的“更多”菜单目前只放日志、复制编号、复制摘要、查看来源和刷新等低频动作，没有把恢复、删除、重启藏进去。
- 纯文本通道消息仍有回退路径，不会因为结构化事件解析失败而让进度面板失效。

## 3. 必须先处理的修改意见

### P1-01 诊断层被进度浮层压住，无法完成“查看启动诊断”交互

设计依据：

- 设计文档第 8.3 节要求诊断层放在全局浮层之后，并能覆盖当前页面。
- 第 11.1 节要求长任务失败后进度面板保持开放，由用户手动关闭。
- 第 2.5.1 节明确把进度浮层列为启动诊断入口。

当前证据：

- ui/src/shell/ProgressOverlay.vue:34-56 在失败状态下保留进度浮层，并提供“查看启动诊断”按钮。
- ui/src/App.vue:332-346 虽然把 DiagnosisShell 放在 ProgressOverlay 后面渲染，但 DOM 顺序不能抵消 z-index。
- ui/src/theme.css:2605-2613 将 progress-overlay 设为 z-index: 3000。
- ui/src/diagnostics/diagnostics.css:5-16 将 diagnosis 设为 z-index: 2200。

结果是：用户点击入口后，诊断层仍然位于进度浮层下面。诊断页的返回、更多、刷新和正文按钮可能看不见或点不到，进度浮层的遮罩也可能继续拦截输入。

修改意见：

1. 先确定两层的交互契约，再统一抽出语义层级变量。若诊断层是进度浮层的后续页面，应让诊断层位于进度浮层之上；若打开诊断时要把进度浮层交给诊断页接管，则需要提供明确的“返回进度”路径。
2. 不要只把某个数字改大而不说明层级关系。Element Plus 弹层、日志弹层、事故面板、进度浮层和诊断层应在同一处写出层级顺序。
3. 保留失败进度面板的手动关闭语义。诊断层返回后，用户仍应能关闭原进度面板。

验收条件：

- 启动失败后，点击“查看启动诊断”，诊断页完整显示在最上层。
- 诊断页的返回、更多、刷新、查看日志和重试按钮都可操作。
- 返回后进度面板仍然开放，且“关闭”按钮有效。
- 在 480×800 窗口中不出现点击穿透或遮罩拦截。

### P1-02 “查看证据”保存了路径，但日志窗口没有定位到这份日志

设计依据：

- 第 5.3、6.5 节要求证据入口指向本次诊断相关的日志。
- 第 8.2 节要求 openEvidence(path) 复用日志模块，而不是另写一套文件读取逻辑。

当前证据：

- ui/src/diagnostics/diagnostic-actions.js:51-56 只把 path 写入 diagnosticStore.evidencePath，随后调用 showLogs()。
- ui/src/logs/logs.js:163-167 每次打开日志时都将 logModal.activeName 清空。
- ui/src/logs/logs.js:145-153 刷新日志列表后默认选择第一份文件。
- StartupDiagnosis.vue 和 OperationDiagnosis.vue 没有传入具体路径；PluginDiagnosis.vue:135-139 虽然传入了沙盒日志路径，但当前日志模块没有消费它。

因此，用户从插件诊断页点击“查看日志”，看到的可能是日志目录中的第一份文件，而不是报告里列出的沙盒日志。这个问题会直接削弱诊断报告的可信度。

修改意见：

1. 为日志模块增加“首选日志”参数，例如接收完整路径或后端返回的稳定文件名。
2. 只允许把首选路径解析到 list_log_files 返回的文件集合中，不能直接让前端把任意路径传给读取命令。
3. 路径不存在时明确提示“证据文件已清理或不可用”，不要静默退回第一份日志。
4. 启动、预检、恢复和二分都要传递各自的 kernelLog / sandboxLog，不要继续使用无参数的 openEvidence()。

验收条件：

- 启动失败页面打开对应的内核日志。
- 插件预检失败页面打开对应的 precheck-*.log。
- 恢复或二分失败页面打开对应的证据文件。
- 目标文件不存在时，日志窗口显示清楚的缺失原因，且不会误显示另一份日志。
- 增加 UI 测试，断言 activeName 与报告中的证据文件一致。

### P1-03 插件预检完成后自动改变目标实例，与设计中的“确认应用”不一致

设计依据：

- 第 6.2 节要求应用变更前建立 pre-change 快照。
- 第 6.3 节明确画出“恢复快照”和“应用变更”两个动作。
- 第 6.6 节要求“沙盒预检 → 展示结果 → 用户确认应用 → 走现有插件变更路径”。
- 第 8.2 节列出了 applyPluginChange(spec, mode) 动作。

当前证据：

- ui/src/plugins/PluginsPanel.vue:550-558 在预检开关打开时，安装按钮直接调用 precheckPlugin。
- ui/src/plugins/plugins.js:274-281 调用的是 plugin_precheck_install。
- src-tauri/src/plugins/precheck.rs:255-270 在沙盒创建失败时按 fail-open 语义直接安装。
- src-tauri/src/plugins/precheck.rs:467-510 在候选通过后立即调用 commit()，把插件物化并接线到目标实例。
- PluginDiagnosis.vue:272-277 没有“应用变更”按钮，预检报告也没有独立的确认阶段。

这不是单纯的按钮遗漏，而是产品契约没有选定。当前实现沿用了旧的 fail-open 安装契约；设计文档描述的却是预检和应用分离。两者都可以成立，但不能同时作为当前实现的说明。

修改意见：

需要在产品层明确选择一条路径：

1. **保留两阶段流程。** plugin_precheck_install 只创建快照、运行沙盒并返回报告；用户确认后再调用独立的应用命令。通过和通过但有告警时显示“应用变更”，未通过或未能完成时禁用应用，并给出继续操作的明确说明。正式应用仍需执行实例级运行守卫、快照和现有物化流程。
2. **保留当前 fail-open 流程。** 那么应同步修改设计文档、示意图和页面文案，把页面定位改成“安装预检结果”，明确说明预检结束时插件已经安装。不要继续保留“应用变更”作为设计要求。

无论选哪条，都需要把快照、预检、应用和刷新拆成可测试的状态机，并为每个按钮使用独立的 loading（加载态）和进度键。

验收条件：

- 页面能够明确告诉用户“当前插件是否已经改变目标实例”。
- 用户不会因为查看预检报告而再次触发一次隐式安装。
- 预检失败、基线未能完成、应用失败和部分应用都有不同的结果文案。
- 应用变更前能看到快照或快照创建失败原因。
- 设计文档、示意图、命令契约和实际按钮行为保持一致。

### P1-04 “恢复快照”按钮没有进入差异预览

设计依据：

- 第 6.6 节规定恢复必须先显示差异，再执行恢复。
- 现有快照流程已经在 ui/src/diagnostics/snapshots.js:51-92 提供了预览、确认和进度链路。

当前证据：

- ui/src/diagnostics/PluginDiagnosis.vue:141-153 的 openRestore() 只调用 loadSnapshots()，然后切换到设置面板。
- 用户必须离开当前诊断上下文，再到设置页自己寻找目标快照。
- PluginDiagnosis.vue:272-277 仍然把这个动作标成“恢复快照”，但没有携带预检产生的 pre-change 快照编号。

这会让按钮名称和实际效果不一致。用户点的是恢复，得到的却是一个快照列表。

修改意见：

1. 在预检报告或运行记录中保存 pre-change 快照编号。
2. 诊断页调用现有的 previewRestore，直接打开 SnapshotRestoreDialog，不要再实现第二套差异计算。
3. 如果旧记录没有快照编号，按钮应显示“查看快照列表”或暂时隐藏，并说明不能自动定位。
4. 恢复确认、进度、结果和跳过项继续使用现有快照模块，避免诊断页自行执行恢复。

验收条件：

- 从插件诊断页点击“恢复快照”后，第一步一定是差异预览。
- 预览中能看到目标快照、改动数量和无法自动处理的项目。
- 未确认前不写入实例配置；确认后才进入进度流程。
- 恢复完成后能回到原诊断上下文，且显示验证结果。

### P1-05 控制塔把所有最近操作都当成启动诊断打开

设计依据：

- 第 4.1 节支持四种运行记录 kind。
- 第 7.2 节要求“最近一次操作”能进入具体的诊断页面。
- 第 8.3 节已经为 startup、plugin、restore、bisect 留出不同视图。

当前证据：

- ui/src/diagnostics/ControlTower.vue:153-190 直接取 recentRuns[0]，openDiagnosis() 固定调用 openStartupDiagnosis()。
- 同一组件的“需要关注”预检项在 ControlTower.vue:174-179 调用 openPluginDiagnosis({}, 'overview')，没有传入运行编号或插件信息。
- 最近操作标题 ControlTower.vue:240-244 只写了“启动 / 预检 / 恢复”，漏掉 bisect。
- DiagnosisShell.vue:137-143 虽然支持恢复和二分视图，但控制塔没有把运行类型路由过去。

结果包括：

- 最近一条是恢复或二分时，会被错误地当成启动记录展示。
- 最近一条是插件预检时，插件页只能显示“未知插件”，无法读取那次预检的上下文。
- 用户从“需要关注”进入预检诊断时，看到的不是对应的失败记录。

修改意见：

1. 在 diagnostics.js 增加按 RunSummary.kind 分派的统一入口。
2. startup 进入启动诊断；restore / bisect 进入操作诊断，并传入 runId。
3. plugin-precheck 要么持久化足够的插件报告字段，要么增加“仅运行记录视图”，不能用空 spec 冒充完整插件诊断。
4. 控制塔的类型文案改为与四种 kind 一致，并为没有对应详情的历史记录提供明确空态。
5. 运行完成后刷新 recentRuns，避免概览卡继续显示上一条结果。

验收条件：

- 分别制造四种运行记录，点击“最近操作”后进入正确页面。
- 预检失败入口能看到正确的插件名、runId、阶段和证据。
- 恢复与二分不会出现在启动时间线中。
- 切回概览后，“最近操作”显示刚完成的那一条。

### P1-06 内核状态页的“刷新状态”菜单当前是无操作

设计依据：

- 第 7.3 节要求用户主动刷新时强制读取状态。
- 第 8.2 节要求提供 loadKernelStatusDiagnosis()，组合当前状态、插件、技能和通知数据。
- 第 9.4 节要求读取失败时保留旧值，并在对应项说明过期或失败。

当前证据：

- ui/src/diagnostics/diagnosis-more-menu.js:30-35 为内核状态页添加了“刷新状态”。
- ui/src/diagnostics/DiagnosisShell.vue:81-86 的 onRefresh() 只处理 startup 和 restore / bisect，kernel 不会执行任何命令。
- ui/src/diagnostics/KernelStatusDiagnosis.vue:12-60 只读取 store.view.kernel，没有自己的状态加载或刷新动作。
- 控制塔的健康数据仍然由概览页状态快照和若干前端缓存拼出，内核状态页并没有实现设计稿中的完整数据来源。

修改意见：

1. 增加 loadKernelStatusDiagnosis(manual)，由诊断动作层统一触发状态读取，并为刷新按钮绑定独立 loading key。
2. 明确状态页和概览控制塔的分工：要么状态页承载完整的“需要关注 / 系统健康 / 最近操作”，要么修改设计文档说明状态页只是当前内核的细节卡片。
3. 为技能、日志和插件接线分别增加“未加载、读取失败、无数据、已过期”状态，不要用初始空数组代替读取结果。

验收条件：

- 修改端口或停止内核后，打开状态页点击“刷新状态”，页面显示新快照。
- 刷新失败时保留上一次值，并显示数据可能过期和重试入口。
- 内核状态页的布局与设计图的职责一致，不把同一组健康信息拆在两个页面却没有说明。

### P1-07 Windows 环境下运行记录可能暴露用户目录

设计依据：

- 第 11.4 节禁止运行记录包含未脱敏的用户 home 路径。
- 项目的路径层已经把 Windows 的 USERPROFILE 纳入 home 解析。

当前证据：

- src-tauri/src/diagnostics/run.rs:324-348 的 sanitize() 只读取 HOME。
- src-tauri/src/shell/paths.rs:109-120 的 dirs_home() 才同时处理 HOME 和 USERPROFILE。
- 启动诊断会把内核日志路径写入 RunEvidence，路径通常来自 Windows 用户目录。

在 Windows 上未设置 HOME 时，运行记录中的 C:\Users\用户名\... 不会被折叠。当前测试只覆盖设置 HOME 的情形，不能证明 Windows 发行版满足隐私要求。

修改意见：

1. 复用路径层的跨平台 home 解析，或抽出一个不依赖高层模块的脱敏路径帮助函数。
2. 对默认 home、DSH_XLINK_HOME 覆盖目录和运行记录中的证据路径分别定义替换规则。
3. 增加 Windows 语义测试：清空 HOME、设置 USERPROFILE，确认日志路径、摘要和事件消息都不会保留用户名。
4. 测试必须使用仓库已有的临时 home guard，不能触碰真实用户目录。

验收条件：

- Windows 默认路径被折叠成约定的短路径。
- 自定义数据根目录不会因为脱敏逻辑遗漏而泄漏完整路径。
- 导出的运行摘要和诊断详情都遵守同一套规则。

## 4. 需要补齐的 P2 项

### P2-01 通道信封中的 runId 没有传到前端事件流

后端 src-tauri/src/diagnostics/run.rs:488-494 已经把 runId 放进通道信封，但：

- ui/src/diagnostics/diagnostics.js:49-63 解析后只返回 event 和 text，没有返回 payload.runId。
- ui/src/store.js:394-400 和 ui/src/shell/progress.js:109-114 调用 ingestChannelMessage(msg) 时没有传第二个参数。
- ingestChannelMessage() 只有在调用方显式传入 runId 时才会写入 event.__runId。

这使得设计第 4.3 节所要求的“事件 runId 与命令返回 runId 一致”没有在实时 UI 中真正成立。当前页面仍能看到阶段，但无法可靠证明这些事件属于当前运行。

修改意见：

- 解析器返回 runId，并让两个 Channel 消费点直接传入。
- 打开启动诊断时记录当前 runId；事件 runId 与当前记录不一致时丢弃、隔离或重新开始时间线。
- 为“连续两次启动、消息延迟到达、纯文本消息混入”增加测试。

### P2-02 诊断动作代理没有覆盖设计列出的动作

diagnostic-actions.js 的注释要求组件只调用动作代理，但目前仍有多个诊断组件直接引入业务动作：

- StartupDiagnosis.vue 直接使用 showIncident、openHarnessWindow。
- PluginDiagnosis.vue 直接使用 loadSnapshots、修改 store.activePanel、调用 closeDiagnosis。
- KernelStatusDiagnosis.vue 直接使用 showLogs。
- ControlTower.vue 直接使用 showLogs、store 和面板跳转。

设计第 8.2 节列出的 applyPluginChange、loadKernelStatusDiagnosis 等动作也还没有对应代理。

修改意见：

- 把打开事故、打开工作台、打开日志、打开恢复预览、刷新内核状态和应用插件变更集中到动作层。
- 动作层负责 loading key、进度和失败文案，组件只负责展示状态。
- 如果某些页面跳转确实不需要代理，应删掉“组件只调这里”这条约束，并在设计文档中说明例外。

### P2-03 启动阶段计数和头部操作没有完全按设计落地

当前 StartupDiagnosis.vue:118-122 显示的是“完成 部分 个阶段”或“完成 0 个阶段”，没有按实际事件计算完成数量。设计图要求显示类似“完成 3 / 6 个阶段”。

同时，DiagnosisShell.vue:105-114 的头部刷新按钮没有绑定 loading，而页面底部刷新按钮有独立 loading。设计第 2.5.4 节要求异步动作的 loading 只显示在触发它的按钮上。

修改意见：

- 按阶段集合统计已完成、失败、运行中和未执行数量；不要用事件总数代替阶段数。
- 头部刷新和页面内刷新复用同一个动作，但要共享同一个明确的 loading 状态。
- 重新检查失败、告警、无记录和运行中四种状态下主操作是否仍在 480×800 视口内。

### P2-04 运行编号的本地时区计算不正确

src-tauri/src/diagnostics/run.rs:459-476 将当前 epoch 秒减去传入的 epoch 秒当作本地时区偏移。调用时传入的就是当前时间，因此得到的值接近零；在东八区等非 UTC 时区，runId 中的时刻会按 UTC 生成，日期又来自本地日期，可能出现日期和时间不一致。

修改意见：

- 使用项目已有的本地日期时间能力或平台时区 API，不要用当前时间差估算 UTC 偏移。
- 增加时区边界测试，至少覆盖本地日期跨天和负偏移时区。
- 保留 runId 的稳定格式和唯一性，不要让修复改变历史记录的读取方式。

### P2-05 崩溃留下的孤儿详情文件仍会累积

设计文档第 17.7 节已经记录：Recorder::push() 会写详情文件，但索引只有 finish() 才更新。进程中途退出时，详情文件不在索引中，后续 prune() 也不会删除它。

这不会立即影响页面，但每次崩溃都会留下一个无法从运行记录列表访问的文件，属于明确的存储维护缺口。

修改意见：

- 重新确定索引是只保存已结束记录，还是也保存 running 记录。
- 如果首次事件就写索引，必须保护正在进行的二分记录，避免被裁剪。
- 如果采用孤儿清理，应通过二分会话、文件年龄和运行锁保护活动记录，不能按目录直接删除。
- 增加“异常退出后重启、二分跨命令进行中、超过保留数”的测试。

### P2-06 预检页面重复展示两条时间线，可能把主操作推到首屏之外

PluginDiagnosis.vue:216-259 先展示静态的五段“实验流程”，随后又展示 RunTimeline 的“阶段时间线”。两者表达的是同一批事件，只是粒度不同。

设计第 6.3 节给出的页面只有一条实验流程，且第 13.3 节要求失败和告警时主操作不要被内容推到窗口外。

修改意见：

- 保留一条以阶段为主的时间线；详细事件放进折叠区，或让每个阶段直接展开事件。
- 在 480×800 下验证“应用变更 / 查看日志 / 恢复快照”等主动作的位置。
- 如果确实需要同时显示两条时间线，应在设计文档中说明它们分别回答什么问题，并给出折叠策略。

## 5. 尚未完成的人工验收

本轮只完成了静态代码审查和自动门禁，没有在安装后的 Tauri 窗口中做人工目视验收。以下项目不能用 npm run check 代替：

- 480×800 下标题、返回按钮、刷新按钮和更多菜单是否互相挤压。
- 启动失败、插件预检失败、恢复部分完成、二分未能判断时，首屏是否能看到下一步动作。
- 诊断层与进度浮层、日志弹层、事故面板叠加时的真实层级。
- 折叠区、滚动区、键盘焦点和 32×32 图标按钮的可操作性。
- prefers-reduced-motion 开启时，时间线和浮层是否仍然清楚。

人工验收建议固定使用设计图中的 480×800 视口，并至少走一遍：

1. 启动成功、启动失败、启动告警。
2. 插件预检通过、未通过、未能完成。
3. 从控制塔分别打开四种运行记录。
4. 从诊断页打开内核日志和沙盒日志。
5. 从插件诊断页进入差异预览并完成一次恢复。

1. 先修 P1-01、P1-02、P1-05、P1-06 和 P2-01。这几项会直接影响用户是否看到正确页面和正确证据。
