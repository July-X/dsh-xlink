本轮优化围绕三个目标展开：**安装来源可以核实，停止与重启结果可以确认，发布前的桌面关键路径可以重复验证。** 保留现有 Tauri、Vue 3、Rust 与官方 dsh 内核的分工，先修复已确认问题，再完善验证与维护机制。

## 一 目标与实施边界

### 1.1 本轮成果

1. 用户明确指定的 GitHub、npm 或其他允许来源，与最终安装来源保持一致。
2. registry、tarball、重定向与 Git 传输遵循统一、可解释的来源策略。
3. 同一壳进程内重复启动、停止、启动失败和异常退出恢复均有明确收尾行为。
4. 预检验证的物料与最终应用的物料一致，失败时保留可恢复状态。
5. Windows 与 Intel macOS 的基础桌面流程拥有可重复的隔离验证。
6. 静态扫描、单元测试、真实 IPC、原生 UI 和 release 产物检查分别报告，不混用证明范围。
7. 当前文档、功能入口和保留的兼容逻辑保持一致。

### 1.2 必须保留的项目约束

- 壳管理内核生命周期、配置和窗口，不修改官方 dsh 或其 fork，也不以未来上游修复作为本轮验收前提。
- 已安装内核目录只读。仅正常安装过程生成安装 stub 和依赖树；不通过修改已安装 node_modules 解决问题。
- 保持 dev/release 的实例、内核安装树、插件中央库与壳状态隔离；有意共享的技能资源按既有契约处理。
- 不为修复而重建用户默认实例、清空配置、删除历史会话或自动卸载已有内核。
- 外部工具数据和本机 Codex 登录仍默认不读取，沿用显式许可、只读和身份校验。
- Windows 保持现有 Job Object/进程树管理路径；Unix 的修复不能直接套用到 Windows。
- 复用已存在的公共原语与服务，不新增另一套安装器、进程管理器或状态存储。
- 来源解析、下载、预检、应用和展示使用同一份解析结果；内核与插件/技能的 registry 成功记录继续按用途分开，不能因为收敛代码而串用缓存。
- 所有测试使用合成数据或本轮独占临时目录；不得用真实用户数据做搬迁、删除、故障注入或权限测试。

上述约束以执行时的根 AGENTS.md、对应子目录 AGENTS.md 及专题文档为准。[全仓约束](https://github.com/July-X/dsh-xlink/blob/f448970fc206fe747f82dd6d889b8f98144a7fae/AGENTS.md) · [运行时边界](https://github.com/July-X/dsh-xlink/blob/f448970fc206fe747f82dd6d889b8f98144a7fae/docs/architecture/runtime-boundaries.md)

### 1.3 本轮不扩大的范围

本轮不安排整体 UI 重设计、全面迁移 TypeScript/Pinia、引入新数据库、接入第二种真实内核、重写记忆系统或扩大第三方官网支持。除 OPT-13 外，不把外部证书申请、账号资源准备计入代码修复完成条件。

### OPT-01 修正 GitHub 与 npm 来源映射

**负责人建议：Rust 安装模块维护者。优先级：P1。依赖：OPT-00。初始状态：待实施。**

**已确认问题**

插件安装会从未带 revision 的 GitHub spec 取仓库末段名称，优先尝试同名 npm 包；owner 不参与归属校验。候选通过插件校验并安装成功时，实际来源可能与用户选择不同。进度日志会显示 npm 尝试，但预检来源标签仍可能按原 spec 填写。

**改动入口**

src-tauri/src/plugins/center.rs 的 npm_candidates_from_github_spec、install_unlocked；plugins/precheck.rs 的来源信息；相关 UI 来源展示与测试。

**实施方案**

1. 显式 GitHub URL、SSH URL 或 owner/repo 简写，始终按解析出的 Git 来源处理；移除按仓库名猜 npm 的自动替换。
2. npm spec 保持原有 npm 路径；两种来源共享下载和校验原语，但不互相隐式替代。
3. 安装结果、预检报告和历史记录保存实际规范化来源、解析后的版本或完整 commit。
4. 如未来提供 npm 加速选择，必须是独立明确选择或可验证的发布映射，不能只信 npm 的 repository 字段。
5. 历史安装项保留实际记录，不按新规则自动改源、重装或删除；记录不足时标为来源待确认。

**验收标准**

- [ ] 两个不同 GitHub owner 的同名仓库保持不同来源身份。
- [ ] 即使 npm 存在合法同名插件，也不会替代显式 GitHub 来源。
- [ ] 带 tag、commit 和不带 revision 的 Git spec 均经过同一解析与策略入口。
- [ ] Git 获取失败时明确失败，不偷偷回退到 npm。
- [ ] npm spec 正常安装，原有可恢复安装事务不退化。
- [ ] UI、预检报告、日志和安装记录对实际来源的描述一致。
- [ ] 历史安装项在读取、更新和卸载时不会被自动重解释为另一来源。

**完成标准**：删除生产路径中的隐式来源替换，并有执行安装解析/分发逻辑的回归测试；只修改说明或字符串检查不算完成。

依据：[来源推导与安装路径](https://github.com/July-X/dsh-xlink/blob/f448970fc206fe747f82dd6d889b8f98144a7fae/src-tauri/src/plugins/center.rs#L2849-L2959) · [预检来源标签](https://github.com/July-X/dsh-xlink/blob/f448970fc206fe747f82dd6d889b8f98144a7fae/src-tauri/src/plugins/precheck.rs#L174-L198)。

### OPT-02 统一安全取源与重定向策略

**负责人建议：Rust pkg 模块维护者。优先级：P1。依赖：OPT-00。初始状态：待实施。**

**已确认问题**

默认 registry 和镜像为 HTTPS，但显式 DSH_NPM_REGISTRY 只做 trim 和补斜杠，仍接受 HTTP；tarball 直接使用元数据 URL；Git scheme 白名单仍允许 git://。风险需按这些触发条件表述，不能声称默认源使用明文。

**改动入口**

pkg/registry.rs、pkg/fetch.rs、pkg/releases.rs、插件/技能来源解析，以及接收 registry 配置的 pnpm 启动路径。

**实施方案**

1. 使用 URL parser 校验 registry 和下载 URL，统一规范化 scheme、host、端口及路径。
2. 生产默认拒绝 HTTP registry 和 HTTP tarball，禁止 HTTPS 重定向降级；拒绝不允许的 scheme、URL 内 userinfo 和不合法 base URL。
3. 保持显式 registry 不自动换源的语义。不合规配置应报可操作的错误，不能静默使用官方源或镜像。
4. Git 允许来源限定为明确支持的 HTTPS、SSH 及等价简写；移除 git://。保留已有的参数与 scheme 防注入边界。
5. 建立 registry 与合法下载域名的策略。支持官方源、镜像和合法 CDN；不机械要求所有 tarball 与 registry 同 host。
6. 自定义 HTTPS 私服可明确配置其下载域名。不得为方便兼容而关闭 TLS 校验；不得以不受控通配或任意重定向放开策略。
7. 重定向每一跳及最终目标均检查，限制跳数；日志不输出带凭据的 URL、token 或完整敏感查询参数。
8. 保留现有 SRI、缺摘要拒绝、体积限制和归档安全规则。测试用本地服务通过依赖注入/专用夹具实现，不开放生产 HTTP 后门。

**验收标准**

- [ ] 未配置时仍按官方 HTTPS 优先、镜像仅在允许的传输故障时回退。
- [ ] 合法 HTTPS、大小写规范化、路径和尾斜杠行为可预测。
- [ ] HTTP、userinfo、非法 scheme、畸形 base URL 在网络请求前被拒绝。
- [ ] 不合规显式配置不会静默回退；已安装内容不被自动删除。
- [ ] 合法 CDN 和配置允许的私服下载域通过，未授权目标被拒绝。
- [ ] HTTPS→HTTP、重定向循环、越界目标和超限跳数失败且清理临时下载。
- [ ] 缺摘要、摘要不符和解包危险路径继续失败，不能被新策略绕开。
- [ ] 内核、插件、技能实际调用同一策略；不能只给某条 UI 入口增加校验。

**兼容影响**：既有 HTTP 配置和 git:// 来源会被拒绝，应给出迁移到 HTTPS/SSH 的说明；不自动重装现有条目。任何生产例外应另行明确范围，不能在本轮以隐式兜底引入。

依据：[registry 解析](https://github.com/July-X/dsh-xlink/blob/f448970fc206fe747f82dd6d889b8f98144a7fae/src-tauri/src/pkg/registry.rs#L63-L82) · [tarball 下载](https://github.com/July-X/dsh-xlink/blob/f448970fc206fe747f82dd6d889b8f98144a7fae/src-tauri/src/pkg/fetch.rs#L115-L149) · [Git 白名单](https://github.com/July-X/dsh-xlink/blob/f448970fc206fe747f82dd6d889b8f98144a7fae/src-tauri/src/plugins/center.rs#L860-L923)。

### OPT-03 修复桥接换代与私有凭据写入

**负责人建议：Rust 运行时维护者。优先级：P2。依赖：OPT-00。初始状态：待实施。**

**已确认问题**

launch 先向固定路径写新凭据，再释放旧 Bridge；旧代 Drop 按路径删除文件，可能删掉新凭据。另有临时文件先按默认权限创建、之后 chmod 的窗口。

**改动入口**

plugins/builtin/bridge.rs、bridge_credential.rs、kernel/kernel_adapter.rs；复用 shell/process.rs 中已存在的私有原子写能力。

**实施方案**

1. 在现有生命周期串行约束下定义桥的创建、发布、替换、停止和失败清理顺序。
2. 旧代只能清理属于自己的凭据；可采用代次标识或内容归属检查，不能仅按固定文件名删除。
3. 新桥发布失败时不留下可误用凭据；不以“仍保留旧代资源”作为未知状态的兜底。
4. 凭据临时文件创建时即为私有，复用已有安全写入原语，避免固定临时名互相覆盖。
5. 保持环境变量通道和文件通道的职责，令牌、文件内容和账户信息不进入日志。
6. 内核启动失败仅回收本轮新建的桥资源；复用且仍被存活内核使用的资源不能无条件关闭。正常停止确认成功后撤销对应桥接代次；停止失败时保留仍运行内核的通信与恢复依据。
7. 列清生命周期锁、桥注册表锁和退出派生闸门的获取顺序；不得持有注册表锁等待线程退出或执行长时阻塞。桥故障沿用现有降级策略，并在诊断中显示具体原因。

**验收标准**

- [ ] 创建带 adapter/update.mjs 的真实形状物化目录，连续两次 launch 后文件仍存在。
- [ ] 文件中的 URL/token 属于第二代，并可调用第二代 ping。
- [ ] 第一代端口关闭，第一代 token 在第二代被拒绝。
- [ ] 连续多轮重启无端口、线程、文件或临时文件持续增长。
- [ ] 旧代清理延迟执行时不会删除已发布的新代凭据。
- [ ] 注入监听、写文件、发布或内核 spawn 失败后，没有残留有效凭据和不可回收桥。
- [ ] Unix 临时文件从创建起即为私有；Windows 沿用项目支持的私有存储策略。
- [ ] 同时存在两个实例时，只清理被停止的实例。

**完成标准**：必须在生产 launch 路径验证凭据换代；只测试 Drop 或旧端口关闭不足以关闭任务。

依据：[桥接换代](https://github.com/July-X/dsh-xlink/blob/f448970fc206fe747f82dd6d889b8f98144a7fae/src-tauri/src/plugins/builtin/bridge.rs#L64-L149) · [凭据写入](https://github.com/July-X/dsh-xlink/blob/f448970fc206fe747f82dd6d889b8f98144a7fae/src-tauri/src/plugins/builtin/bridge_credential.rs#L35-L78)。

### OPT-04 统一 Unix 进程组停止策略

**负责人建议：Rust 运行时维护者。优先级：P2。依赖：OPT-00。初始状态：待实施。**

**已确认问题**

当前停止逻辑在主 Child 已退出时跳过组级强制收尾；同组内忽略 TERM 的后代可能残留。后续按主 PID 再次校验不能替代这个阶段。

**改动入口**

kernel/lifecycle.rs 的 stop、commands.rs 的 stop_kernel、shell/process.rs 的 terminate_process_tree，以及正常退出中复用该行为的调用方。

**实施方案**

1. 复用并收敛现有进程组停止原语；完成条件覆盖本壳启动且仍归属本轮运行的进程组。
2. 保存并核验启动时的进程身份与进程组归属。不得事后按任意历史 PID 推导 PGID 并强杀。
3. 在有界宽限时间内请求退出，组长先退出后仍处理受管理的存活后代；组收尾与主进程回收的顺序必须保留可证明的所有权。不得简单改成 try_wait 已回收组长之后无条件 kill(-旧 PID)。
4. 对 PID/PGID 复用、权限不足和身份不确定给出明确失败/未知状态，不误报全部停止。停止失败或无法确认时保留可用的 Child、PID/runtime 身份和诊断，不无条件清空记录或写成 Stopped；重启入口只有确认停止成功后才可派生新内核。
5. 保持 Windows Job Object/进程树停止实现；不能因共享函数整理削弱它。
6. 超出进程组、主动脱离管理的进程不作“全部已回收”承诺，说明可观测边界。

**验收标准**

- [ ] 正常组长与后代均退出。
- [ ] 组长立即退出、后代忽略 TERM 时，后代仍被正确收尾。
- [ ] 组长和后代都忽略 TERM 时，有界升级处理并回收。
- [ ] 进程已退出、PID 记录过期或身份不符时不误杀。
- [ ] 权限不足或仍存活时返回真实结果，不清成虚假的成功状态。
- [ ] 重复停止和并发启停在现有锁约束下行为一致。
- [ ] Windows 原有停止、退出与 Job Object 路径定向回归通过。

**完成标准**：用隔离进程夹具驱动实际停止实现；Linux POSIX 夹具只证明通用行为，Intel macOS 的原生入口仍需 OPT-09 验证。

依据：[当前停止逻辑](https://github.com/July-X/dsh-xlink/blob/f448970fc206fe747f82dd6d889b8f98144a7fae/src-tauri/src/kernel/lifecycle.rs#L1832-L1879) · [现有公共终止原语](https://github.com/July-X/dsh-xlink/blob/f448970fc206fe747f82dd6d889b8f98144a7fae/src-tauri/src/shell/process.rs#L828-L873)。

### OPT-05 按实例身份恢复遗留内核

**负责人建议：Rust 实例与运行时维护者。优先级：P2。依赖：OPT-00、04。初始状态：待实施。**

**已确认问题**

启动扫描仍使用 cwd 等于壳 data_dir 的条件；现役 DshAdapter 使用实例 workspace 或外部工作目录，因而该回收条件与当前布局不一致。

**改动入口**

lib.rs 的启动恢复、kernel/lifecycle.rs 的 reap_orphans、kernel_adapter.rs、shell/instance.rs 与 paths.rs。

**实施方案**

1. 以本壳模式对应的实例注册表和 PID/runtime 记录定位候选，不以 cwd 是否等于壳目录识别所有权。
2. 结合可获得的启动时间、命令行、安装路径、实例 home、记录端口等信息校验身份；仅凭端口占用不够。
3. 对确认属于本实例的遗留内核，完成有界停止，再进入新启动流程。身份不确定时保留进程并展示原因。
4. 不直接认领携带旧壳桥地址的进程为健康新实例；如采取认领方案，必须另行证明全部桥与资源重连。
5. 将启动恢复与普通启动放在一致的生命周期锁下，避免边扫描边再次启动。
6. 记录发现、判定、处理和失败原因；恢复失败时禁止继续启动一个可能冲突的新内核。
7. 不跨 dev/release 清理，不动用户手工运行的外部 dsh。

**验收标准**

- [ ] 默认实例 workspace 下的遗留内核能被识别并处理。
- [ ] 配置外部 workspace 后仍能正确识别。
- [ ] dev、release 同时运行时仅处理本壳所属遗留实例。
- [ ] 相同端口的无关服务、用户手工启动的 dsh、复用 PID 均不被误杀。
- [ ] 记录缺失或损坏、查询工具不可用、身份不足时显示明确状态。
- [ ] 壳被强制终止后重开，旧桥失效，新启动使用新桥且无重复受管内核。
- [ ] 恢复失败不会继续覆盖运行状态或宣称已经恢复。

**完成标准**：夹具采用实际适配器启动形状，覆盖默认与外部 workspace；不得只用旧 cwd 规则造测试。

依据：[启动恢复调用](https://github.com/July-X/dsh-xlink/blob/f448970fc206fe747f82dd6d889b8f98144a7fae/src-tauri/src/lib.rs#L215-L237) · [旧 cwd 判据](https://github.com/July-X/dsh-xlink/blob/f448970fc206fe747f82dd6d889b8f98144a7fae/src-tauri/src/kernel/lifecycle.rs#L1762-L1819) · [现役 workspace](https://github.com/July-X/dsh-xlink/blob/f448970fc206fe747f82dd6d889b8f98144a7fae/src-tauri/src/kernel/kernel_adapter.rs#L449-L475)。

### OPT-06 绑定预检与正式安装物料

**负责人建议：Rust 安装与预检维护者。优先级：P2。依赖：OPT-01、02。初始状态：待实施。**

**已确认问题**

预检安装并验证一次，应用时再按原 spec 下载。latest、可变 tag 或依赖重新解析可能让两阶段使用不同内容；事后提示版本变化不能形成可靠的预检闭环。

**改动入口**

plugins/precheck.rs、plugins/center.rs、pkg/fetch.rs，以及暂存、依赖安装、发布与回滚路径。

**实施方案**

1. 预检生成不可变的安装计划，记录 schema、plan id、实际来源、完整版本/commit、内容摘要、内核版本、实例/profile 和相关设置指纹。
2. 计划以已经解析出的物料为准，不把 latest、短 hash 或可变 tag 当最终内容身份。
3. 固定依赖闭包及构建所需信息；优先复用已验证物料。正式应用不得重新按浮动约束解析依赖或重新执行未经绑定的构建。
4. 如跨临时目录搬移会影响路径、原生依赖或构建结果，应明确可复用边界并在最终物料上重新验证，不声称摘要相同就保证所有运行环境相同。
5. 应用前校验计划未过期、未被修改、实例/内核/profile 条件一致，平台、架构和影响物料兼容性的 Node 版本一致；目标实例处于允许修改的停止状态。
6. 缓存缺失、摘要变化或环境不一致时拒绝应用并要求重新预检，不能降级成普通安装成功。
7. 延续 tmp/new/final/backup 的恢复设计；计划缓存只清理本系统证明归属的对象，限制占用并处理失败残留。

**验收标准**

- [ ] 预检后 latest 或 Git tag 指向变化，应用仍使用已验证物料或明确拒绝。
- [ ] tarball、解包内容或计划字段被篡改时拒绝应用。
- [ ] 相同主包版本但依赖解析变化时，不绕过预检绑定。
- [ ] 内核版本、目标实例、profile 或关键设置变化后，旧计划不能直接应用。
- [ ] 缓存丢失、计划过期、构建结果不可迁移时给出重新预检出口。
- [ ] 发布中断、磁盘写入失败、启动探测失败时保留旧可用安装和可定位证据。
- [ ] 正式安装记录的来源、版本、commit、摘要与预检报告一致。
- [ ] 重复点击应用不产生并发安装或重复发布，正在被真实实例引用的候选不会被过期清理删除。

**建议计划字段**

~~~json

  "schemaVersion": 1,

  "source": {
    "kind": "npm-or-git",
    "canonical": "normalized-source",

    "commit": "full-commit-if-applicable"
  },
  "artifact": {
    "algorithm": "sha256-or-sha512",
    "digest": "content-digest",

    "preparedTreeDigest": "prepared-content-digest"

  "context": {
    "kernelVersion": "tested-kernel-version",
~~~

### OPT-07 明确兼容性预检的信任边界

**负责人建议：安装模块维护者与前端开发。优先级：P2。依赖：OPT-01、06。初始状态：待实施。**

**已确认边界**

当前预检是临时实例、目录与端口隔离。Git 来源在缺少预构建入口且声明 prepare 时会运行构建脚本；它不提供 OS 级恶意代码隔离，也不能撤销脚本对外部目录的全部影响。

**实施要求**

1. 用户文案统一为兼容性预检，说明它验证安装、接线和启动结果。
2. 展示实际来源、确切版本/commit、准备执行的构建阶段和预检覆盖范围。
3. 在操作发生前说明来源代码会以当前用户权限执行；复用现有安装动作表达，不额外堆叠重复确认弹窗。
4. 报告区分取源校验、构建、插件规范、启动探测与物料绑定结果，不给“安全无害”的整体结论。
5. 错误保持进度面板开放并引用日志；回滚只描述实际恢复的受管状态。
6. 不自动复制真实实例凭据到预检实例；需要模型交互的测试优先使用 stub。相同 OS 用户运行的代码仍可能访问该用户可读文件，不能因未复制凭据就声称实现了权限隔离。
7. 来源或候选内容变化后不得沿用旧来源展示和执行选择；取消后不再继续构建、加载或接线。
8. 不在本任务中建设容器或系统级沙盒，若未来需要应独立设计。

**验收标准**

- [ ] 预检与安装界面展示的来源和 OPT-06 计划一致。
- [ ] 需要 prepare 的路径在执行前给出准确说明。
- [ ] 各阶段失败能定位，不被泛化为无意义的“安装失败”。
- [ ] 报告明确哪些检查通过、失败、未执行。
- [ ] UI 和文档不声称临时目录能阻止恶意插件访问用户文件。
- [ ] 取消后没有继续启动脚本，预检实例无真实凭据副本，日志与报告不暴露秘密。
- [ ] 不通过关闭所有插件能力或禁止所有 Git 插件回避问题。

依据：[沙盒范围](https://github.com/July-X/dsh-xlink/blob/f448970fc206fe747f82dd6d889b8f98144a7fae/src-tauri/src/plugins/sandbox.rs#L13-L29) · [prepare 执行](https://github.com/July-X/dsh-xlink/blob/f448970fc206fe747f82dd6d889b8f98144a7fae/src-tauri/src/plugins/center.rs#L1468-L1542)。

## 六 测试执行规则与完成标准

### 6.1 定向验证

日常开发按任务选择实际受影响的测试与检查。以下命令均为仓库已有入口；具体筛选名称以实施分支为准，不将整张清单重复执行于每次小改动。

~~~sh
# 前端变动的构建与产物检查
npm run build:ui
npm run check:ui-bundle
~~~

Rust 使用 debug profile 的相关测试，按任务需要执行 cargo check、格式及 Clippy。release 条件编译检查保持现有要求。**OPT-08 完成后才使用隔离的 npm run e2e 入口进行本轮原生测试。**

发布候选按仓库既有发布规则，在相同候选代码状态上完成一次全量 npm run check；代码状态改变后，按影响重验并更新候选证据。不得用几轮不同提交上的零散成功拼成“当前版本全部通过”。

### 6.2 每项任务的统一完成标准

- [ ] 已定位并修改生产调用路径，缺陷触发条件得到处理。
- [ ] 核心回归执行真实逻辑，不只断言源码包含某个字符串。
- [ ] 正常、失败、重复操作及必要并发场景有对应结果。
- [ ] 涉及门禁规则时做过目标明确的反向验证，失败原因命中该规则。

- [ ] 错误文案准确，长任务失败保留进度与日志出口。
- [ ] 用户可见行为、目录或安全策略变化已同步当前文档。
- [ ] 证据对应实际执行 commit、平台与产物，未执行项如实记录。

**状态建议**：待实施 → 实施中 → 已实现待验证 → 已验证待合入 → 完成。资源缺失单列 blocked_resource；某项代码已实现但原生必测未执行时，不得直接改为完成。

### 6.3 发布门禁

1. M1、M2 本轮包含的缺陷修复全部达到任务完成标准。
2. 本轮 release 必测矩阵中的 fail 为零；必测项的 skip/not_run 不算通过。
3. Windows 与 Intel macOS 的证据对应同一候选提交，产物版本和内置资源可核对。
4. WebDriver 未进入 release，更新清单与签名对应最终产物。
5. 如明确缩小发布范围，应逐项记录未覆盖能力和影响，不能保留“全量验收通过”的措辞。
