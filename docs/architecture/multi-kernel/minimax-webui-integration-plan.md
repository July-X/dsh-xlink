# MiniMax Code 第二工作台接入计划

状态：可行性计划，待实施。日期：2026-11-06。分支：`codex/minimax-webui`，源码基线 `5d9a068f`。

## 1. 结论与首版范围

可按第二内核族接入。Xlink 托管 `mcode-webui` 进程和独立工作台窗口，页面、登录、会话、权限审批、模型、技能和插件由 MiniMax Code 自己管理。首版每种壳模式配置一个 MiniMax 实例，允许它与 DSH 同时运行。能否交付内嵌工作台，取决于两个平台的登录、项目选择和任务验证。

首版使用用户已安装的 npm 包，提供检测和安装指引。自动下载安装、更新和卸载，任意外部 URL 接入，多个 MiniMax 实例的管理入口，DSH 扩展接线、通知、用量或会话跨平台合并，均列为后续独立事项。远程控制、浏览器扩展桥、IM、Mini App 应用功能沿用 MiniMax 自有界面，本轮验收 Mini App 监听端口的隔离与回收。

本计划独立于 [11 月后续开发计划](../../operations/development-followup-2026-11-plan.md)。[旧 sidecar 设计](../kernel-binary-sidecar-seam.md)保留早期背景，本轮开发以本计划为准。官方 WebUI 已覆盖聊天前端，首版移除自建前端、ACP 事件归一化、源码构建和独立接管 OAuth 的工作项。

## 3. 运行边界

### 安装识别

- 首次点击「检测安装」或启动前探测。优先读取用户在面板明确选择的包目录和 Node 路径，其次检查从可信 Node/npm 安装布局解析出的全局包目录。自动检测无结果时显示设置路径的入口，覆盖 Windows GUI 的 npm shim 和 Intel macOS GUI 缺少终端 PATH 的情况。
- 规范化实际文件路径，核对 `package.json` 的包名、版本、`engines` 和 `bin.mcode-webui`，验证入口真实位于包目录内。使用匹配的绝对 Node 路径直接启动脚本。路径保留参数边界，不执行同名 PATH 命令或用户输入的命令串。检测区分包未装、包或入口无效、版本未验、Node 不兼容、原生依赖不可用。检测结果展示来源路径和版本，方便用户确认。
- `0.1.7` 声明 Node `>=22.19 <23 || >=24.2 <27`。本机服务证据来自 Node `26.12.0`；仓库的托管 Node `24.20.0` 虽满足版本范围，仍须用配套 npm 安装环境验证 `better-sqlite3` 与 `node-pty`。用实际选定的 Node 运行原生依赖探测，明确报告 ABI 或安装脚本问题。依赖构建和重装由用户在 Xlink 外发起。
- 用户先按官网指引安装候选版本并允许官网列出的原生依赖脚本，再回到管理页重新检测。外部安装原样只读使用，探测与启动均重新确认版本和入口。包元数据用于识别本机安装，来源可信度仍取决于用户安装渠道。后续如新增壳内安装，应单独设计固定来源、下载摘要校验与无摘要拒装，沿用 [运行时边界](../runtime-boundaries.md)。

候选版安装指引示例，适用于支持 `--allow-scripts` 的 npm。P0 确认两平台的安装组合后再写入界面。

```text
npm install -g @minimax-webui/minimax-code@0.1.7 --allow-scripts=better-sqlite3,node-pty,bufferutil,utf-8-validate
```

### 实例、数据与端口

- 通过 `paths::*` 和实例注册表记录当前壳的 `mcode` 实例，按现有 id 规则分配 dev/release 不同实例。应用数据在 `<xlink_home>/kernels/mcode/instances/<id>/home/`，以 `MINIMAX_DATA_DIR` 明确传入。注册记录、运行锁和工作台浏览器档案按模式及实例隔离。测试应核对重定向后的实际路径，特别检查凭据存储、浏览器档案和工作区选择是否越过实例边界。
- Xlink 管理的 MiniMax 独立登录。MiniMax Desktop/CLI 使用的数据目录不自动共享或导入，避免已有 SQLite 迁移、并发写入与账户状态耦合。用户在 WebUI 内主动选择的项目是任务工作区，和 MiniMax 自身的运行数据是两项。继续由 DSH 默认实例驱动现有资源页与用量页。
- 为 WebUI 与 Mini App 各分配并记录一个端口。初始分配排除已有实例保留项、实例锁和实际监听，随后尽量复用同一对端口，保持工作台站点来源稳定。启动发现端口被占用时显示对应端口，用户可在停机状态重分配，提示页面可能需要重新登录。绑定竞争时回收本轮已启动进程和已开端口，状态回到可重试。
- `McodeAdapter` 显式设置 `WEBUI_HOST=127.0.0.1`、两个端口和 `WEBUI_OPEN_BROWSER=0`。子进程保留必要的代理与证书配置，按仓库子进程规则处理 `NODE_OPTIONS`，过滤会覆盖端口、数据目录或浏览器行为的变量。维持包的正常权限和连接模式，禁止传入 `--full-access`。前端无权提交自选启动参数、端口 URL 或数据目录环境变量。

### 进程、就绪与凭据

- 采用当前实例锁和进程组/树工具。首次启动记录归属，状态与停止按本壳、内核族、实例、启动代次和子进程核验。优先使用已持有的子进程句柄，重启后的遗留进程另外校验进程创建身份、入口和实例证据。PID、端口或命令名均不可单独用于收养或停止；证据不足时报冲突并保留诊断。DSH 安装路径回退与 DSH 进程识别规则仅用于 DSH。
- `Ready` 要求本轮子进程存活、两端口属于预期启动、WebUI 首页可识别且连接可建立。HTML、WebSocket 和来源检查以候选版本探针确认。仅开放 TCP、旧日志或任意 HTTP `200` 不足以标记成功。探针直连已验证的回环端口，不跟随任意跳转。启动超时、退出和探针失败返回不同错误。
- 优先加载已验证的本机根地址，由页面获取自己的连接配置。若候选版本确需启动 URL 携带凭据，仅在 Rust 本轮启动和开窗状态中短时持有。进程输出流在落盘前统一处理，覆盖 `credential token:`、URL 查询参数以及独立、分片、stdout/stderr 中的打印方式。日志查看、诊断导出、前端状态和运行记录只保留脱敏值。回环服务的边界以实际包行为为准，验收不能从跨站拒绝推导出所有本机客户端均需要 token。
- 正常停止先使用平台验证过的退出路径，确认进程树退出后再清运行记录、关闭所属窗口和释放端口；停止失败保留可重试的进程证据。启动与停止按实例串行，应用退出加全局停止门闩，禁止出现确认退出后又派生一个工作台。守护或崩溃后重启只清理能确认归属的遗留进程，首版由用户手动重新启动。

## 4. UI 调整

### 信息架构与布局

- 侧栏「工作台」组在「概览」之后、「用量分析」之前新增「MiniMax Code」。它进入管理页，点击导航本身不启动服务。收起侧栏时图标提供同名 tooltip 和可访问名称。现有「官方对话」入口继续打开官网对话，与 MiniMax 本地工作台分列。
- 管理页标题为「MiniMax 工作台」，副标题为「在本机运行 MiniMax Code，登录与会话保存在当前实例」。上方一张状态卡给出运行状态和主动作，下面「安装与运行环境」显示包、Node、安装来源和检测动作。「运行详情」折叠区提供数据目录、监听端口、版本和脱敏日志入口。安装说明含官网链接，显示可复制的候选版本安装指令和原生依赖提示；缺依赖时直接指向这里。
- 沿用固定 `1040×748` 管理窗口、侧栏宽度和设计 token。卡片按钮支持键盘操作，状态有文本，错误区提供原因、下一步和日志路径。路径允许换行或省略加完整 tooltip，收起侧栏、窄内容区、长路径和中英文混排不得产生横向滚动。浅色、深色、系统三种模式均验。
- 独立窗口标题为「MiniMax 工作台 · Dsh-Xlink」，使用可缩放的原生窗口，默认内容宽度至少 `1080px` 且按可用屏幕收敛。保留 MiniMax 页面自己的响应式布局。已有窗口只聚焦，新启动代次重新建窗以刷新连接配置。关闭 MiniMax 窗口只关页面，服务继续运行，管理页按钮变回「打开工作台」。管理面板收起与恢复沿用 `shell/resident.rs`。


### UI 与窗口接线

- `SideBar.vue` 声明导航项，`App.vue` 登记面板。MiniMax 管理页使用仓库现有 Composition API 组件形态，通过专用 store 调 `shell/bridge.js` 的动作；组件渲染状态和发出意图，派生展示用 `computed`。Rust 是安装、运行和窗口状态的唯一真值。进入管理页、壳恢复前台、操作完成及窗口关闭后刷新，迟到的查询响应不得覆盖新启动代次。
- 拟新增 `get_mcode_status`、`detect_mcode_installation`、`save_mcode_installation`、`start_mcode`、`open_mcode_workbench`、`stop_mcode` 与停机重分配端口入口。普通状态返回安装结果、版本、两个端口、运行阶段、窗口是否打开、可恢复错误和日志路径。启动进度走现有 Channel 约定，命令结束后关闭事件流。启动和开窗按当前壳实例寻址。实际 IPC 字段和错误枚举在开发阶段只维护一份契约，管理面板与 Rust 联测。
- MiniMax 窗口使用独立 label（拟 `mcode-workbench`）、实例浏览器档案和最小权限。MiniMax 本机顶层页面只导航到本轮认可的 origin，外部登录按 [窗口架构](../window-architecture.md) 的授权弹窗链处理，继承发起方档案，回调来源必须经 P0 实测。远端页面无管理面板命令权限，通用窗口交互如需 IPC 单独收窄。复用通用窗口构建、底色和当前窗口外观；DSH 草稿、健康探针、桥接与 DSH 专用主题信号按族隔离。主题接线在 P0 确定稳定偏好来源，按现有单窗口主题契约实现。
- 托盘退出确认同时列出实际运行中的工作台。保留 `request_id` 认领，正常确认和原生兜底汇合到 Rust 的同一套退出编排，确认时重新查询归属并停止全部本壳管理的实例。某项停止失败就保留壳与剩余任务入口，错误明确是哪一个。现有 DSH 自动启动仍归 DSH 管理，MiniMax 首版只由用户点击启动。

## 6. 验收标准

自动化覆盖适配器、IPC 契约和可重复的状态转换。两平台真实服务与安装版用下表验收，受控夹具不能代替 MiniMax 实际 WebUI。

| 编号 | 操作 | 通过条件 | 验证 |
| --- | --- | --- | --- |
| A01 | 未装包、空 PATH、选错路径、版本不符、原生模块损坏，随后选择正常安装 | 逐项显示对应原因和操作，探测没有创建服务、替换包或写用户目录。正确检测展示包与 Node 版本，路径带空格和中文仍可启动。 | 自动 + 双平台 |
| A02 | 从管理页双击启动或在两个壳模式几乎同时启动 | 每实例只有一个服务，两端口有效且回环绑定，互不占用。HTML 和 WebSocket 就绪才转为运行，进度事件在启动命令结束后停止。 | 自动 + 双平台 |
| A03 | 分别占用 WebUI 与 Mini App 端口，伪造返回 `200` 的 HTTP 服务，模拟旧 PID 复用与启动中退出 | 展示正确端口或阶段，拒绝陌生服务；竞争失败只回收本轮进程，陌生进程仍在，清理完成后可重试。 | 自动 + 双平台 |
| A04 | 独立窗口登录测试账户，选含空格和中文的测试项目，发送一条产生权限请求的任务，分别审批和拒绝 | 登录回到原窗口；工作目录准确；审批可完成，拒绝不会执行对应操作；能读到任务结果。关窗和重开恢复原会话，完整停启后数据和登录可用。 | 双平台真实服务 |

## 7. 交付边界与回退

- Intel macOS 的原生依赖、WKWebView 登录/选目录、候选版本真实任务、凭据与档案隔离、停止过程是首批验收前置。若只剩系统浏览器能走通，可用它继续诊断服务，不计作壳内工作台验收通过。
- 开发阶段仅在隔离构建中打开入口。回退时先停 Xlink 管理的 MiniMax 服务，再撤掉入口或回到旧构建，保留 MiniMax 实例与外部安装目录。重新启用应从原有实例读取数据，不自动迁移、降级或删除 SQLite。
