# 事故经过存档

`AGENTS.md` 里每条纪律背后都有一次真实踩坑。纪律本身留在 `AGENTS.md`（它受运行时
的指令字节预算约束——上限由内核的 `agent-instructions.maxBytes` 给出，现为 65536，
超出部分会被截断），事故经过归档在这里，供需要
追溯时查。

写作约定：每条写清 **现象 → 根因 → 结论**，结论一句话。日期用事件发生日。

---

## 1. 给内核打补丁「可逆所以安全」是答错了问题（2026-09-29）

**现象**：有人给 `dsh-client-ui-renderer/lib/client.js` 打过一个补丁——「作用域缺席时
挂起而不是抛错」，随 0.3.5-rc.4 发布。

**经过**：该补丁的论证是「可逆 + 有备份 + 有哈希校验」，很快被认定为违背产品定位并撤销。

**结论**：那套论证回答的是「破坏可不可逆」，不是「该不该做」。两者是不同的问题，
而「该不该」在 `AGENTS.md` 的只读内核边界那一条里已经答完了。可逆性不构成写入理由。

---

## 2. 从仓库删掉补丁，不等于用户机器上消失（2026-09-29）

**现象**：删掉两个补丁目录后重新装 rc.4，用户安装目录 `<install>/patches/` 下
**两个目录仍在**。

**根因**：更新只覆盖与新增，不清理上游删掉的东西。

**结论**：要真正清干净，得让应用自带一份「本次构建带了哪些补丁 id」的名单（构建期
生成），再在 `load_patches` 时按它裁剪资源目录。在此之前，删除补丁后必须在发布说明里
写明它不会自动卸载。

---

## 3. PowerShell 恢复文件后不更新时间戳，验的是旧产物（2026-09-30）

**现象**：给 `kernel::tests` 做反向验证，「备份 → 改坏 → 跑测试（红）→ 恢复」四步走完，
恢复后**仍然红**。

**根因**：PowerShell 的 `Copy-Item` **保留源文件的 `LastWriteTime`**。恢复那一步写回去的
是比「改坏」那一步**更早**的 mtime，cargo 判定无需重编译，于是第二次跑的还是改坏时的
产物。真相是根本没重编，不是断言不成立。

**结论**：恢复后补一句 `(Get-Item <file>).LastWriteTime = Get-Date` 再跑。
同理，**反向验的红必须是「改坏的当次」的红**——中途任何一次重编失败都可能让红变成
「编不过」而不是「断言不成立」，那不算验过。

---

## 4. 版本号只改两处，门禁比文档多查一处（2026-10-03，v0.3.9-rc.1）

**现象**：`package.json` 与 `src-tauri/tauri.conf.json` 都改了版本，`Cargo.toml` 漏了。

**后果不是编译失败**：crate 版本与壳版本不同源，Tauri 打的产物里元数据会带着一个
对不上的壳版本号，updater 与「关于」面板显示的都可能不是这个 release。是
`check:invariants` 的 `[versions]` 项当场抓出来的。

**结论**：**改版本号一律三个文件一起改**，别等门禁报。

---

## 5. `bundle.resources` 少一步生成，CI 全红而本地全绿（2026-10-09，v0.4.4）

**现象**：新 checkout 上第一个 cargo 命令死在
`resource path 'resources/builtin-plugins' doesn't exist`。表现为 quality job 的
`cargo test` 与两个平台的 `tauri build` 报同一行、而 `Publish release` 被跳过——
**red 的表象与真正原因隔着两层**。该 break 在 main 上已连红 4 个提交。

**根因**：`src-tauri/resources/builtin-plugins/` 是构建期产物（`.gitignore` 挡住，
由 `npm run prep:builtin` 从 `plugins/openai-oauth/` 生成），而 build script 校验的是
登记在 `bundle.resources` 里的**每一个**路径。本地 `npm run dev` / `build` / `check`
都各自带着这一步，所以**本地永远看不出来**。

**结论**：`scripts/dev-builtin.test.mjs` 钉住接线形状——任何会跑
`cargo build/check/test/clippy` 的 workflow job 都必须先生成资源，并带「判据空转时
必须红」的兜底。新增一个同类生成目录时，把它的生成步骤挂进判据，不要只改 workflow。

## 6. 常驻行为「抄一份就会漂」的三次实例（2026-10-02 / 10-05 / 10-09）

**a. 恢复动作被抄了一份（10-02）**：`lib::show_main_shell` 与工作台拉绳的
`focus_main_shell` 各自实现了一份唤回逻辑，Windows 上两边互调过一次，直接
`thread 'main' has overflowed its stack`。

**b. 收起动作绕过了统一实现（10-05）**：登录自启分支裸调 `window.hide()`，macOS 上
激活等级没降到 Accessory——进程带着「在运行」小点的 Dock 图标、**零可见窗口**地挂在
后台，点它还没反应。`RunEvent::Reopen` 只抬工作台，而 macOS 的激活不会替我们显示
`hide()` 掉的窗口，抬不到时必须兜底 `show_main_shell`。

**c. 任务栏按钮只删不补（10-09）**：删除走 `ITaskbarList::DeleteTab`，而 `show()` 不会
让它自己回来。补回的那一份曾经住在 `tray::show_main_shell` 而**没有任何调用方**走它，
于是登录自启藏起面板后，用户点启动项唤回的窗口在任务栏上没有按钮。那份实现已删。

**结论**：常驻行为（关闭 / 收起 / 恢复）三件事各只有一份实现，全在 `shell/resident.rs`。
抄一份就会漂，而漂在 Windows 上往往直接是崩栈或「点了没反应」。

## 7. 「只搬进 release」防的是再犯，防不了已经犯的（2026-09-28）

**现象**：release 侧工作台从此是空列表，而 `~/.dsh` 已空——搬不动第二次。

**根因**：dev 壳在闸门落地（`713bb40`）前 15 分钟就把 `~/.dsh` 并进了 `default-dev`。

**结论**：补的是回收路径 `home_recovery`——只读扫描别的实例 home 里本实例缺的
`sessions/` 与 `attachments/`，用户拍板后**复制**过来，源永不删除、目标已有条目永不覆盖。
执行前要求**目标实例**的内核未在运行（判据按实例 pid 文件而非本壳工作台：用户自建实例
留在两份注册表里，另一壳正跑着它同样要拒）。UI 挂在「数据迁移」面板的「找回历史会话」
卡片上（`scan_misplaced_home` / `recover_misplaced_home`）。

## 8. `DSH_CUSTOM_SKILL_DIRS` 注了半年，内核从来不读（2026-09-30 查清）

**现象**：技能「装得上、内核看不见」持续约半年，无人察觉。

**根因**：`dsh-skill-filesystem` 的 `customSkillDirs` 只从 `cordis.patch.yml` 的插件配置
读；0.2.0-rc.2 全树 3481 个 js/d.ts 里无 `CUSTOM_SKILL` 命中。

**结论**：**判断「内核到底认不认某个注入方式」必须实测，不能读接口名推断**。已用
`--dump-config` + `skills/list` RPC 端到端验证。接通靠的是 `ensure_skill_wiring` 往
`cordis.patch.yml` 追加的 loader 行，不是那条 env。
## 9. 扫源码的判据命中了文件头的注释，反向验才发现（2026-10-14）

**现象**：给 `plugins/memory/host/index.js` 加了一条判据「注入块要显式 `interpolate: false`」。
把真代码改成 `interpolate: true` 之后**判据照样绿**（19 条插件用例全过）。

**根因**：判据先用 `replace(/^\s*\/\/.*$/gm, '')` 剥注释，**只剥行注释**；而该文件的
`/** … */` 头注释里正好写着「`interpolate: false`——记忆正文原样带出去」。于是正则命中的
是解释，不是代码。同一段判据里另外几条（`beginStep(` / `applyStep(` / `applyResult(` 不许出现）
有同样的风险。

**结论**：**扫源码的判据必须连块注释一起剥**，且每条判据都要真的反向验一次——不是「改坏了看它
红不红」走个形式，而是**先确认它现在绿得有理由**。修法是
`src.replace(/\/\*[\s\S]*?\*\//g, '').replace(/^\s*\/\/.*$/gm, '')`，改完再反向验一次：
`interpolate: true` 立刻红。这与根 `AGENTS.md` 那条「锚点找在原文上，匹配再过 `productionRust()`」
是同一件事的 JS 版本——那边是 Rust 判据，这边是插件装配层的判据，坑一样。

## 10. 把令牌抹掉一半，比不抹更坏（2026-10-15）

**现象**：诊断日志与模型输入共用的凭据掩码，在 `Authorization: Bearer abc.def.ghi` 上输出
`Authorization=*** abc.def.ghi`——**令牌原样留着**，而这一行看起来已经脱敏了。看到 `***` 的人不会
再看第二眼，所以它比完全没抹更危险。

**根因**：键名规则（键名含 `authorization` → 抹掉值）先命中，而它的值扫描到**第一个空格**就停，
值只是 `Bearer` 这个词；真正是凭据的那一段在它后面。

**是怎么发现的**：为了给 P2 的提取输入做脱敏，在插件里**逐条复刻** Rust 那套形状（设计原本写的是
「复用 `diagnostics::run::sanitize`」，但那份函数还带 480 字符截断与 home 折叠，是给日志行用的，
套到 64 KiB 的模型输入上会把输入毁掉）。复刻时先用原始实现跑夹具，第二组就撞见了。

**结论**：**同一个判据在两侧各有一份时，「逐项对比」的判据比「都写了」重要**——漂的那一侧不会报错，
它只是**少抹掉一个**。这次两边一起修，夹具共用，键名表与方案名由冒烟测试读 Rust 源码对比钉住。
两条附带教训：① 反向验是唯一能证明修复真的在修的办法（摘掉修复，用例立刻红在
`"Authorization=*** abc.def.ghi"`）；② 修的过程中又发现第二处反向错误——空格也被当成分隔符，
散文里的「token 这个词」会被吃成 `token=***`（中文没有词间空格，一吃就是一整句），
**漏抹与误抹要分开评估**：误抹的是用户写下的正文，而正文是唯一的价值。

## 11. 反向验的变异要**真的把东西拿掉**（2026-10-15）

**现象**：给「记忆清单里引用的判据必须真的存在」写了一条新不变量，然后反向验——把
`src-tauri/src/memory/store.rs` 里的判据 `the_same_body_is_not_collected_twice` 改名成
`the_same_body_is_not_collected_twice_renamed`，判据**照样通过**。看起来是新判据假绿。

**根因有两层，第一层是变异的问题**：新名字**把旧名字当子串包含了**，而判据用的是包含关系
（`includes`）。所以「拿掉」这件事根本没发生。改成真正的改名（`duplicates_are_refused_here`）
之后立刻红。**结论：反向验里，先确认「我改的那一下真的让被判的东西消失了」，再谈红不红。**

**第二层是判据自己的问题（在更早一次尝试里现形）**：为了让判据只认代码、不认解释，先写的是
「剥掉所有 `/* … */`」。结果源码里有 `'**/*.js'` 这样的 glob 字符串，它的 `/*` 会与**几千行
之后**的 `*/` 配成一对，一次吞掉一大片——**37 条明明存在的判据全被判成找不到**。改成「只剥
**行首**的注释（前面只允许空白）」之后，`///` 文档注释照样剥得到，而假配对基本不可能发生。
这条与 §9 是同一个形状的第二次：**扫源码的判据，剥注释的方式本身就是判据的一部分**，
剥多了会假红、剥少了会假绿，两个方向都要反向验。

## 12. 插件的配置被断言拒绝时，它是**静默不激活**的（2026-10-15）

**现象**：为了让一次真机会话里发生压缩，给 `compaction-basic` 打了配置补丁。跑了三轮，
会话日志里**一次 `compaction/start` 都没有**，而我的注意力全在桩桥有没有收到请求上，于是
一路往「阈值算错了」「压力信号不对」的方向猜。

**真相在第一次运行的输出里**：`compaction-basic: Error: BasicCompactionConfig.maxTokens
(explicit or from headroomTokens) (0) must be a positive integer`——`headroomTokens: 0` 让
`maxTokens` 默认取到 0，构造期断言直接抛，**整个插件从未激活**。而它在终端上只有一行
`dsh: warning: 1 entry did not activate`，后面跟一行错误摘要，很容易被当成噪声。

**结论**：**每次真机跑完先读 `did not activate` 那几行**。配置被断言拒绝时的症状（插件不在栈里）
与「条件没到」完全一样：都没有事件、都没有报错、都只是「什么也没发生」。这与 §8 那条
「判断内核到底认不认某个注入方式必须实测」是同一件事的两面——那边是「读接口名推断」不行，
这边是「读自己的配置以为它生效了」也不行。**判据是运行输出里的激活行，不是配置文件里的那几行。**

## 13. 做 A/B 之前，先确认**被测量的那个量真的会动**（2026-10-15）

**现象**：给「压缩之后恢复注入预算」做真机验收，看到 6 个回合里有 6 次 `/v1/memory/context`，
就下了结论——因为「没有重置时一个会话最多 5 次」。第二天回头核对计数逻辑，发现**两个前提都不成立**：

1. 桩桥当时回的是 `hits: []`，插件从没「应用」过任何东西 ⇒ `injections` 一直是 0 ⇒ 每回合都走
   refresh 路径。**取不取检索与压缩无关**，那个 6 什么也证明不了；
2. 换成回真命中之后（`/note` 回报证明注入被计数了），仍然看不出差别——因为**每次 `dsh headless`
   都是一个独立进程**，插件的会话状态每回合从零开始，`injections` 同样涨不到 3。

**结论**：**A/B 的前提是「处理组真的改变了被测量的那个量」**。这次测的是「注入预算被重置」，
而被测量的量（`injections`）在两组里**都**是 0——所以两次实验都是假绿，只是第二次的假绿更隐蔽
（有 `/note` 回报看起来很实证）。动手前该问的三个问题：**这个计数在哪累加？它在两组里分别是多少？
我的观测方式能不能把它区分开？** 这与 §11 是同一个形状的第三次：那次是变异没把东西拿掉，
这次是**被测量的量根本没动**——「反向验」这一族的坑，核心都是**先确认变化真的发生了**。

## 14. A/B 的两边要**钉到具体版本**——`HEAD` 会随你自己的提交前移（2026-10-15）

**现象**：给「只对成功的压缩重置」这个修复做 A/B。用 `git show HEAD:plugins/memory/host/index.js`
取「修复前」的版本，跑了三轮，结论都是「修复前修复后一样，看不出差别」，于是开始怀疑是钩子顺序
导致重置被覆盖——一个听起来很合理的假设，还写进了清单。

**根因**：那个修复**已经在上一次提交里了**。`HEAD` 不是「修复前」，它是「我最近一次提交」——
而那次提交就是修复本身。三轮实验的两边其实是**同一份代码**，所以当然没有差别；而「没有差别」
被我解释成了「有某种机制抹掉了效果」，还据此编了个假设出来。

**结论**：**A/B 的每一版都要用不可变的坐标钉住**（具体的 commit hash / tag / 文件哈希），
不要用 `HEAD`、`HEAD~1` 这类**会随会话推进而改变**的引用；实验记录里带着「这一版是什么」的
证据（这次是 `rg -c isCompactionDone` 的输出——一查就知道拿错了版本）。
钉住版本之后结论立刻反转：修复前 6 次注入、修复后 3 次，差别清清楚楚；那个「被覆盖」的假设
是错的（插桩轨迹显示重置按时发生、`injections` 1→0、`textLen` 40→0）。
这与 §13 同族：**先确认你测的是什么，再测**——§13 是「被测量的量没动」，这是「被测的两边是同一个」。

## 15. 兜底路径自己没被跑过：假件全绿，接线一跑就炸（2026-10-15）

**现象**：会话日志的读取加了一条 live 兜底（durable 主路失败时改读 `sessionQuery.readSession`），
6 组假件用例全绿，覆盖了「不落盘时不去开句柄」「兜底裁剪范围并带上主因」「兜底也失败时两条原因都在」。
几天后把两端接起来一起跑（真内核 + 真插件 + 真桥 + 真任务表），第一次就炸：

```
等落盘屏障时失败：session "…" is not live in this store；
live 兜底也失败：cannot get required service "sessions" in inactive context
```

**根因**：服务是在 `ctx.inject([...], (scoped) => …)` 的**子上下文**里读出来存下来的。
那个子上下文只在回调期间活着，事后通过它读服务就抛「inactive context」。假件测的是**逻辑**，
而这段接线是**取服务的方式**——夹具里根本没有内核，所以它永远测不到。

**结论**：**兜底路径和主路的接线是两件要分别验的事**。主路天天被跑，兜底只在主路失败时才走，
于是它的接线错误可以安然无恙地活很久——直到真的需要兜底的那一天，两个错叠在一起，
报出来的原因还是主路那条（更容易被当成主路的毛病）。这与 §13／§14 同族：
§13 是「被测量的量没动」，§14 是「被测的两边是同一个」，这条是「被测的那条分支根本没被走到」。
**做法**：任何兜底都要有一条**真的会走到它**的路径（本地就能造——把主路弄坏即可），
并且在两端接起来的运行里至少走一次。

## 16. 夹具的断言强度决定了它能发现什么（2026-10-15）

**现象**：两侧端到端的手动夹具（真内核 + 真插件 + 真桥 + 真任务表）跑出来是**绿的**，
可它打印的任务表里明明有一条任务带着 `inactive context` 的错。原因是断言只写了
「**有候选落下来**」——第 1 条任务成了、候选落库了，断言就满足了；第 2 条怎么死的它看不见。

**更糟的是**：上一次修这个问题（把服务改成「急取快照」）时，我正是拿这条夹具当验收依据的。
夹具绿了，我就记成「修好了」——而真相是**快照本身就是 bug**（`ctx.get` 返回的是绑定当时那个
fiber 的追踪代理，服务 fiber 事后重载，快照下来的对象就失活了）。**弱断言不但发现不了 bug，
还会给一个没修好的改动盖章。**

**结论**：**写夹具时先问「它能发现什么」**。这条夹具后来改成区分两类 error——**业务拒绝**
（去重闸、开关关了、来源对不上）是正常结果，**基础设施失败**（服务失活、读不到会话、落盘屏障失败）
才是链没走通——于是它立刻在复跑里把上面那个 bug 现出来。同族的坑：§13（被测量的量没动）、
§14（被测的两边是同一个）、§15（被测的分支没被走到），这条是第四个：**被测的东西被测了，
但断言弱到测不出问题**。四条的共同点都是「验证动作看起来做了，其实没起作用」。

## 17. 用脚本往 Rust 测试文件里插用例，锚点要含 `#[test]`（2026-10-15，第 5 次）

**现象**：一个用了五次的脚本模式，五次都咬到自己。锚点选在**函数行**上：

```python
anchor = "    fn some_existing_test() {"
src.replace(anchor, new_test + anchor, 1)   # ✗ 旧测试的 #[test] 在锚点上面
```

`#[test]` 在 `fn` 的**上一行**，于是插进来的新用例把它「继承」走了：新用例头上两个 `#[test]`、
旧用例一个都没有。后果是 clippy 报 `duplicated attribute` + 「function is never used」——
**门禁每次都拦住了**（所以没造成真事故），但每拦一次就是一轮重跑（本仓一轮全量门禁约 3 分钟）。

**怎么改**：锚点选在**属性块**上（`#[test]\n    fn xxx(`），或者插在**上一个用例的收尾 `}` 之后**。
前者更稳，因为它同时钉住了「这个函数是个测试」这件事。

**为什么记在教训里而不是只改一次**：它是**可复用的正确做法**缺失，不是一次手误——
同族的 §3（反向验要先确认改动进了产物）、§11（变异要真的移除被引用的东西）都是
「动作看起来做了、其实作用在别的东西上」。判据能拦住它（`-D warnings` 里有
`duplicate_macro_attributes`），但**拦得住不等于代价为零**。

## 18. 扫源码的闸只认一种引号，整类漏判，而闸**绿着**（2026-10-15）

**现象**：新加的不变量 `builtin-peer-imports` 要抓的形状是「插件**静态** `import` 了一个没在
`BuiltinSpec::peers` 里声明的 `@deepseek-ai/*` 包」——真事故就是这么发生的：`openai-oauth` 的
`host/adapter.js` 静态导入 `@deepseek-ai/dsh-llm`，而 `peers` 里没有它，缺 peer 时插件连
`import` 都过不去、整条静默失效。第一版判据的正则写的是单引号：

```js
/import\s+[^;]*?from\s+'(?<pkg>@deepseek-ai\/[^']+)'/   // ✗ 仓库里那个文件用的是双引号
```

于是**双引号的静态导入整类漏判**。反向验（把 `peers` 里的 `dsh-llm` 删掉）时才发现：闸**照样绿**。
换句话说，这道闸的价值是零，而它绿着的那一刻，正是真事故在场的那一刻。

**怎么改**：引号写成 `['"]`，并按**源码里实际存在的形状**把「相对引用」也枚举全——
`export … from`、纯副作用 `import`、无扩展名（`./x` 要试 `x` / `x.js` / `x.mjs` / `x/index.js`）、
两种引号；文件不存在时 `problems.push` 而不是静默跳过。改完再反向验一次：红，恢复，绿。

**为什么记在教训里**：判据的覆盖面要按**仓库里真实存在的写法**枚举，不是按**你脑子里那一份**。
写判据时脑子里想的是「import 语句长什么样」，而源码里长什么样是另一回事——这类错误不会
自己暴露，它只会让闸**安静地变绿**。同族的 §3 / §11 / §17 都是「动作看起来做了」。
另有一条顺带结论：**反向验不只是验实现，它同时是验判据**——这一轮两次反向验，一次逮到
「判据恒绿」（本条），一次逮到「实现真的坏了」（桥换代没执行 `Drop`）。只跑正向的绿，
两者都看不见。

## 19. 反向验的变异**没进文件**、或者**改的不是行为**，而判据照样绿（2026-10-15）

**现象**：给记忆的 schema 窗口（C4 来源合并）做反向验时，四条判据里两条**第一次验出来是绿的**，
而其中一条是真的红的。三种失效形状在同一轮里各出现一次：

1. **变异写了 `assert`，但没写文件**——想把
   `#[serde(default, alias = "source", deserialize_with = "…")]` 里的 `alias` 去掉，脚本按
   **单行**去找那一串；`cargo fmt` 早就把超过 100 列的属性**折成了五行**，于是
   `t.count(old) == 1` 断言失败、脚本没写盘、**文件原封不动**、判据绿。stderr 里那条
   `AssertionError` 和 stdout 的「exit=0」是分开的两条流，`2>&1 | tail` 之后很容易只看见绿。
2. **变异改的是形状，不是行为**——想禁掉合并，写的是
   `if index == usize::MAX { return None; } // MUTANT`：`index` 永远达不到那个值，于是这行
   是死的，**合并照旧发生**，判据也照样绿。这条最阴：它读起来确实像「这里有一道早退」。
3. **真·无效变异**（前两轮的同一个）：`if source.kind.len() >= 0 { return None; }`
   才真的关掉了合并，判据立刻红。

**怎么改**：① 变异脚本**先确认它写进去了**再跑判据——把「变异后的那一行」回读一次并打印，
`assert` 失败时**明确退出**而不是让流程继续（Python 的 `assert` 抛异常后 shell 默认仍继续下一步，
除非 `set -e`）；② 变异必须**改变行为**，写法上优先「把判据的输入改成另一个值」
（去掉 `alias`、把上限从 8 改成 1、把 `!=` 改成 `==`）而不是「加一个永不成立的条件」；
③ 跑完把 `MUTANT` 在目标文件里的出现次数数一遍，恢复后必须是 0——这比「我 `cp` 回来了」可靠，
因为 `/tmp` 备份本身也可能不是你要的那一份。

**为什么记在教训里**：「反向验过了」这四个字，只有在**红确实来自变异**时才算数。同族的
§3（改动真的进了被测产物）、§11（变异真的移除了被引用的东西）、§17（测试锚点对得上）都是
同一件事的不同外衣：**动作看起来做了**。这一轮多出来的一层是——**格式化工具（`cargo fmt`）
会在你写完变异脚本之后重排源码**，所以「按当前文件形状写的变异脚本」在跑第二次时就失效了；
脚本要按**语义锚点**（属性名、函数名）找，而不是按整行文本找。

## 20. 内核客户端束会被**重新求值**：顶层 `const` 第二次就死（2026-10-15）

**现象**：给内置插件写客户端半边（内核按 `dsh.client` 声明把它当客户端模块供给给工作台页面）
时，照着仓里那份先例把字典与样式声明放在**顶层**。首次加载一切正常，徽标也挂上了——直到碰了一下
那个文件，内核的 client-hmr 推了重建帧，页面重新求值这一份，控制台一条
`SyntaxError: Identifier 'SLOT' has already been declared`，**整条 entry 当场静默死掉**，
而面板上「已启用」照常显示，没有任何业务面报错。

**为什么**：客户端束是**普通脚本**（单文件服务在 `/plugins/<id>/client.js` 上，不过打包器），
求值落在页面的**全局词法作用域**里，而那一份束会在文件变化时被重新求值。`var` 与 `function`
可重复声明，`const` / `let` / `class` 不可——所以「先例里能跑」与「重新求值能跑」是两件事。
更糟的是它与**同名冲突**同源：顶层声明是全局的，别处同名也会在加载那一刻炸。

**怎么判**：`node --test` 里把这一份在**同一个 vm context 里连跑两遍**，第二遍抛就红。
首次加载只验一遍的话，这条判据永远绿——而真实世界里的失效点恰恰是第二遍。
写新的客户端束时**一个顶层声明都不写**（字典、样式、常量、助手全放进 factory 闭包，顺带一个全局
都不挂）；要留顶层就只用 `var`，并把这条判据钉上。

**顺带**：这一轮同时发现仓里那份先例（已发布的账户卡）正踩着同一个坑——把它顶层四个绑定从
`const` 改成 `var` 并补了判据。**已发布的代码里可能有同形状的缺陷**，读先例时读的是「当时能跑」，
不是「一直能跑」。

## 21. 用户报「Windows 拒绝访问」，而同一行代码在命令行里跑得通（2026-10-19）

**现象**：用户贴图报「工作台未就绪：内核进程没有被拉起来：建立 peer 链接失败……拒绝访问。(os error 5)」。
查日志确认是内嵌插件 `openai-oauth` 的 `@deepseek-ai` peer 链接建不出来——这条链失败会经
`refresh_enabled` → `AdapterError::Io` **挡住整个内核**，坏的只是一个插件的一条链接。

**为什么会卡住**：内核树是 pnpm 扁平布局（`dsh-llm` 自己没有 `node_modules`，依赖全在树根），
而 Node 按真实路径解析 `import`。所以「链不通就复制一份」这条常见的降级在这里**必然坏**——
复制过去的那份在自己的目录里一条依赖都解析不到。故障面被结构放大成整个工作台。

**排查中被三次误导**（每一次都是「看起来已经找到根因了」）：

1. `symlink_dir` 报 os error 5 → 判定「未开开发者模式」，而错误文案本来就是这么建议用户的。
   但 PowerShell 的 `New-Item -ItemType SymbolicLink` 在**同一秒、同一目录**成功。
2. 于是去问「std 为什么不行」，自己声明了一个裸 `extern "system" CreateSymbolicLinkW`，
   它**返回 TRUE**——看上去完美。直到顺手查了一次落地物：`symlink_metadata()` 查不到。
   **那个「成功」什么也没建**，比报错更坏：这个改法会交付一个静默无链接的版本。
3. 改用 `windows-sys` 那份，返回 `ERROR_PRIVILEGE_NOT_HELD`（1314）——又一个「权限问题」的
   解释，于是差点把「权限不足」当成结论写进代码。

**真相**：三个写法三种结果（5 / TRUE 但没建 / 1314），而**同一时刻 320 次连续全绿**。
这台机器装着 360安全卫士，过滤器驱动在扫描目录时会把「在这个目录里建 reparse point」拒掉，
`ERROR_ACCESS_DENIED` 是它的签名——权限本身没问题（同一目录里 `create_dir_all` 刚成功过）。
07:37 应用启动失败、07:53 之后同一条命令全绿，时序对得上。**用户重新点一次「启动工作台」就好了**
（当场复验：69ms 通过，内核起在 3090）。

**四条纪律**：

- **同一条命令在别的进程里跑通，不等于「我的写法错了」**，也不等于「用户的机器坏了」。
  先把**时序**摊开：失败集中在哪个时间段、恢复之后是否稳定全绿。
- **「返回成功」不等于「做成了」**。凡是要落到磁盘上的操作，判据必须查**产物**，
  不能只看返回值——裸 FFI 那次就是靠多问一句 `symlink_metadata()` 才没把坑埋进去。
- **Windows 上「拒绝访问」先问是不是瞬时**，再问是不是权限。同一个 errno 既是权限的签名，
  也是过滤器驱动抖动的签名；本例里后者才是真的。
- **修 bug 的顺序是：先把用户从故障里捞出来（当场能重试就重试并复验），再改代码。**
  本例用户的问题在诊断结束前就已经好了——修的是那条「一次抖动炸掉整个工作台」的脆弱结构，
  不是用户当时看见的那个错误。

**落点**：`shell::link::make_dir_link`（建目录链接的唯一入口，瞬时错误重试三次，模块文档里记着
上面三个误导写法的实测数据）、`plugins/builtin/materialize.rs` 的错误文案、README 与
`src-tauri/AGENTS.md` 的内置插件通道一节。

**2026-10-19 当日复核推翻了本条的一个前提**（当天晚些时候，同一台机器）：原文把「未开开发者模式」
当成事实写进了 `link.rs` 模块文档、README 与 `src-tauri/AGENTS.md`，据此推出「建链不需要开发者模式」，
还要求错误文案别提开发者模式。复核结果：`whoami /priv` 里确实没有 `SeCreateSymbolicLinkPrivilege`，
但 `HKLM\SOFTWARE\Microsoft\Windows\CurrentVersion\AppModelUnlock\AllowDevelopmentWithoutDevLicense = 1`，
且该注册表键的最后写入时间是 **2026-07-15**——**早于事故三个月，开发者模式一直是开着的**。
所以这台机器能建链恰恰因为开发者模式开着；没有它的机器上，`CreateSymbolicLinkW` 返回的是
`ERROR_PRIVILEGE_NOT_HELD`（1314，确定性失败），与本次的 5（瞬时）不是一回事。
教训与第 1 条同源但更进一步：**「我确认过它不是那个原因」也要有可复核的证据**——原文的确认过程
只是「错误码看起来像权限问题，而文案早就是这么写的」，没有去查开发者模式的实际状态。
现在 5 与 1314 分开处置（5 重试 + 查安全软件；1314 一次上抛 + 提示开开发者模式），
「不需要开发者模式」这条结论已从三处撤回。
