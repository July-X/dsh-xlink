# 事故经过存档

`AGENTS.md` 里每条纪律背后都有一次真实踩坑。纪律本身留在 `AGENTS.md`（它受运行时
的指令字节预算约束——上限由内核的 `agent-instructions.maxBytes` 给出，现为 65536，
超出部分会被截断），事故经过归档在这里，供需要
追溯时查。

写作约定：每条写清 **现象 → 根因 → 结论**，结论一句话。日期用事件发生日。

---

## 1. 给内核打补丁「可逆所以安全」是答错了问题（2026-09-29）

**现象**：有人给 `dsh-client-ui-renderer/lib/client.js` 打过一个补丁——「作用域缺席时
挂起而不是抛错」，随 0.3.5-rc.4 发布。

**经过**：该补丁的论证是「可逆 + 有备份 + 有哈希校验」，很快被认定为违背产品定位并撤销。

**结论**：那套论证回答的是「破坏可不可逆」，不是「该不该做」。两者是不同的问题，
而「该不该」在 `AGENTS.md` 的只读内核边界那一条里已经答完了。可逆性不构成写入理由。

---

## 2. 从仓库删掉补丁，不等于用户机器上消失（2026-09-29）

**现象**：删掉两个补丁目录后重新装 rc.4，用户安装目录 `<install>/patches/` 下
**两个目录仍在**。

**根因**：更新只覆盖与新增，不清理上游删掉的东西。

**结论**：要真正清干净，得让应用自带一份「本次构建带了哪些补丁 id」的名单（构建期
生成），再在 `load_patches` 时按它裁剪资源目录。在此之前，删除补丁后必须在发布说明里
写明它不会自动卸载。

---

## 3. PowerShell 恢复文件后不更新时间戳，验的是旧产物（2026-09-30）

**现象**：给 `kernel::tests` 做反向验证，「备份 → 改坏 → 跑测试（红）→ 恢复」四步走完，
恢复后**仍然红**。

**根因**：PowerShell 的 `Copy-Item` **保留源文件的 `LastWriteTime`**。恢复那一步写回去的
是比「改坏」那一步**更早**的 mtime，cargo 判定无需重编译，于是第二次跑的还是改坏时的
产物。真相是根本没重编，不是断言不成立。

**结论**：恢复后补一句 `(Get-Item <file>).LastWriteTime = Get-Date` 再跑。
同理，**反向验的红必须是「改坏的当次」的红**——中途任何一次重编失败都可能让红变成
「编不过」而不是「断言不成立」，那不算验过。

---

## 4. 版本号只改两处，门禁比文档多查一处（2026-10-03，v0.3.9-rc.1）

**现象**：`package.json` 与 `src-tauri/tauri.conf.json` 都改了版本，`Cargo.toml` 漏了。

**后果不是编译失败**：crate 版本与壳版本不同源，Tauri 打的产物里元数据会带着一个
对不上的壳版本号，updater 与「关于」面板显示的都可能不是这个 release。是
`check:invariants` 的 `[versions]` 项当场抓出来的。

**结论**：**改版本号一律三个文件一起改**，别等门禁报。

---

## 5. `bundle.resources` 少一步生成，CI 全红而本地全绿（2026-10-09，v0.4.4）

**现象**：新 checkout 上第一个 cargo 命令死在
`resource path 'resources/builtin-plugins' doesn't exist`。表现为 quality job 的
`cargo test` 与两个平台的 `tauri build` 报同一行、而 `Publish release` 被跳过——
**red 的表象与真正原因隔着两层**。该 break 在 main 上已连红 4 个提交。

**根因**：`src-tauri/resources/builtin-plugins/` 是构建期产物（`.gitignore` 挡住，
由 `npm run prep:builtin` 从 `plugins/openai-oauth/` 生成），而 build script 校验的是
登记在 `bundle.resources` 里的**每一个**路径。本地 `npm run dev` / `build` / `check`
都各自带着这一步，所以**本地永远看不出来**。

**结论**：`scripts/dev-builtin.test.mjs` 钉住接线形状——任何会跑
`cargo build/check/test/clippy` 的 workflow job 都必须先生成资源，并带「判据空转时
必须红」的兜底。新增一个同类生成目录时，把它的生成步骤挂进判据，不要只改 workflow。

## 6. 常驻行为「抄一份就会漂」的三次实例（2026-10-02 / 10-05 / 10-09）

**a. 恢复动作被抄了一份（10-02）**：`lib::show_main_shell` 与工作台拉绳的
`focus_main_shell` 各自实现了一份唤回逻辑，Windows 上两边互调过一次，直接
`thread 'main' has overflowed its stack`。

**b. 收起动作绕过了统一实现（10-05）**：登录自启分支裸调 `window.hide()`，macOS 上
激活等级没降到 Accessory——进程带着「在运行」小点的 Dock 图标、**零可见窗口**地挂在
后台，点它还没反应。`RunEvent::Reopen` 只抬工作台，而 macOS 的激活不会替我们显示
`hide()` 掉的窗口，抬不到时必须兜底 `show_main_shell`。

**c. 任务栏按钮只删不补（10-09）**：删除走 `ITaskbarList::DeleteTab`，而 `show()` 不会
让它自己回来。补回的那一份曾经住在 `tray::show_main_shell` 而**没有任何调用方**走它，
于是登录自启藏起面板后，用户点启动项唤回的窗口在任务栏上没有按钮。那份实现已删。

**结论**：常驻行为（关闭 / 收起 / 恢复）三件事各只有一份实现，全在 `shell/resident.rs`。
抄一份就会漂，而漂在 Windows 上往往直接是崩栈或「点了没反应」。

## 7. 「只搬进 release」防的是再犯，防不了已经犯的（2026-09-28）

**现象**：release 侧工作台从此是空列表，而 `~/.dsh` 已空——搬不动第二次。

**根因**：dev 壳在闸门落地（`713bb40`）前 15 分钟就把 `~/.dsh` 并进了 `default-dev`。

**结论**：补的是回收路径 `home_recovery`——只读扫描别的实例 home 里本实例缺的
`sessions/` 与 `attachments/`，用户拍板后**复制**过来，源永不删除、目标已有条目永不覆盖。
执行前要求**目标实例**的内核未在运行（判据按实例 pid 文件而非本壳工作台：用户自建实例
留在两份注册表里，另一壳正跑着它同样要拒）。UI 挂在「数据迁移」面板的「找回历史会话」
卡片上（`scan_misplaced_home` / `recover_misplaced_home`）。

## 8. `DSH_CUSTOM_SKILL_DIRS` 注了半年，内核从来不读（2026-09-30 查清）

**现象**：技能「装得上、内核看不见」持续约半年，无人察觉。

**根因**：`dsh-skill-filesystem` 的 `customSkillDirs` 只从 `cordis.patch.yml` 的插件配置
读；0.2.0-rc.2 全树 3481 个 js/d.ts 里无 `CUSTOM_SKILL` 命中。

**结论**：**判断「内核到底认不认某个注入方式」必须实测，不能读接口名推断**。已用
`--dump-config` + `skills/list` RPC 端到端验证。接通靠的是 `ensure_skill_wiring` 往
`cordis.patch.yml` 追加的 loader 行，不是那条 env。
## 9. 扫源码的判据命中了文件头的注释，反向验才发现（2026-10-14）

**现象**：给 `plugins/memory/host/index.js` 加了一条判据「注入块要显式 `interpolate: false`」。
把真代码改成 `interpolate: true` 之后**判据照样绿**（19 条插件用例全过）。

**根因**：判据先用 `replace(/^\s*\/\/.*$/gm, '')` 剥注释，**只剥行注释**；而该文件的
`/** … */` 头注释里正好写着「`interpolate: false`——记忆正文原样带出去」。于是正则命中的
是解释，不是代码。同一段判据里另外几条（`beginStep(` / `applyStep(` / `applyResult(` 不许出现）
有同样的风险。

**结论**：**扫源码的判据必须连块注释一起剥**，且每条判据都要真的反向验一次——不是「改坏了看它
红不红」走个形式，而是**先确认它现在绿得有理由**。修法是
`src.replace(/\/\*[\s\S]*?\*\//g, '').replace(/^\s*\/\/.*$/gm, '')`，改完再反向验一次：
`interpolate: true` 立刻红。这与根 `AGENTS.md` 那条「锚点找在原文上，匹配再过 `productionRust()`」
是同一件事的 JS 版本——那边是 Rust 判据，这边是插件装配层的判据，坑一样。

## 10. 把令牌抹掉一半，比不抹更坏（2026-10-15）

**现象**：诊断日志与模型输入共用的凭据掩码，在 `Authorization: Bearer abc.def.ghi` 上输出
`Authorization=*** abc.def.ghi`——**令牌原样留着**，而这一行看起来已经脱敏了。看到 `***` 的人不会
再看第二眼，所以它比完全没抹更危险。

**根因**：键名规则（键名含 `authorization` → 抹掉值）先命中，而它的值扫描到**第一个空格**就停，
值只是 `Bearer` 这个词；真正是凭据的那一段在它后面。

**是怎么发现的**：为了给 P2 的提取输入做脱敏，在插件里**逐条复刻** Rust 那套形状（设计原本写的是
「复用 `diagnostics::run::sanitize`」，但那份函数还带 480 字符截断与 home 折叠，是给日志行用的，
套到 64 KiB 的模型输入上会把输入毁掉）。复刻时先用原始实现跑夹具，第二组就撞见了。

**结论**：**同一个判据在两侧各有一份时，「逐项对比」的判据比「都写了」重要**——漂的那一侧不会报错，
它只是**少抹掉一个**。这次两边一起修，夹具共用，键名表与方案名由冒烟测试读 Rust 源码对比钉住。
两条附带教训：① 反向验是唯一能证明修复真的在修的办法（摘掉修复，用例立刻红在
`"Authorization=*** abc.def.ghi"`）；② 修的过程中又发现第二处反向错误——空格也被当成分隔符，
散文里的「token 这个词」会被吃成 `token=***`（中文没有词间空格，一吃就是一整句），
**漏抹与误抹要分开评估**：误抹的是用户写下的正文，而正文是唯一的价值。

## 11. 反向验的变异要**真的把东西拿掉**（2026-10-15）

**现象**：给「记忆清单里引用的判据必须真的存在」写了一条新不变量，然后反向验——把
`src-tauri/src/memory/store.rs` 里的判据 `the_same_body_is_not_collected_twice` 改名成
`the_same_body_is_not_collected_twice_renamed`，判据**照样通过**。看起来是新判据假绿。

**根因有两层，第一层是变异的问题**：新名字**把旧名字当子串包含了**，而判据用的是包含关系
（`includes`）。所以「拿掉」这件事根本没发生。改成真正的改名（`duplicates_are_refused_here`）
之后立刻红。**结论：反向验里，先确认「我改的那一下真的让被判的东西消失了」，再谈红不红。**

**第二层是判据自己的问题（在更早一次尝试里现形）**：为了让判据只认代码、不认解释，先写的是
「剥掉所有 `/* … */`」。结果源码里有 `'**/*.js'` 这样的 glob 字符串，它的 `/*` 会与**几千行
之后**的 `*/` 配成一对，一次吞掉一大片——**37 条明明存在的判据全被判成找不到**。改成「只剥
**行首**的注释（前面只允许空白）」之后，`///` 文档注释照样剥得到，而假配对基本不可能发生。
这条与 §9 是同一个形状的第二次：**扫源码的判据，剥注释的方式本身就是判据的一部分**，
剥多了会假红、剥少了会假绿，两个方向都要反向验。

## 12. 插件的配置被断言拒绝时，它是**静默不激活**的（2026-10-15）

**现象**：为了让一次真机会话里发生压缩，给 `compaction-basic` 打了配置补丁。跑了三轮，
会话日志里**一次 `compaction/start` 都没有**，而我的注意力全在桩桥有没有收到请求上，于是
一路往「阈值算错了」「压力信号不对」的方向猜。

**真相在第一次运行的输出里**：`compaction-basic: Error: BasicCompactionConfig.maxTokens
(explicit or from headroomTokens) (0) must be a positive integer`——`headroomTokens: 0` 让
`maxTokens` 默认取到 0，构造期断言直接抛，**整个插件从未激活**。而它在终端上只有一行
`dsh: warning: 1 entry did not activate`，后面跟一行错误摘要，很容易被当成噪声。

**结论**：**每次真机跑完先读 `did not activate` 那几行**。配置被断言拒绝时的症状（插件不在栈里）
与「条件没到」完全一样：都没有事件、都没有报错、都只是「什么也没发生」。这与 §8 那条
「判断内核到底认不认某个注入方式必须实测」是同一件事的两面——那边是「读接口名推断」不行，
这边是「读自己的配置以为它生效了」也不行。**判据是运行输出里的激活行，不是配置文件里的那几行。**

## 13. 做 A/B 之前，先确认**被测量的那个量真的会动**（2026-10-15）

**现象**：给「压缩之后恢复注入预算」做真机验收，看到 6 个回合里有 6 次 `/v1/memory/context`，
就下了结论——因为「没有重置时一个会话最多 5 次」。第二天回头核对计数逻辑，发现**两个前提都不成立**：

1. 桩桥当时回的是 `hits: []`，插件从没「应用」过任何东西 ⇒ `injections` 一直是 0 ⇒ 每回合都走
   refresh 路径。**取不取检索与压缩无关**，那个 6 什么也证明不了；
2. 换成回真命中之后（`/note` 回报证明注入被计数了），仍然看不出差别——因为**每次 `dsh headless`
   都是一个独立进程**，插件的会话状态每回合从零开始，`injections` 同样涨不到 3。

**结论**：**A/B 的前提是「处理组真的改变了被测量的那个量」**。这次测的是「注入预算被重置」，
而被测量的量（`injections`）在两组里**都**是 0——所以两次实验都是假绿，只是第二次的假绿更隐蔽
（有 `/note` 回报看起来很实证）。动手前该问的三个问题：**这个计数在哪累加？它在两组里分别是多少？
我的观测方式能不能把它区分开？** 这与 §11 是同一个形状的第三次：那次是变异没把东西拿掉，
这次是**被测量的量根本没动**——「反向验」这一族的坑，核心都是**先确认变化真的发生了**。

## 14. A/B 的两边要**钉到具体版本**——`HEAD` 会随你自己的提交前移（2026-10-15）

**现象**：给「只对成功的压缩重置」这个修复做 A/B。用 `git show HEAD:plugins/memory/host/index.js`
取「修复前」的版本，跑了三轮，结论都是「修复前修复后一样，看不出差别」，于是开始怀疑是钩子顺序
导致重置被覆盖——一个听起来很合理的假设，还写进了清单。

**根因**：那个修复**已经在上一次提交里了**。`HEAD` 不是「修复前」，它是「我最近一次提交」——
而那次提交就是修复本身。三轮实验的两边其实是**同一份代码**，所以当然没有差别；而「没有差别」
被我解释成了「有某种机制抹掉了效果」，还据此编了个假设出来。

**结论**：**A/B 的每一版都要用不可变的坐标钉住**（具体的 commit hash / tag / 文件哈希），
不要用 `HEAD`、`HEAD~1` 这类**会随会话推进而改变**的引用；实验记录里带着「这一版是什么」的
证据（这次是 `rg -c isCompactionDone` 的输出——一查就知道拿错了版本）。
钉住版本之后结论立刻反转：修复前 6 次注入、修复后 3 次，差别清清楚楚；那个「被覆盖」的假设
是错的（插桩轨迹显示重置按时发生、`injections` 1→0、`textLen` 40→0）。
这与 §13 同族：**先确认你测的是什么，再测**——§13 是「被测量的量没动」，这是「被测的两边是同一个」。

## 15. 兜底路径自己没被跑过：假件全绿，接线一跑就炸（2026-10-15）

**现象**：会话日志的读取加了一条 live 兜底（durable 主路失败时改读 `sessionQuery.readSession`），
6 组假件用例全绿，覆盖了「不落盘时不去开句柄」「兜底裁剪范围并带上主因」「兜底也失败时两条原因都在」。
几天后把两端接起来一起跑（真内核 + 真插件 + 真桥 + 真任务表），第一次就炸：

```
等落盘屏障时失败：session "…" is not live in this store；
live 兜底也失败：cannot get required service "sessions" in inactive context
```

**根因**：服务是在 `ctx.inject([...], (scoped) => …)` 的**子上下文**里读出来存下来的。
那个子上下文只在回调期间活着，事后通过它读服务就抛「inactive context」。假件测的是**逻辑**，
而这段接线是**取服务的方式**——夹具里根本没有内核，所以它永远测不到。

**结论**：**兜底路径和主路的接线是两件要分别验的事**。主路天天被跑，兜底只在主路失败时才走，
于是它的接线错误可以安然无恙地活很久——直到真的需要兜底的那一天，两个错叠在一起，
报出来的原因还是主路那条（更容易被当成主路的毛病）。这与 §13／§14 同族：
§13 是「被测量的量没动」，§14 是「被测的两边是同一个」，这条是「被测的那条分支根本没被走到」。
**做法**：任何兜底都要有一条**真的会走到它**的路径（本地就能造——把主路弄坏即可），
并且在两端接起来的运行里至少走一次。

## 16. 夹具的断言强度决定了它能发现什么（2026-10-15）

**现象**：两侧端到端的手动夹具（真内核 + 真插件 + 真桥 + 真任务表）跑出来是**绿的**，
可它打印的任务表里明明有一条任务带着 `inactive context` 的错。原因是断言只写了
「**有候选落下来**」——第 1 条任务成了、候选落库了，断言就满足了；第 2 条怎么死的它看不见。

**更糟的是**：上一次修这个问题（把服务改成「急取快照」）时，我正是拿这条夹具当验收依据的。
夹具绿了，我就记成「修好了」——而真相是**快照本身就是 bug**（`ctx.get` 返回的是绑定当时那个
fiber 的追踪代理，服务 fiber 事后重载，快照下来的对象就失活了）。**弱断言不但发现不了 bug，
还会给一个没修好的改动盖章。**

**结论**：**写夹具时先问「它能发现什么」**。这条夹具后来改成区分两类 error——**业务拒绝**
（去重闸、开关关了、来源对不上）是正常结果，**基础设施失败**（服务失活、读不到会话、落盘屏障失败）
才是链没走通——于是它立刻在复跑里把上面那个 bug 现出来。同族的坑：§13（被测量的量没动）、
§14（被测的两边是同一个）、§15（被测的分支没被走到），这条是第四个：**被测的东西被测了，
但断言弱到测不出问题**。四条的共同点都是「验证动作看起来做了，其实没起作用」。

## 17. 用脚本往 Rust 测试文件里插用例，锚点要含 `#[test]`（2026-10-15，第 5 次）

**现象**：一个用了五次的脚本模式，五次都咬到自己。锚点选在**函数行**上：

```python
anchor = "    fn some_existing_test() {"
src.replace(anchor, new_test + anchor, 1)   # ✗ 旧测试的 #[test] 在锚点上面
```

`#[test]` 在 `fn` 的**上一行**，于是插进来的新用例把它「继承」走了：新用例头上两个 `#[test]`、
旧用例一个都没有。后果是 clippy 报 `duplicated attribute` + 「function is never used」——
**门禁每次都拦住了**（所以没造成真事故），但每拦一次就是一轮重跑（本仓一轮全量门禁约 3 分钟）。

**怎么改**：锚点选在**属性块**上（`#[test]\n    fn xxx(`），或者插在**上一个用例的收尾 `}` 之后**。
前者更稳，因为它同时钉住了「这个函数是个测试」这件事。

**为什么记在教训里而不是只改一次**：它是**可复用的正确做法**缺失，不是一次手误——
同族的 §3（反向验要先确认改动进了产物）、§11（变异要真的移除被引用的东西）都是
「动作看起来做了、其实作用在别的东西上」。判据能拦住它（`-D warnings` 里有
`duplicate_macro_attributes`），但**拦得住不等于代价为零**。

## 18. 扫源码的闸只认一种引号，整类漏判，而闸**绿着**（2026-10-15）

**现象**：新加的不变量 `builtin-peer-imports` 要抓的形状是「插件**静态** `import` 了一个没在
`BuiltinSpec::peers` 里声明的 `@deepseek-ai/*` 包」——真事故就是这么发生的：`openai-oauth` 的
`host/adapter.js` 静态导入 `@deepseek-ai/dsh-llm`，而 `peers` 里没有它，缺 peer 时插件连
`import` 都过不去、整条静默失效。第一版判据的正则写的是单引号：

```js
/import\s+[^;]*?from\s+'(?<pkg>@deepseek-ai\/[^']+)'/   // ✗ 仓库里那个文件用的是双引号
```

于是**双引号的静态导入整类漏判**。反向验（把 `peers` 里的 `dsh-llm` 删掉）时才发现：闸**照样绿**。
换句话说，这道闸的价值是零，而它绿着的那一刻，正是真事故在场的那一刻。

**怎么改**：引号写成 `['"]`，并按**源码里实际存在的形状**把「相对引用」也枚举全——
`export … from`、纯副作用 `import`、无扩展名（`./x` 要试 `x` / `x.js` / `x.mjs` / `x/index.js`）、
两种引号；文件不存在时 `problems.push` 而不是静默跳过。改完再反向验一次：红，恢复，绿。

**为什么记在教训里**：判据的覆盖面要按**仓库里真实存在的写法**枚举，不是按**你脑子里那一份**。
写判据时脑子里想的是「import 语句长什么样」，而源码里长什么样是另一回事——这类错误不会
自己暴露，它只会让闸**安静地变绿**。同族的 §3 / §11 / §17 都是「动作看起来做了」。
另有一条顺带结论：**反向验不只是验实现，它同时是验判据**——这一轮两次反向验，一次逮到
「判据恒绿」（本条），一次逮到「实现真的坏了」（桥换代没执行 `Drop`）。只跑正向的绿，
两者都看不见。

## 19. 反向验的变异**没进文件**、或者**改的不是行为**，而判据照样绿（2026-10-15）

**现象**：给记忆的 schema 窗口（C4 来源合并）做反向验时，四条判据里两条**第一次验出来是绿的**，
而其中一条是真的红的。三种失效形状在同一轮里各出现一次：

1. **变异写了 `assert`，但没写文件**——想把
   `#[serde(default, alias = "source", deserialize_with = "…")]` 里的 `alias` 去掉，脚本按
   **单行**去找那一串；`cargo fmt` 早就把超过 100 列的属性**折成了五行**，于是
   `t.count(old) == 1` 断言失败、脚本没写盘、**文件原封不动**、判据绿。stderr 里那条
   `AssertionError` 和 stdout 的「exit=0」是分开的两条流，`2>&1 | tail` 之后很容易只看见绿。
2. **变异改的是形状，不是行为**——想禁掉合并，写的是
   `if index == usize::MAX { return None; } // MUTANT`：`index` 永远达不到那个值，于是这行
   是死的，**合并照旧发生**，判据也照样绿。这条最阴：它读起来确实像「这里有一道早退」。
3. **真·无效变异**（前两轮的同一个）：`if source.kind.len() >= 0 { return None; }`
   才真的关掉了合并，判据立刻红。

**怎么改**：① 变异脚本**先确认它写进去了**再跑判据——把「变异后的那一行」回读一次并打印，
`assert` 失败时**明确退出**而不是让流程继续（Python 的 `assert` 抛异常后 shell 默认仍继续下一步，
除非 `set -e`）；② 变异必须**改变行为**，写法上优先「把判据的输入改成另一个值」
（去掉 `alias`、把上限从 8 改成 1、把 `!=` 改成 `==`）而不是「加一个永不成立的条件」；
③ 跑完把 `MUTANT` 在目标文件里的出现次数数一遍，恢复后必须是 0——这比「我 `cp` 回来了」可靠，
因为 `/tmp` 备份本身也可能不是你要的那一份。

**为什么记在教训里**：「反向验过了」这四个字，只有在**红确实来自变异**时才算数。同族的
§3（改动真的进了被测产物）、§11（变异真的移除了被引用的东西）、§17（测试锚点对得上）都是
同一件事的不同外衣：**动作看起来做了**。这一轮多出来的一层是——**格式化工具（`cargo fmt`）
会在你写完变异脚本之后重排源码**，所以「按当前文件形状写的变异脚本」在跑第二次时就失效了；
脚本要按**语义锚点**（属性名、函数名）找，而不是按整行文本找。

## 20. 内核客户端束会被**重新求值**：顶层 `const` 第二次就死（2026-10-15）

**现象**：给内置插件写客户端半边（内核按 `dsh.client` 声明把它当客户端模块供给给工作台页面）
时，照着仓里那份先例把字典与样式声明放在**顶层**。首次加载一切正常，徽标也挂上了——直到碰了一下
那个文件，内核的 client-hmr 推了重建帧，页面重新求值这一份，控制台一条
`SyntaxError: Identifier 'SLOT' has already been declared`，**整条 entry 当场静默死掉**，
而面板上「已启用」照常显示，没有任何业务面报错。

**为什么**：客户端束是**普通脚本**（单文件服务在 `/plugins/<id>/client.js` 上，不过打包器），
求值落在页面的**全局词法作用域**里，而那一份束会在文件变化时被重新求值。`var` 与 `function`
可重复声明，`const` / `let` / `class` 不可——所以「先例里能跑」与「重新求值能跑」是两件事。
更糟的是它与**同名冲突**同源：顶层声明是全局的，别处同名也会在加载那一刻炸。

**怎么判**：`node --test` 里把这一份在**同一个 vm context 里连跑两遍**，第二遍抛就红。
首次加载只验一遍的话，这条判据永远绿——而真实世界里的失效点恰恰是第二遍。
写新的客户端束时**一个顶层声明都不写**（字典、样式、常量、助手全放进 factory 闭包，顺带一个全局
都不挂）；要留顶层就只用 `var`，并把这条判据钉上。

**顺带**：这一轮同时发现仓里那份先例（已发布的账户卡）正踩着同一个坑——把它顶层四个绑定从
`const` 改成 `var` 并补了判据。**已发布的代码里可能有同形状的缺陷**，读先例时读的是「当时能跑」，
不是「一直能跑」。

## 21. 用户报「Windows 拒绝访问」，而同一行代码在命令行里跑得通（2026-10-19）

**现象**：用户贴图报「工作台未就绪：内核进程没有被拉起来：建立 peer 链接失败……拒绝访问。(os error 5)」。
查日志确认是内嵌插件 `openai-oauth` 的 `@deepseek-ai` peer 链接建不出来——这条链失败会经
`refresh_enabled` → `AdapterError::Io` **挡住整个内核**，坏的只是一个插件的一条链接。

**为什么会卡住**：内核树是 pnpm 扁平布局（`dsh-llm` 自己没有 `node_modules`，依赖全在树根），
而 Node 按真实路径解析 `import`。所以「链不通就复制一份」这条常见的降级在这里**必然坏**——
复制过去的那份在自己的目录里一条依赖都解析不到。故障面被结构放大成整个工作台。

**排查中被三次误导**（每一次都是「看起来已经找到根因了」）：

1. `symlink_dir` 报 os error 5 → 判定「未开开发者模式」，而错误文案本来就是这么建议用户的。
   但 PowerShell 的 `New-Item -ItemType SymbolicLink` 在**同一秒、同一目录**成功。
2. 于是去问「std 为什么不行」，自己声明了一个裸 `extern "system" CreateSymbolicLinkW`，
   它**返回 TRUE**——看上去完美。直到顺手查了一次落地物：`symlink_metadata()` 查不到。
   **那个「成功」什么也没建**，比报错更坏：这个改法会交付一个静默无链接的版本。
3. 改用 `windows-sys` 那份，返回 `ERROR_PRIVILEGE_NOT_HELD`（1314）——又一个「权限问题」的
   解释，于是差点把「权限不足」当成结论写进代码。

**真相**：三个写法三种结果（5 / TRUE 但没建 / 1314），而**同一时刻 320 次连续全绿**。
这台机器装着 360安全卫士，过滤器驱动在扫描目录时会把「在这个目录里建 reparse point」拒掉，
`ERROR_ACCESS_DENIED` 是它的签名——权限本身没问题（同一目录里 `create_dir_all` 刚成功过）。
07:37 应用启动失败、07:53 之后同一条命令全绿，时序对得上。**用户重新点一次「启动工作台」就好了**
（当场复验：69ms 通过，内核起在 3090）。

**四条纪律**：

- **同一条命令在别的进程里跑通，不等于「我的写法错了」**，也不等于「用户的机器坏了」。
  先把**时序**摊开：失败集中在哪个时间段、恢复之后是否稳定全绿。
- **「返回成功」不等于「做成了」**。凡是要落到磁盘上的操作，判据必须查**产物**，
  不能只看返回值——裸 FFI 那次就是靠多问一句 `symlink_metadata()` 才没把坑埋进去。
- **Windows 上「拒绝访问」先问是不是瞬时**，再问是不是权限。同一个 errno 既是权限的签名，
  也是过滤器驱动抖动的签名；本例里后者才是真的。
- **修 bug 的顺序是：先把用户从故障里捞出来（当场能重试就重试并复验），再改代码。**
  本例用户的问题在诊断结束前就已经好了——修的是那条「一次抖动炸掉整个工作台」的脆弱结构，
  不是用户当时看见的那个错误。

**落点**：`shell::link::make_dir_link`（建目录链接的唯一入口，瞬时错误重试三次，模块文档里记着
上面三个误导写法的实测数据）、`plugins/builtin/materialize.rs` 的错误文案、README 与
`src-tauri/AGENTS.md` 的内置插件通道一节。

**2026-10-19 当日复核推翻了本条的一个前提**（当天晚些时候，同一台机器）：原文把「未开开发者模式」
当成事实写进了 `link.rs` 模块文档、README 与 `src-tauri/AGENTS.md`，据此推出「建链不需要开发者模式」，
还要求错误文案别提开发者模式。复核结果：`whoami /priv` 里确实没有 `SeCreateSymbolicLinkPrivilege`，
但 `HKLM\SOFTWARE\Microsoft\Windows\CurrentVersion\AppModelUnlock\AllowDevelopmentWithoutDevLicense = 1`，
且该注册表键的最后写入时间是 **2026-07-15**——**早于事故三个月，开发者模式一直是开着的**。
所以这台机器能建链恰恰因为开发者模式开着；没有它的机器上，`CreateSymbolicLinkW` 返回的是
`ERROR_PRIVILEGE_NOT_HELD`（1314，确定性失败），与本次的 5（瞬时）不是一回事。
教训与第 1 条同源但更进一步：**「我确认过它不是那个原因」也要有可复核的证据**——原文的确认过程
只是「错误码看起来像权限问题，而文案早就是这么写的」，没有去查开发者模式的实际状态。
现在 5 与 1314 分开处置（5 重试 + 查安全软件；1314 一次上抛 + 提示开开发者模式），
「不需要开发者模式」这条结论已从三处撤回。

## 22. 用官方文档的通用表格否定一条具体路线的实测之前，先去量那条路线（2026-10-19）

**事情**：评审 `f0910696`（会话身份映射成稳定的 `prompt_cache_key`）时，我读了 OpenAI 官方的
prompt-caching 指南，它的模型差异表写着「GPT-5.6 及以后：路由由 OpenAI 自动处理，这个键
**不是优化缓存所必需的**」；而本机账号的模型目录（`shell/<mode>/openai-oauth/catalog-*.json`）
里只有 `gpt-6.1-sol` / `gpt-6-*` / `gpt-5.6-*`——**一个 5.6 之前的模型都没有**。于是我判定
「这个修复大概率不会让命中率回升」，并把「按模型族改口径」写成了 Must fix。

**那份评审错了，方向反了**。去内核会话日志里量了同一条会话（26 次调用，`gpt-6.1-sol`）：

- `instructions`（1707 token）与 `tools`（7181 token）**逐字不变**——不是前缀被改写；
- 上游给的**保留期 24h**——不是过期；
- 26 次调用回显了 **26 个互不相同的随机 `prompt_cache_key`**，命中 6 次 / 未命中 20 次
  （合计 16.9%）。

前缀没变、没过期，丢的**不是缓存内容，是「落到哪台机器」**：官方文档说的「自动路由」
在**这条路线上**并没有把相同前缀的请求钉在同一台机器上——因为上游给每次请求合成的那个
随机键参与了分片。**那个修复是对的**，而我差点按一份**通用表格**否掉它。

**三条纪律**：

1. **通用文档 ≠ 这条路线的行为**。模型差异表说的是 API 的一般形态；套餐（SIWC）这条路是
   公开 Responses 端点 + ChatGPT 令牌，行为可以不同。**先量这条路线，再谈修法**。
2. **「上游没有这个字段」也要实测**。我建议改用 `prompt_cache_diagnostics` 做诊断，逐条响应
   一查——**这条路线根本没有这个字段**；真正能分字段看缓存量的是
   `usage.attribution.request_fields`（前缀整体命中时 `instructions` / `tools` 的
   `cached_tokens` 等于各自 token 数，未命中时都是 0）。凭印象写的口径会把人带到空字段上。
3. **判据的量纲要挑对**。「命中率」是**结果**，「键是否稳定」「前缀是否变过」「保留期够不够」
   才是**原因**。只盯结果就会在「这个键有没有用」上打转，而真正要问的是「这次请求和上次
   是不是同一段前缀、是不是落到了同一台机器」。

**落点**：`scripts/analyze-prompt-cache.mjs`（`npm run analyze:prompt-cache`，只读会话日志，
一次回答命中率 / 键稳不稳 / 前缀变没变）+ `scripts/analyze-prompt-cache.test.mjs`；
`plugins/openai-oauth/README.md` 与开发计划 §8.1 的复核口径；根 `AGENTS.md` 的通用约定一条。
**内核会话日志是上游行为的唯一事实来源**（上游响应原样存在 `replayState.response` 里），
读它只读——它同时也是「用户到底经历了什么」的唯一现场。


## 23. 判断「上游怎么用这个参数」要去读参考实现的源码：抄契约要抄全（2026-10-19）

**事情**：`f0910696` 把会话身份映射成稳定的 `prompt_cache_key` 发给上游。修完我以为齐了——
用户让「实际分析 Codex 源码再看看修改是否正确」，我去读 `F:/code/2026/codex`，发现
**原生 Codex 两处都发**：请求体的 `prompt_cache_key`（`codex-rs/core/src/client.rs`）与
`session-id` 头（`codex-rs/codex-api/src/requests/headers.rs`，无条件加），而且它自己的注释写着
「ChatGPT derives cache affinity from the Responses session-id header」——**亲和性是从头推的**。

根代理下两处取的是**同一个值**（`responses_session_id` → `prompt_cache_key` → `session_id`），
所以那不是两种身份，是同一身份的两个投递位置。`f0910696` 只抄了请求体那一份。

**三条纪律**：

1. **参考实现的源码 > 官方文档**。文档说的是 API 的一般形态；同一个产品的客户端源码里写着
   「我们实际发什么」。本次两者不一致——文档没提 `session-id` 头，源码里它无条件发着，还带着
   为什么发它的注释。
2. **抄契约要抄全**。只抄请求体字段、不抄头，得到的是「看起来对、实际可能不生效」的修法——
   而它**看上去**是对的，最难发现的恰恰是这一类。缺口要在读参考实现时当场列出来，不是事后。
3. **写进文档的「原生客户端基线」也要能复现**。先前写的「同账号原生 Codex 96–97%」从本机
   落盘日志里**复现不出来**：实测 8 次调用全部命中、单次 67%–89%、合计 79.0%。数字进文档时
   应当带着量它的命令，否则下一个复核的人只能照抄。

**落点**：`src-tauri/src/openai/transport.rs`（发 `session-id` 头）、`src-tauri/src/openai/inference.rs`
（从载荷取键 → 两处同源）、`src-tauri/src/openai/bridge.rs`（两条用例）；`scripts/analyze-prompt-cache.mjs`
加读原生 Codex 落盘日志（`token_usage_record`），基线与现状同一把尺子。



## 24. 「读路径」和「写路径」一样要持 env 锁，而泄漏的 env 会掩盖别的缺陷（2026-10-20）

**事情**：Windows CI 上 Dependabot 的 cargo 补丁版分支连红两次（run 39346453918 / 39363486523），
红在「Windows compile + tests」里的两条 Rust 用例：

- `shell::paths::integration_paths_tests::release_and_dev_shells_do_not_overlap`——
  断言 `release_settings.starts_with(&home)` 失败；
- `usage::local::tests::truncate_resets_account_and_append_continues_from_offset`——
  「文件消失后账目必须移除」失败。

看着像"升级了依赖把用例搞坏了"，其实不是：那条分支与 main 的**代码逐字节相同**，只差
`Cargo.lock` 里 13 个依赖的补丁版，而 main 上同一个 Windows job 是绿的。红的是**时序**。

**根因一：env 竞态，而且两边都有份。**

`xlink_home()` 每次调用都现读 `DSH_XLINK_HOME`。而那条 paths 用例**不持守卫**地读了两次
（一次拿路径、一次拿 `home`）——两次若跨过别的测试的守卫边界，读到的就是**两个不同的根**，
`starts_with` 于是假红。写的那一端同样有问题：`diagnostics/run.rs` 里有两处**裸改**
`set_var` / `remove_var`——一处把 `DSH_XLINK_HOME` 指到一个**文件**再删掉，一处把 `HOME`
指到临时目录**而且从不还原**。仓库自己的纪律写着「裸 `std::env::set_var` 拦不住别的测试
正持着同一把 env 锁」，这次它自己撞上了。

**根因二：时钟 tick。** `usage::local` 那条用例删掉文件后立刻重扫，而「这一轮该读哪个文件」
是靠 `variant_cache::resolve_variant` 的**目录 mtime 闸**判缓存失效的。删文件与上一轮扫描
若落在同一个 tick（Windows 默认粒度 15.6ms），两轮读到一模一样的目录 mtime，缓存继续命中
并返回**那个已经删掉的文件**的路径——这一轮照样把它算作"还在"，账目就不会被移除。
同一文件里 `a_new_generation_in_the_same_session_dir_is_still_picked_up` 早在 2026-10-16 就为
同一形状修过一次（Windows CI run 38923395574），**这条漏了**。

**三条纪律**：

1. **"读路径"和"写路径"一样要持守卫。** 原先那条纪律只说"测试不许碰用户的真实数据目录"，
   读的人以为不写就没事——可 `xlink_home()` 每次都现读 env，**读**同样会被别人改掉。判据
   能钉住"不许裸 `set_var`"，钉不住"必须持锁读"，后者靠纪律。
2. **泄漏的 env 会掩盖别的缺陷。** 那条从不还原的 `HOME` 让
   `display_xlink_home_falls_back_to_full_path_outside_home` **一直是对的**——因为泄漏的
   `HOME` 是个临时目录，而用例的样本取自 `%TEMP%`。把泄漏修掉，真实 `HOME` 是
   `C:\Users\<我>`，而 `%TEMP%` 正好在它**底下**：样本压根不在 home 之外，用例立刻红给你看。
   **清掉一个假绿，往往会露出一个真红**——所以修泄漏时要把"原先被它遮住的用例"一起重看。
3. **断言的前提要自己验，别让时钟替你验。** 目录 mtime 变了才失效缓存，这条前提要**跨过一个
   tick** 才成立；范式就在同文件里：睡 40ms，做变更，**先断言前提成立**再判行为。

**落点**：`src-tauri/src/shell/paths.rs`（paths 用例持 `scoped_xlink_home`）、
`src-tauri/src/diagnostics/run.rs`（两处裸改 env 改成只走守卫；`HOME` 那处直接删掉——
守卫的 `DSH_XLINK_HOME` 已经进了 `home_roots()`，折叠效果一样）、
`src-tauri/src/usage/local.rs`（删文件前跨 tick 并断言前提）、
`src-tauri/src/kernel/lifecycle.rs`（样本换成字面量路径，与兄弟用例一致）、
`scripts/check-invariants.mjs` 第 23 项（除 `lib.rs` 的守卫外，裸改 home 类 env 一律禁止）。

## 25. 依赖大版本升级的断点常在**格式化 trait 与 io trait**上，不在主 API 上（2026-10-20）

**事情**：Dependabot PR #9 把 sha2 0.10.9 → 0.11.1，CI 两个 job 全红（run 39366295003）。

**断点不在 sha2 的主 API**（`Sha256::new` / `update` / `digest` 两版一模一样），而在两处**trait
消失了**：

1. `format!("{:x}", hasher.finalize())`——0.11 的 `finalize()` 返回 `hybrid_array::Array`，
   它**不再实现 `LowerHex`**（0.10 返回的 `GenericArray` 实现）。于是「摘要转十六进制」这
   一步编不过，仓库里 6 处全炸。
2. `io::copy(&mut file, &mut hasher)`——0.11 **不再给摘要器实现 `io::Write`**（0.10 有）。
   这条更阴：它不在摘要那一行，而在「把文件读进 hasher」那行，报错时看着像 IO 问题。

**三条纪律**：

1. **摘要的十六进制自己写，并收编到一处。** 仓库里另有 8 处用
   `digest.iter().map(|b| format!("{b:02x}")).collect()` 写的一样的逻辑——它们**两版都能编**，
   属于"恰好没坏"，但下一次未必。统一到 `src-tauri/src/shell/digest.rs::hex`：**同一语义只留
   一份**，下次再升 sha2 只改这一处。
2. **调用点传 `&digest[..]` 切片**，不要直接传 `finalize()` 的返回值。两版返回类型不同
   （`GenericArray` vs `hybrid_array::Array`），各自的 `AsRef` / `Index` 实现细节并不相同，
   **切片 `&x[..]` 才是两版都成立的交点**。顺带：`hex` 的参数是 `impl AsRef<[u8]>`，传数组
   与传切片都合法，但传 `&[u8; 4]` 会触发 clippy 的 `needless_borrow`（`[u8; 4]` 自己就实现
   了 `AsRef<[u8]>`）。
3. **摘要的十六进制是落盘数据，不是显示数据。** 技能的 `materialized_sha256`、插件 id 的短
   哈希、凭据指纹、Node 产物校验都用它——改一位就与存量数据对不上，所有权判定**静默失效**，
   用户的技能会被当成"不是我们的"而重新物化。所以 `digest::hex` 的测试钉的是**标准向量逐字节
   相同**（`e3b0c442…7852b855` / `ba7816bf…f20015ad`），不是"能算出来"。

**边界：只动 sha2 摘要那一类。** `pkg/releases.rs` 的 sha1 摘要（0.11 升级与 sha1 无关）、
`memory/store.rs` 的随机 id、`openai/*` 的 key 字节——都不是 sha2 摘要，顺手收编只会把改动面
扩大、把不同语义混成一处。

**main 不抬依赖版本**：大版本升级留在 Dependabot PR 里由维护者决定合并，main 只获得
**向前兼容**的代码。验证要**两版都跑**：`Cargo.toml` 临时抬到 `sha2 = "0.11"` 让 cargo 自己解析
（lock 里会出现 0.11.1 与 wry 需要的 0.10.9 **并存**——`cargo update -p sha2 --precise` 会失败，
它要全局升级，而 wry 钉着 `^0.10`），test + clippy 全绿后 `git checkout` 恢复。

## 26. 「某分支不发生」要由**代码结构**保证；测试的 profile 也会改变被测语义（2026-10-20）

**一、计时赋值写在条件之外，契约就是靠运气成立的。**

`shell::atomic_write` 里 `timings.dir_sync_us = started.elapsed()` 原本写在 `if sync {}` **外面**。
于是「免 fsync 入口 `dir_sync_us` 恒为 0」这条**文件头就写着的文档承诺**，实际测的是一段
**空代码块**的耗时：正常 0µs，线程被抢占一下就是几微秒（2026-10-20 macOS runner 实测 **7µs**），
用例于是随机红在一条与 fsync 毫无关系的断言上（run 39366411194，PR #30 的 Quality gates）。

修法不是把断言改宽松，而是**把赋值移进 `if sync` 块内**——契约从此是**结构保证**。

> 通用形态：**「某分支不发生」必须由代码结构保证，不能由"那段代码恰好很快 / 恰好为零"保证。**
> 计时、计数器、哨兵值都属这一类。

**二、profile 不只是"快慢"，它会改变被测代码走哪条分支。**

本机一度记着"跑 Rust 用例要加 `--release`"（因为 debug profile 偶发加载即失败
`0xc0000139`）。改用 release 后，7 条用例**必然假红**：`ShellMode::current()` 判定为 release
（`cfg!(debug_assertions)`），那些断言"dev 壳的默认实例是 `default-dev`"的用例拿到的却是
`default`——红的不是代码，是**验证姿势**。

> 断言"dev 壳"的用例必须在 **dev profile** 下跑。门禁 `check:rust:ci` 用的是 debug 的
> `cargo test --locked`，本地验证必须跟它一致；`--release` 只该出现在
> `cargo check --release --all-targets`（查 release-only 的编译错误）那一步。

## 27. 嵌入式 webview 里「页面自己开窗口」的流程会静默死掉：wry 默认吞掉 `window.open`（2026-10-20）

**症状**：官网网页版（官方对话窗口）里 ChatGPT 的「下载设计规范文档」点了没反应，右侧文件预览
面板报「无法加载此文件 · 重试」。页面本身完全正常，壳侧一行日志都没有。

**根因**：那三扇内容 webview 是 `WebviewBuilder` 直接建的，**没有装 `on_new_window`**。wry 在
WebView2 上只在装了处理器时接管 `NewWindowRequested`，否则走默认实现 —— `SetHandled(true)` 把请求
吞掉：没有窗口、没有下载、`window.open()` 返回 `null`。而站点自己的前端 bundle 写得很清楚：文件
下载走 `window.open(download_url, '_blank')`（下载地址由后端 `download_url` 决定，`<a download>`
是另一条分支），查看器也有靠新窗口的流程。所以**这不是「WebView2 缺能力」，是壳没接上那条已经存在
的桥**：浏览器里 `window.open` 是新标签页，嵌入式壳里没人接就什么都不会发生。

**修法**：内容页签的 `on_new_window` 复用工作台弹窗的同一套路由
（`harness_window::new_window_response`：`about:blank` / 本机页面建壳托管弹窗，外部 `http(s)` 交系统
浏览器，其余拒绝），每条请求落一行 `official-chat` 日志；同一处 `on_download` 把落点显式钉到系统
「下载」目录（解析不到时壳数据目录下的 `downloads`）并记录起止 —— WebView2 的默认下载路径能用，但
「有没有发生过、落到哪里」在壳侧不可见。**下载这条已被 bundle 与代码两头证实；右侧预览面板的报错
与它同属「需要新窗口 / 文件流程」这一族，是否同一根因要等真机复验**，不要把它写进结论。

**可复用的判据**：
- **页面某条流程失败、又看不到控制台时，先问「它有没有走 `window.open`」**。嵌入式 webview 与
  浏览器差的能力往往不是渲染引擎，而是这些必须由 host 自己接的钩子（新窗口、下载、文件选择）。
  缺 `on_new_window` 的症状恰好是「静默」：不抛错、不写日志、页面只表现为点了没反应。
- **wry 的默认值是「允许下载、拒绝新窗口」**（`download_started_handler` 默认返回 `true`；
  `NewWindowRequested` 无 handler 时 `SetHandled(true)`）。判断某条链有没有接，去读依赖源码，
  别凭「Tauri 应该处理了」推断。
- **用页面自己的 bundle 证伪「是不是站点的问题」**：WebView2 的 `Cache_Data` 里 `f_*` 是
  brotli / gzip 压缩的响应体，解压后按站点字符串分类，能直接读到
  `window.open(r.download_url, '_blank')` 这种原话 —— 比猜测快，也比端到端复现便宜。
  官方对话窗口的档案在 `<data_dir>/webview-official-chat/EBWebView/Default/Cache/Cache_Data`。
> **profile 变了，先怀疑自己是不是在测另一件事**，别去改断言。

## 28. 平台差异只能落在**函数体**里：挂在类型别名或纯逻辑上，两平台一起红（2026-10-21）

**症状**：macOS 门禁连红两处，且**都只在一侧红**：① `cargo test --lib` 报
`E0599: no associated function or constant named from_body`（8 处）；
② `cargo clippy --all-targets` 报 `E0432` / `E0433` 共 12 个 error
（`webview2_com` / `windows_core` 解析不到）＋ 2 个 warning（未使用的 import、
`collapsible_match`）。**Windows 那边全绿** ⇒ 看着像「macOS 环境问题」，其实是代码
形状问题。

**根因**：三处同一类错误 —— **把「平台差异」挂在了不该挂的地方**：

1. **签名用到的类型别名**（`EventStream`）被挂了 `#[cfg(windows)]`，而
   `arm_capture_window` / `capture_in` 各有**两个平台分支、签名必须一致**
   ⇒ 非 Windows 分支的签名里也写着那个别名 ⇒ **引用不到** ⇒ `E0425`。
2. **跨平台共享的纯逻辑**（协议 §2.4 的裁剪 ＋ §4.2/§6.2/§6.3 的四档判断）被挂了
   `#[cfg(windows)]`，而**本模块的用例是跨平台的**（它们断言的是**协议口径**，
   不是平台能力）⇒ 非 Windows 上用例引用不到它 ⇒ `E0599`。
3. **平台专用的 example** 没带平台门 ⇒ macOS 上整个 example 编译不过（它要的
   `webview2_com` 在别的平台上根本不存在）。

**结论**：**平台差异只能落在函数体里** —— 两分支保持同一签名（差异写在**体**里）、
**纯逻辑跨平台存在**（差别只是「那边没有生产调用方」）、**平台专用的 example 自带
平台门**。

**可复用的判据**：

- **给一段代码加 `#[cfg(windows)]` 之前，先问两句**：「它的**用例**跨平台吗？」
  「它的**类型**被别的平台分支的签名引用吗？」两个「是」任意一个成立 ⇒ 这段不该被裁。
- **非 Windows 构建里「死代码」是常态**（那边的取数链整块不存在）⇒ 用**模块级**
  `#![cfg_attr(not(windows), allow(dead_code))]` 豁免（**只豁免非 Windows 那边**；
  **Windows 那边的构建才是这条链的严格检查面**），别一条一条加 `allow`。
- **平台专用的 example 必须自带平台门**：真 `main` 挂 `#[cfg(windows)]`，另给非
  Windows 一个「打印『只支持 Windows』＋ `exit(2)`」的 `main` 占位 ⇒ 门禁在 macOS
  上也编得过，而真机跑法一个字不变。
- **「只在 macOS 红」的第一嫌疑不是环境，是「Windows 侧独有的依赖/形状没被门」**
  —— 本轮三处全是这一类；**Windows 全绿时，绿得毫无信息量**。

## 30. 「读不动 ⇒ 拒绝服务」的 fail-closed，会被**非原子写**变成并发下的硬失败（2026-10-22）

**症状**：official-chat 插件的「序号水位」文件让**两个壳同时开着**时随机出事：某一条
会话**直接停发**（报 `snapshot_invalid`「序号水位记录不可读（拒绝分配：宁可停发也
不复用序号）」）。表现为 `plugins/official-chat/test/seq-store.test.mjs` 的「跨进程
（真进程）并发分配」用例**随机红**。

**实测**：本机连跑 6 轮 ⇒ **红 2 轮（复现率约 1/3）**；而 **desktop-ci 全绿** ⇒
「CI 绿」不能证明这条没问题（CI 机器上那个窗口可能刚好没撞上）。

**根因**：两件事叠加，缺一不可：

1. **写不是原子的** —— `writeFileSync(path, …, { flag: 'w' })` 是**原地截断后写**；
   并发读者会读到**半个文件**（空的或半截 JSON）。
2. **fail-closed 的读把「瞬时半个文件」和「真坏文件」混为一谈** —— 解析失败 ⇒
   「水位不明」⇒ **拒绝分配**（这条纪律本身是对的：宁可停发也不复用序号）。

⇒ 崩在写一半时还会留下**永久**坏掉的水位文件 ⇒ 那条会话再也发不出去。

**修法**：先写**同目录**的临时文件、再 `rename` 覆盖目标 —— 同一文件系统内
`rename` 是**原子**的 ⇒ ⇒ 读者要么看到旧记录、要么看到新记录，**永远看不到半个
文件** ⇒ ⇒ fail-closed 只对**真的坏文件**生效。临时文件名**不以 `.json` 结尾**
⇒ 既不会被认领扫描当成一个序号，也不会被清理流程（只动 `.json` 家族）删掉。

**可复用的判据**：

- **凡是「读不动 ⇒ 拒绝服务」的代码，它的写入必须原子**：否则并发写会把瞬时状态
  变成硬失败。**fail-closed 要分清「瞬时」与「真坏」** —— 能用原子写消掉的瞬时，
  不该让读方承担。
- **flaky 用例先量复现率再定性**：6 轮里红 2 轮 ⇒ **代码红**，不是「读数红 / 环境
  问题」；**上游 CI 绿 ≠ 这条没问题**（别用 CI 绿给 flaky 开脱）。
- **按「写盘路径」判的判据，在实现换写法时会误红** ⇒ 判据要认**语义事件**
  （「水位在盘上」＝ 写到位 **或** `rename` 到位），别认某一种实现细节；而
  **实现细节（原子性）要另有一条判据单独钉**（本轮是「并发写时读者不许读到半个
  文件」）。
- **反向验要报量化读数**：把修复改回原地写后，新用例报「读到 **303/10176** 次半个
  水位文件」⇒ 证明它量的是**撕裂读**，不是空转；恢复后逐字节核对（sha256 相同）。

## 31. 「响应体超过上限」是**上限太小**，不是网络故障；而压缩传输必须把上限加在**解压之后**（2026-10-24）

用户报「插件目录加载失败：`the response body is larger than request limit: 10485760`」，
面板同时提示「请检查网络或代理设置后重试」。**那句提示把用户指向了错误的方向**。

**取证**（不是推断）：

- 远端目录 `/api/plugins-data` 实测 **12712365 字节 / 21421 条**；回退源
  `registry/all.json` 实测 **10521095 字节**。**两条源同时越过 10 MiB 那条通用上限**
  ⇒ 回退救不了场 ⇒ 插件中心整体空白。
- 服务端**支持 gzip**：同一个端点在 `Accept-Encoding: gzip` 下只回 **2583034 字节**
  （明文的 1/5）。
- 真机复验：旧路径在真实目录上确实失败（`Err("...larger than request limit: 10485760")`），
  新路径成功取回 12712365 字节 / 21421 条。

**被实测否掉的方向**（用户提出的「改抓 `/zh/plugins` 页面」）：那个页面是 Astro SSR 站，
**它自己的 island JS 也是去拉同一个 `/api/plugins-data` 全量**（页面文案写着
「正在加载全部 21421 个插件…」「显示 100 / 21421 个插件」）；HTML 里只有 100 条卡片，
且**不含壳需要的结构化字段**（stars / category / downloads）。抓 HTML = 用脆弱的
HTML 解析换 100 条，**不减量也不可行**。⇒ **减量的手段是压缩传输，不是换端点**。

**三条可复用的结论**：

1. **失败原因要分类，不同类的下一步不同**。「体积超限」与「网络不通」合成一句
   「请检查网络」时，用户会照着网络方向白查半天（网络其实是好的）。判据是后端
   自己留的标记，**前端不复制那份判定**——同一句标记写两处，两边就会漂。
2. **开了 gzip 之后，上限必须加在**解压后**的量上**。ureq 的 `LimitReader` 位于解压器
   **内层**（`BodyReader = ContentDecoder<LimitReader<…>>`），所以 ureq 自带的 gzip
   特性会让上限**只约束压缩后的字节**——9.9 MiB 的 gzip 炸弹能解出数十 GB 并触发
   OOM abort（2026-09-10 的 P1-6 正是为此关掉那个特性）。所以壳**自己带
   `Accept-Encoding: gzip` 头并用 flate2 解压**，上限加在解压输出上：炸弹解不开，
   压缩收益保留。**顺带实测**：ureq 在 gzip 特性关闭时**不会**自动带这个头
   （探针打印的请求头只有 accept / host / user-agent），必须壳自己带。
3. **上限要自己判，别让依赖抛英文原文**。ureq 的 `limit()` 超限时抛的是
   「response body is larger than request limit: N」——那句话会随依赖版本变，而
   调用方（前端分类）靠**壳自己的标记**区分「体积超限」与「网络不通」。**去匹配
   依赖的英文原文 = 把正确性绑在别人的版本号上**：依赖一升级，提示就悄悄退化成
   「请检查网络或代理设置」，而网络是好的。改成自己 `take(max_bytes + 1)` 读：
   多读到的那**一个字节**就是「超了」的证据，两条路径（明文 / gzip）给出**同一条**
   带标记的原因。**顺带实测**：沿用 ureq 的 `limit` 时，**明文**响应会被通用那条
   10 MiB 挡下——服务端哪天不压缩了，目录就**再次**整体空白，而那天的原因还是
   体积。于是同一条上限必须**同时管线上字节与解压后字节**。
4. **反向验要能造出它要杀的那个行为**。这一条本轮踩了两次：
   - 夹具里「压缩体与明文内容相同」⇒ 去掉 `Accept-Encoding` 头（服务端改回明文）
     时断言照样成立 ⇒ 判据**造不出它要杀的行为**。改成两边内容**不同**才红。
   - 夹具用重复字符做 gzip ⇒ 10 MiB 明文压后只剩 10 KB ⇒ 走的是「解压后超限」
     那条路径，与断言想测的「压缩体超限」**对不上**。改用伪随机字节才真的压不动。
   ⇒ **判据首跑即绿先当嫌疑**；反向验时若某条变异**没让判据变红**，第一反应
   应该是「判据没造出那个行为」，而不是「这条变异无所谓」。
   - **补一条（同一轮）**：线上上限改用 `max_bytes` 之后，原先那条「压缩体超限」
     的用例**没有跟着改**就失去了判据力（它的上限仍是旧的 10 MiB 语义）。改判据
     时要**逐条问「它现在测的还是我以为的那条路径吗」**，不是只问「它绿了吗」。

## 32. 副窗的真机复验：可以直接**挂到已经在跑的 debug 壳**上驱动，不必等 e2e（2026-10-24）

给「模型用量」副窗加来源标记时，需要**看一眼那扇窗真的长什么样**。本仓的
e2e（`e2e/wdio.conf.mjs`）只驱动**主壳**，「模型用量」是 `usage-viewer` 副窗，
够不到；而副窗是**独立 webview**（每个副窗各是独立的 JS 上下文），
`document.querySelector` 在主壳里根本找不到它。

**实测出来的路**：debug 壳把 `tauri-plugin-wdio-webdriver` 编进去后，会在
**127.0.0.1:4445** 起一个 W3C WebDriver HTTP 服务（`scripts/check-webdriver-gating.mjs`
记着这条，release 产物里绝不能有它）。**那个服务可以单独挂**——不必走 wdio 的
local runner 去拉起进程：

```sh
SID=$(curl -s -X POST http://127.0.0.1:4445/session \
  -H 'Content-Type: application/json' \
  -d '{"capabilities":{"alwaysMatch":{}}}' | python3 -c 'import json,sys;print(json.load(sys.stdin)["value"]["sessionId"])')
# 副窗不在 handles 里时，先在主窗里 invoke('open_usage_window') 开一扇
curl -s -X POST "http://127.0.0.1:4445/session/$SID/window" \
  -H 'Content-Type: application/json' -d '{"handle":"usage-viewer"}'   # 注意是 handle 不是 name
curl -s -X POST "http://127.0.0.1:4445/session/$SID/execute/sync" \
  -H 'Content-Type: application/json' \
  -d '{"script":"return document.body.innerText","args":[]}'
curl -s "http://127.0.0.1:4445/session/$SID/screenshot"   # base64 PNG
```

**三条踩出来的坑**：

1. **切窗的请求体字段是 `handle` 不是 `name`**（W3C 标准是 `name`，这个插件要
   `handle`）——传错不报错，只是静默不切，于是后面的 `execute` 全部打在**主窗**
   上，读出来的是概览页的 DOM。「读出来的东西不对」时先确认切没切。
2. **副窗不在 `/window/handles` 里**，要先在主窗里 `invoke('open_usage_window')`
   开一扇，handle 才出现。
3. **Rust 侧一改，tauri dev 会重编并重启壳，session 随之失效**（报
   `invalid session id`）。改完 Rust 就要重开 session，别拿旧 session 继续查。
4. **副窗的滚动容器不是 `document`**，是 `main.usagewin-main`（`overflow: auto`），
   `document.documentElement.scrollTop` 恒为 0——要滚它才看得见下半屏。

**为什么值得记**：这一屏**同时摆两套账**（内核的用量与外部工具的用量），而
「模型用量」是 760×800 的小窗、内容比视口高，**外部那一块在首屏之外**。只看
用户随手截的那张首屏图，会得出「外部那一块没渲染」的结论——而它其实好好地
在那儿。**判据能钉住结构，钉不住「用户在视口里看得见什么」**；这正是
`usageExternal.test.js` 那条跨语言字段契约判据**替代不了**的部分。

**边界**：这条只用于**只读观察**（读 DOM、截图）。要驱动壳做**写路径**的实跑，
根 `AGENTS.md` 那条仍然成立——**隔离 home + 编译期 `appDirectoriesOverride`**，
别去抢用户正在跑的壳的 WebView2 user-data 目录。

## 33. 读别家的数据：形态、单位、失败，三处都得对着真实盘上的数据量（2026-10-24）

给「模型用量」窗口加外部来源（Codex / MiniMax Desktop 留在本机的会话用量）时，
一次评审挖出四个坑。**四个里有三个的根因相同**：代码里写着一句**静态假设**，
而没人拿真实数据量过它。

### ① 收集器只收一种文件形态 ⇒ 最近一周的账整段丢失

Codex 的会话有**两种形态**：`.jsonl` 与 `.jsonl.zst`——它把**7 天没动过**的会话
压成同名 `.zst`（单帧 zstd、保留 mtime）并删掉原文件，所以**最近的会话是普通
形态**。本仓最初只收 `.zst`。

**实测**（本机 `~/.codex`，208 个会话）：201 个 `.zst`、7 个普通 `.jsonl`；那 7 个
装着 **42,401,192 tokens**，且**全部落在 10-13 ~ 10-18**（距今不到两周）——
「今日」「近 7 天」这两个最常看的范围恒为 0。总量占比只有 0.79%，**按比例看
根本看不出问题**——问题在于缺的那一段正好是用户最常看的那一段。

**判据**：普通形态的会话也要计入账。

**顺带**：同一逻辑会话的两种形态**可能同时存在**（Codex 继续压缩过的会话时先
解压回 `.jsonl` 再追加）。两份都读 = 数两遍；留压缩那份 = 漏掉追加的行。留
**普通那份**（与 cc-switch 的 `dedupe_siblings` 同一条规则）。

### ② 时间下界的单位错一位 ⇒ 过滤恒真 ⇒ 每次扫描整表读

MiniMax 的用量库（当前库 2.0 GB / 5.6 万行，老库 367 MB / 25,016 行）里 `ts` 存
的是**毫秒**；下界算成了**秒**。于是 `WHERE ts >= ?1` 拿毫秒比秒，**恒真**——
SQL 那一层等于没过滤，每次扫描把两整份读出来，再靠 Rust 侧按本地日历日剪掉。

**这一条差点被写错**：评审第一版结论是「窗口首日的 8 小时被滤掉了」——**推错了**。
写单测时断言红了才看出来：旧代码因为单位错 1000 倍，过滤压根没发生，首日**没丢**。
真实现象是**性能**问题（整表扫），不是丢数。**「下界小于所有数据」和「下界大于
部分数据」的效果完全相反，而两者都能让一行 SQL 看起来「对」**——只有单测与实测
能分辨。

**判据**：下界的单位与被比列同单位（断言 `bound > 1e12`），且不晚于窗口首日的
**本地**午夜（正 UTC 偏移下取 UTC 午夜会晚 8 小时）。

### ③ 读失败写成空账 ⇒ 那个文件的用量永久归零

扫描失败时把结果写成**空账**并缓存下来——而缓存的判据是「大小与 mtime 没变
就跳过」，于是下一轮直接复用那份空账，**这个文件此后再也不会被读一遍**。
`archived_sessions/` 里的文件 Codex 不再重写 ⇒ **永久归零**。

**修法**：读不出来就标成「**没读全**」（`stale`）——**保留上一次读到的账**
（别让数字凭空少一块），但**下一轮一定重扫**。

**判据**：坏文件扫完后条目必须带 `stale`；文件修好后下一轮账要回来。

### ④ 同一张卡里摆两个时间窗口

外部来源那张卡的**大数字与模型列表**用的是后端给的 90 天合计，**柱状图**却是按
范围切的——切到「今日」时内核那几块变了，外部卡片纹丝不动。

**修法**：外部卡片与内核那几块共用 `sliceDays` + `summarizeDays` 这条路，90 天
合计只留在 tooltip 里说清。

**判据**：模板里的大数字必须来自范围口径的聚合，且不得出现内核那份的
`rangeSummary`。

### 顺带两条同源的

- **`response_id` 的去重集合是按文件一份的**，而注释写着「同一请求可能被写进
  多个文件」——**注释声称的没兑现**。改成**跨文件共用**一份（`Arc<Mutex<..>>`）。
- **schema 变更要真的作废旧文档**：注释写着「结构变了就 +1，旧文档按整体重扫
  处理」，但代码里**没有这个判断**——`#[serde(default)]` 会把缺的字段默默补成 0，
  于是拿一份半旧半新的账继续用，比全量重扫更坏。

### 口径本身**没有**被这些坑带偏（实测 65,539 行计数行）

本轮顺手复核了 Codex 那条「两个形状只取一个」的口径：`token_count` 与
`token_usage_record` 在本机数据上 **4,069 对逐对相等、0 对不等**，重发率
**25,045 / 65,317 = 38.3%**（与模块文档里写的 38.4% 吻合）。cc-switch 那条
「`token_count` 的 `last` 为 0 时用 `token_usage_record` 补记」的规则在这批数据
上**不会改变总量**（那 4 条 `last` 为 0 的行没有配对的 record）——所以口径**不动**，
只修收集范围与健壮性。**换实现之前先量口径**：不然会把「口径本来就对」和
「口径错了」混成一笔账，改完也说不清改的是哪一头。

## 34. 新加的那一段在滚动容器之外：DOM 里有 ≠ 屏幕上看得见（2026-10-24）

外部来源那两张卡片，功能全对、单测全绿、语义树里也确实渲染出来了（`inspect` 看得见
region「外部 Agent 工具用量」+ 两个 `article`）——**但在真机窗口里它们只剩一条边**，
段落的标题露在页脚上方就被切掉了。用户永远看不到这个功能。

**根因**：`.usagewin-main` 是 `overflow-y: hidden`，而外部段是 `<main>` 的**最后一个**
子元素。全局 `theme.css` 里本来就有 `main { overflow-y: auto }`（主壳各面板的约定：
内容装不下就滚），副窗这条 `hidden` 把全局约定盖掉了。760×800 的窗口装不下
「概览 + 趋势 + 模型明细 + 外部卡片」四段，超出的那一段被**整段裁掉**。

**为什么这类缺陷能一路绿灯**：判据覆盖的是「有没有渲染出来」，不是「渲染出来能不能被
看到」。模板源码对、单测对、语义树对——**没有一个判据看「它落在屏幕上的哪个位置」**。
DOM 有元素 ≠ 元素在可视区里。

**怎么量的**：按**真机几何**渲染再截屏。副窗是 `USAGE_VIEWER_SIZE` 760×800，而浏览器
面板的视口是 1280×720——**面板装得下、真机装不下**，拿面板当准就看不出问题。复刻办法：
临时预览页把 `html/body` 与 `.viewer-shell` 钉成 760×800（布局仍是真机尺寸，只把显示
尺寸缩放），截屏对照。

**修法**：回到全局约定（`overflow-y: auto` + `scrollbar-gutter: stable`，滚动条出现时
内容宽度不变），而不是另发明一套滚动语义。判据取**层叠后的生效值**
（`effectiveDeclaration(['main','usagewin-main'], …, 'overflow-y')`）——只在源码里找
`overflow-y: auto` 不算数，别的规则再写一条 `hidden` 就盖回去了，而那正是当初出事的
那条。**变异验过**：把它改回 `hidden`，那条判据立刻红。

**顺带一条**：目视验证时 `scroll` 一直返回 `SCROLL_EFFECT_UNVERIFIED`（moved=false），
当时差点当成工具的问题。**实际原因正是这个缺陷**：那个容器本来就不该滚（`hidden`），
所以「滚不动」是**正确**的反馈。⇒ 工具说「滚不动」时，先问「这个容器本来该能滚吗」，
别急着换工具。

## 35. 上游把某列留空 ≠ 那个值不存在：模型名要从旁证取回（2026-10-25）

用户盯着 MiniMax Desktop 那张卡上的 `minimax/未标注` 问：**「未标注的模型应该是
M3.1-Flash-preview 吧？」**——听起来只要把标签换成那个名字就完事了。**实测下来，
这个前提本身就是错的**，而且错得比标签本身更值得记。

### ① 「未标注」不是一个模型，是**一段时间没写**

当前库（`~/.minimax/v2/sqlite/runtime-state.sqlite`，2.0 GB / 快照 56,421 行，**库在持续写入**）的
`model` 列是**分三段**的：

| 区间 | 写法 | 行数 |
| --- | --- | --- |
| 2026-07-11 ~ 08-06 | `minimax/MiniMax-M3` | 6,836 |
| 2026-08-11 ~ 10-23 | **空** | 47,955（全表 85.0%） |
| 2026-10-23 ~ 至今 | `minimax/MiniMax-M3.1-Flash` | 1,630（快照） |

⇒ 那 47,955 行**不是某个模型**，而是 MiniMax 有两个多月**没往这一列里写模型名**
（期间用户换过 7 个模型）。此前一律归进 `minimax/未标注`——诚实，但把一整段历史
（8.9 B tokens）压成了一个说不清是什么的桶。

### ② 模型名**并没有丢**，在同一个库的隔壁那张表里

`local_runtime_message_rows.data_json` 的 `$.context_usage_telemetry.model` 记着
**每一轮实际用的模型**（52,379 条消息带这个字段、1,667 个不同的轮次）。按
`(session_id, turn_id)` 对齐，用量表里空着的那批行就能把模型名**取回来**：

| 取回来的模型 | 行数 | tokens | 区间 |
| --- | --- | --- | --- |
| `MiniMax-M3.1-Flash-Preview` | 30,374 | 5,642,575,011 | 09-27 ~ 10-19 |
| `MiniMax-M3` | 10,298 | 1,791,511,702 | 08-11 ~ 09-29 |
| `MiniMax-M3.1-Flash` | 6,950 | 1,468,501,001 | 10-19 ~ 10-23 |
| `gpt-5.6-luna` | 150 | 23,262,417 | 10-01 ~ 10-02 |
| `glm-5.3-flash` | 83 | 8,292,544 | 09-18 |
| `MiniMax-M2.7-highspeed` | 80 | 4,013,308 | 09-06 ~ 09-27 |
| `MiniMax-M2.7` | 13 | 668,361 | 09-07 |
| （取不到，仍标「未标注」） | 7 | 1,400,605 | — |

**用户的猜测对了一半**：M3.1-Flash-Preview 占 token 的 **63%**，剩下 **37%** 是
另外 6 个模型。**「未标注」这种桶不是一个东西，是一类东西**——把它当成一个模型
去猜，猜错的那 37% 用户永远看不到，还会以为自己看对了。

### ③ 这条取证链凭什么可信：三条**对照**，不是推断

1. **显式段对照**：显式写了模型名的那批 `minimax/MiniMax-M3.1-Flash`（快照 1,630 行），
   用**同样的键**对齐后 **1,630 行逐行相等、0 行不等**——**100%** 落回
   `MiniMax-M3.1-Flash`。若键选错了，这里就会散。
2. **一对多检查**：1,667 个轮次 = 1,667 个模型映射，**没有一个轮次对应两个模型**
   （若消息表里一个 turn 有两种模型，按 `(session_id, turn_id)` 归并就会出现一对多）。
3. **边界连续**：补出来的模型与显式段**首尾相接**——`MiniMax-M3`（显式 08-06 结束）
   → `MiniMax-M3`（空列段 08-11 起）→ `MiniMax-M3.1-Flash-Preview`（09-27 起）
   → `MiniMax-M3.1-Flash`（10-19 起）→ `MiniMax-M3.1-Flash`（显式段 10-23 起）。
   **换模型的那一刻正是模型列恢复写入的那一刻**，两段拼得起来。

### ④ 怎么取：**只查缺名字的那几轮**，别全表扫、也别按时间裁剪

- 只查「`model` 为空的那批 `(session_id, turn_id)`」，走 `(session_id, turn_id)`
  索引 ⇒ 实测 **0.63s**，比全表扫消息表（1.03s）快。
- **不按时间裁剪消息**：查的就是要的那一轮，于是**「消息还没落库所以查不到」这类
  时间差问题根本不存在**（实测用量行与消息落库时间的偏移最大是 **−20.7 分钟**，
  用量行可能早于消息落库——任何「按时间取消息」的做法都会踩到这个坑）。
- 显式值**永远优先**（那是上游自己写的，最权威）；显式值不存在才回补；两边都没有
  才落 `minimax/未标注`——**宁可标「未标注」，不编一个**。

### ⑤ 复验办法：把**生产源码**编进探针，而不是复刻一份

改的是「数据口径」的代码，单测用的是**造出来的**库——它证明不了真实盘上的数字。
这次用 `#[path]` 把 `src/usage/external/mod.rs`（连同 `codex.rs` / `minimax.rs`）
**直接编进一个 example**，把壳侧那几个 API 打桩，对真实 `~/.minimax` 跑完整扫描，
再拿**独立的 SQL** 逐项对账：8 个模型的行数与 token **逐个相等**（唯一一处差异是
两次测量之间本次会话自己又写了几行）。**对账的两边必须互相独立**：一边是生产代码
路径，一边是手写 SQL。

### 教训

- **「上游某列留空」有两种可能**：「那个值不存在」与「上游那段时间没写」。当成第一
  种，就会把一整段历史标成「未标注」，而数据其实就在隔壁那张表里。
  **先问「留空的是哪一段时间」，再问「同一个来源的别处有没有记着同一个事实」。**
- **桶不是模型**：`未标注` 这种桶是一**类**东西；把它当一个东西去猜，猜错的部分
  用户看不见，还以为自己看对了。**要猜也得先量出桶里到底有几种。**

## 36 外部来源的扫描：缓存与增量，以及「变异没让判据变红」的第三种分诊（2026-10-25）

用户问「外部 Agent 工具用量」有没有数据缓存避免反复扫描。查出来的答案是**两套语义**：
Codex 侧有**文件级**增量缓存（`size` + `mtime` 一致就复用），MiniMax 侧**一点缓存都没有**；
而**外部这条链没有新鲜度窗口**——内核那份账有 90s 窗口，外部没有，于是「连着开两次窗」
就是两次真扫。

### ① 先量成本，别凭印象

sqlite3 CLI 实测本机那张 56,700 行的表（3 次取中位，进程启动等固定开销约 100ms）：

| 查询 | 中位 |
| --- | --- |
| `count(*)` / `max(ts)` | 约 0ms（走索引） |
| 全量窗口查询（8 列） | 312ms |
| **模型名回补**（47,757 行 JSON 提取） | **1245ms** |
| 增量版（近 1 小时的同一段查询） | 约 0ms |

⇒ **大头是回补，不是读数**。所以增量的收益几乎全在「只查新增的那几轮」上；而
`count(*)` / `max(ts)` 走索引近乎免费，**拿它们当库的身份指纹不花钱**。

### ② 新鲜度窗口要按**日历日**也作废

窗口按毫秒算（90s），而「今日用量」按**日历日**算。23:59:50 扫的缓存，00:00:10
拿来用，「今日」就整整差一天。⇒ 缓存里除了时刻还要记**本地日历日**，跨日即作废。
另一道闸：上一轮**没读全**就不许当新鲜缓存——空账被当成「已读过」缓存下来，那个
来源的用量会从此一直是 0（§35 那个坑的整源版本）。

### ③ 增量必须配**身份对账**

表是只增不改的日志 ⇒ 总行数只会增加，且增加的正好是这一轮新读到的行数。对不上
（库被换掉 / 被重写）就**整表重扫**：宁可多扫一次，不可少算。

### ④ 反向验分诊的**第三种情形**

把增量下界从 `ts > 高水位` 改成 `ts >= 高水位`（旧行会被重复计数），判据**没红**。
分诊结论既不是「判据坏了」也不是「变异没生效」，而是**第三种**：**另一道闸把后果
兜住了**——身份对账发现行数对不上，立刻整表重扫，账仍然对，只是**从增量退化成了
全量重扫**。

⇒ 由此要分清判据钉的是**正确性**还是**效率**：正确性被兜住了，效率没有。办法是给
效率性质一个**可观测的量**（这里给缓存状态加 `scanned_rows`：这一轮实际读了多少行），
让「退化成全量重扫」这件事**看得见**。

### 教训

- **「有没有缓存」这句话底下常常是两套语义**：同一个「外部来源」，Codex 按文件增量、
  MiniMax 全量重扫。问的时候要问「**哪一层的缓存**」，否则会得到「有缓存」这种半真
  半假的答案。
- **窗口按毫秒、数据按日历日**：跨零点那一秒，毫秒窗口认为缓存还新鲜。
- **增量没有身份对账就没有下限**：库被换掉时，高水位会让新数据**永远进不来**。
- **反向验里「变异没让判据变红」要先分诊**（判据坏 / 变异没生效 / 另一道闸兜住了），
  第三种最容易被误判成「判据坏了」，白改一轮。

## 37 「全部展示、不出内部滚动条」：内层滚动条是三层链条，且 `min-height: auto` 托不住（2026-10-25）

用户提的：「模型详细展示这里让 UI 全部展示，不出内部的纵向滚动条，下方的 agent 数据
也是这样处理」。附的截图里，模型列表右侧有一条**内嵌**滚动条（最后一行「gpt-6.1-sol」
被切），而窗口右侧同时还有外层那条——**两条纵向滚动条抢同一份内容**，拖外层那条到
底也只露出列表的前几行。

### ① 内层滚动条是**三层链条**造出来的，不是某一条 CSS

| 层 | 当时的值 | 作用 |
| --- | --- | --- |
| `.usage-model-section` | `flex: 1 1 0` + `min-height: 252px` | basis 为 0、下限钉在 252px，内容一多这一段就只剩 252px |
| `.usage-models` | `overflow: hidden` | **滚动容器的 min-content 高度按 0 算** ⇒ 上一段的自动最小尺寸塌成 0，整段被压扁 |
| `.usage-model-list` | `overflow-y: auto` | 内容于是在自己容器里滚 |

⇒ 改的时候要**三处一起改**：列表去掉内部滚动（`overflow-y` 回到 visible）、中间那层
去掉 `overflow: hidden`（否则 min-content 塌成 0）、外层那段改成 `flex: 1 0 auto`
（basis 用 auto 而不是 0）。只改一处，另两处会把形状复原。

### ② `min-height: auto`（自动最小尺寸）**托不住**被压扁

去掉 `min-height: 252px` 之后，本以为自动最小尺寸会兜住「不许被压扁」——**并没有**。
自动最小尺寸按 **min-content 高度**算，而外部那一段里有**百分比高度**的日柱条
（高度百分比在高度不定的祖先里按 auto 处理），min-content 高度因此偏小，那一段
照样被压扁（实测 clientHeight 349 / scrollHeight 480）。

⇒ 真正管用的是 **`flex-shrink: 0`**：内容超出一屏时由 `.usagewin-main` 自己滚，
而不是把某一段挤成「内容比盒子高」。这条对**所有**段都成立。

### ③ 静态判据钉不住「行有没有全露出来」

判据能钉的是**层叠后的生效值**（列表没有 `overflow-y: auto`、中间那层不是
`overflow: hidden`、各段 `flex-shrink` 是 0），钉不住的是**渲染后的几何**：
「最后一行是不是完整可见」「内部还剩几个真滚动容器」。后者要**真实渲染 + 量 DOM 几何**。

量法（这次用的，临时脚手架，测完即删）：真组件 + 真 CSS + 桩数据（字段名照后端
`UsageView` / `ExternalToolUsage` 造），容器复刻真机 `USAGE_VIEWER_SIZE` 760×800，
读数取 `clientHeight` / `scrollHeight` / 最后一行 `getBoundingClientRect().bottom`
是否 ≤ 列表底边 / main 内**真滚动容器**的个数。写进容器**外面**的元素——测量本身
不许改变被测布局。

**A/B 基线**：同样桩数据下把 CSS 还原到 HEAD 再量一次，`modelList` clientHeight 212
/ scrollHeight 221（`internalScroll` true、最后一行不可见）——**用户截图里的缺陷被
忠实复现**，于是「改完再量一遍」的对照才有意义。

### ④ 测量脚本里的两个假阳性

- `overflow-x: auto` 的热力图，在 `overflow-y` 上**也算** `auto`——一条轴不是 visible
  时另一条轴按 spec 计算成 auto。只按 overflow-y 筛，它会被当成纵向滚动容器；它其实
  只横着滚（`scrollHeight == clientHeight`）。判据要加「真的有纵向溢出」这一条。
- `inline` 元素的 `clientHeight` 是 0 ⇒ 「内容比盒子高」永远成立。趋势图的 y 轴标签
  就是这种，按内容比盒子高筛会满屏假阳性。

### 教训

- **「内部滚动条」不是一条 CSS 的事**：它常常是「上层给了硬下限 + 中层是滚动容器 +
  下层自己滚」三层叠出来的。只改最显眼的那个（列表的 `overflow-y`），形状会被上层
  复原成「被压扁的一段」。
- **自动最小尺寸按 min-content 算**，不是按内容高度算——里面有百分比高度时，它比你想
  的小。要「不许被压扁」，写 `flex-shrink: 0`。
- **判据钉「层叠后的生效值」，量测钉「渲染后的几何」**，两者不能互相替代；截图能看见
  的缺陷，先在隔离预览里复现并量出数字（基线也要量），再改。
