## 2. 调研事实

### 2.1 动机：算术上的硬失败（不是「省用户操作」）

协议 §4 的常量摆在一起时，硬失败是算出来的：

| 常量 | 值 | 出处 |
| --- | --- | --- |
| 单条正文预算 | 64 KB | 协议 `:187` |
| 单消息引用数上限 | 8 条 | 协议 `:186` |
| 单次消息总预算 | 256 KB（含原生 `@session`） | 协议 `:188` |
| 最大正文字节 | 256 KB（超过 → `body_too_large`） | 协议 `:182` |

⇒ **64 KB × 8 条 = 512 KB > 256 KB** ⇒ 同一段正文被引用 8 次时，**总预算必然超限**，落 `body_too_large`（错误码见协议 `:151`）。**这是 P2 议题的硬约束来源**；「省用户操作」则不是硬约束（多一条提示不省任何操作）。

### 2.2 键的形状

去重/合并的判定键 = **(accountScope, sessionId, branch, capturedAt, contentDigest) 全等**。

- **五字段全等**才判定为「同一份」；**任一不同即不是**。
- **跨会话 / 跨账号 / 跨分支 / `capturedAt` 不同 ⇒ 一律不合并**。
- 依据：development-plan §8（`:168`）「快照 id 标识固定版本，重新选择生成新版本；**去重不能抹掉账户、分支或捕获事实**」——`capturedAt` 进入键，正是这条的后半句。
- **五字段都已在快照里** ⇒ **不必新建索引表**（无新增存储、无新增一致性面）。

### 2.3 落点：三层的能力分界（本议题最关键的一条）

「插件能不能做消息级操作」取决于**内核的调用点在浏览器侧还是 Node 进程侧**，不能凭「都是同一个产品的插件」想当然。

现役内核 release 树 `0.2.1-rc.2`（绝对路径 `C:\Users\zxx\.dsh-xlink\dsh\desktop\kernels\0.2.1-rc.2\node_modules\@deepseek-ai\`）：

| 层 | 事实 | 出处（文件 / SHA-256 / 行号） |
| --- | --- | --- |
| **浏览器侧**（client） | 引用展开在浏览器侧：拿到整条消息的 occurrences 后**逐个**调 `serializeReference` ⇒ **插件的 `codec.serialize` 只看得到单 ref**，看不到同行其它引用 | `dsh-client-ui-conversation/lib/client.js` SHA `8554738CBEEB5218AD1BFA4773EF094363B066D052A1893D7A96797C5BC33A63`（774080 B / 20065 行）`:15505-15513`；`dsh-client-ui-input-trigger/lib/client.js` SHA `4A9605B0A811354ED49495790B331BF4F5198FF41614920D9D0C488E22A0F2AF`（77121 B / 1951 行）`:1249-1253` |
| **Node 进程侧**（host） | 消息级入口 = host 监听 `agent/pre-step`（带整批 `messages` 且**可 replace messages**）；但 `UserMessage` **不含 ref/occurrence 结构** ⇒ **只能做文本级判定**（用 digest 反查） | `dsh-agent/lib/types/runtime-types.d.ts` SHA `7C03F0F92BE4A48CC7960AC02FC040B2088B462AE790EAB1427E50BFE5E74B31`（20625 B / 410 行）`:304-310`；`dsh-llm/lib/types/message.d.ts` SHA `C1E9B9F05FC0EAB9BB791D6CBFC42828E608539BA16CD0E441164AFF005B9775`（10469 B / 246 行）`:144-146` |
| **存储层** | 只供材料，不改 | — |

⇒ **推论形态**：「同一消息内合并两份相同正文」这类需求，在**逐 occurrence 展开**的契约下**没有干净落点**——只能降级为文本级判定或 UI 提示。

### 2.4 红线

1. **绝不复用旧 id**：合并/去重不得让两个引用拿到同一个 `snapshotId`（撞 S-1「两次 pick 两个 id」与 S-6「失效即拒」）。
2. **隐式去重撞 S-7**：协议 S-7 写「同一段对话被引用两次 → 两个 `snapshotId`，正文按引用次数各送一份（不隐式去重）」⇒ **合并必须对用户可见**，否则不做。
3. **内核重放不在管辖范围**：内核会把本轮用户输入在同一请求里重放多次（实测 p1-r9：盘上正文在请求体命中 4 处，逐字节相同）——那是**内核的上下文组织**，发生在展开之后，插件观测不到也控制不了。⇒ **不得写「正文只出现一次」这类判据**（见 §5 A8）。
4. **偏向宁可漏**：宁可少识别一组重复，也不要错合并（错合并会让用户以为引 A 其实是 B）。

### 2.5 digest 反查的可用边界

- **可作为「提示」的判定依据**：误报的后果只是多一条提示。
- **不可作为「合并」的依据**：误判的后果是错合并（见 §2.4-4）。

### 2.6 协议内部张力（已消歧）

`development-plan` §7:155（G4 验收）「正文只出现一次」与协议 S-7「引用两次各送一份」**字面冲突**。⇒ **协议 v0.7 已以 S-7 为准消歧**，并把「一次」解释为「**同一份快照**的正文只追加一次（不因内核重放/工具循环被多次追加）」；同时记入 feasibility §7 第 12 条。⇒ **P2 若立项，不必回头改 development-plan**（改写归属待 izzy 指定，见 §6）。

## 3. PM 建议的判据方向（**尚未写**）

P2 立项后由 tester 依协议落判据；**本轮不写判据、不写夹具**。建议方向（三条，非清单）：

1. **重复识别**：构造「同一会话同一分支、同一正文被引用多次」的夹具 ⇒ 断言产出的「重复组」与 §2.2 的键一致；**键任一字段不同 ⇒ 必须不在同一组**。
2. **可见性**：重复发生时必须有**可见**提示（不能静默）。**「可见」如何判定需先定承载位**（见 §4-2）。
3. **预算预检**：引用数 × 单条正文预算逼近总预算时，**在发送前**给出可见预检信号；**不得**靠截断正文来绕过超限（截断＝静默裁掉，撞 S-7）。

## 4. PM 建议裁定（三条）

> **状态：建议，待 izzy 拍板。** P2 尚未立项；下列三条不生效。

1. **目标 = 省预算，不动 chip 数。** 理由：§2.1 的算术是硬失败（`body_too_large`）；「少一次操作」不是硬约束。⇒ **不动引用标签的数量**（chip 数由用户操作决定）。
2. **第一步只做「重复识别 ＋ 可见提示 ＋ 预算预检」，不做消息级自动合并。** 理由：① 合并必须对用户可见，而 **P2 阶段没有可见承载位**（详情面板属 P5）；② toast 瞬态 ⇒ 判据易假红；③ §2.3 的落点在消息级没有干净落点。⇒ **没有可见方案就不做**（S-7 禁止静默裁掉）。
3. **落点 = host 命令层产出「重复组」，client 呈现；不改消息内容。** 理由：host 是**唯一**能同时看到整批快照与 id 的层（client 逐 occurrence 只看得到单 ref）；而改消息内容会与 §2.4-2 撞。⇒ **不在 `agent/pre-step` 里改消息**（那里只做引用展开，见 development-plan §7 `:149`；改它＝替内核改上下文语义）。
