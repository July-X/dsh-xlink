## 2. 调研事实

### 2.1 动机：算术上的硬失败（不是「省用户操作」）

协议 §4 的常量摆在一起时，硬失败是算出来的：

| 常量 | 值 | 出处 |
| --- | --- | --- |
| 单条正文预算 | 64 KB | 协议 `:187` |
| 单消息引用数上限 | 8 条 | 协议 `:186` |
| 单次消息总预算 | 256 KB（含原生 `@session`） | 协议 `:188` |
| 最大正文字节 | 256 KB（超过 → `body_too_large`） | 协议 `:182` |

⇒ **64 KB × 8 条 = 512 KB > 256 KB** ⇒ 同一段正文被引用 8 次时，**总预算必然超限**，落 `body_too_large`（错误码见协议 `:151`）。**这是 P2 议题的硬约束来源**；「省用户操作」则不是硬约束（多一条提示不省任何操作）。

### 2.2 键的形状

去重/合并的判定键 = **(accountScope, sessionId, branch, capturedAt, contentDigest) 全等**。

- **五字段全等**才判定为「同一份」；**任一不同即不是**。
- **跨会话 / 跨账号 / 跨分支 / `capturedAt` 不同 ⇒ 一律不合并**。
- 依据：development-plan §8（`:168`）「快照 id 标识固定版本，重新选择生成新版本；**去重不能抹掉账户、分支或捕获事实**」——`capturedAt` 进入键，正是这条的后半句。
- **五字段都已在快照里** ⇒ **不必新建索引表**（无新增存储、无新增一致性面）。
- **协议把「快照 id 唯一」与「正文去重」写成两条独立条款**（S-7 在协议 `:135-137`，其中 `:137` 明写「正文去重列为 P2 议题……属 mention 展开与模型输入预算的范畴」）⇒ 正文去重**不是 id 制度的延伸** ⇒ 合并不等于改 id 制度。

### 2.3 落点：三层的能力分界（本议题最关键的一条）

「插件能不能做消息级操作」取决于**内核的调用点在浏览器侧还是 Node 进程侧**，不能凭「都是同一个产品的插件」想当然。

现役内核 release 树 `0.2.1-rc.2`（绝对路径 `C:\Users\zxx\.dsh-xlink\dsh\desktop\kernels\0.2.1-rc.2\node_modules\@deepseek-ai\`）：

| 层 | 事实 | 出处（文件 / SHA-256 / 行号） |
| --- | --- | --- |
| **插件自己的 client 层** | **client 侧不碰正文**：id 由 host 在 `catalog` 那一步分配好、正文由 host 在 `capture` 那一步取好并落盘、模型输入的正文由 host 在 `preview` 那一步**从盘上读回**；client 只做三件事（同步返回句柄 / 等或拒 / 把状态报给用户）⇒ **客户端层做不了去重**；且在客户端层动去重 = 改**用户可见的 chip 数** | `plugins/official-chat/client/client.js:227-230`（仓库内源码） |

⇒ **推论形态**：「同一消息内合并两份相同正文」这类需求，在**逐 occurrence 展开**的契约下**没有干净落点**——只能降级为文本级判定或 UI 提示。

### 2.4 红线

1. **绝不复用旧 id**：合并/去重不得让两个引用拿到同一个 `snapshotId`（撞 S-1「两次 pick 两个 id」与 S-6「失效即拒」）。**依据**：协议 §6（`:228` 起）「快照不可变、同 id 不重写」＋ development-plan §8（`:168`）「重新选择生成新版本」⇒ **只能在展开/呈现层做，id 分配（host `seq-claims/` ＋ `snapshots/` 两份取大）一个字不动**。
2. **隐式去重撞 S-7**：协议 S-7 写「同一段对话被引用两次 → 两个 `snapshotId`，正文按引用次数各送一份（不隐式去重）」⇒ **合并必须对用户可见**，否则不做。
3. **内核重放不在管辖范围**：内核会把本轮用户输入在同一请求里重放多次（实测 p1-r9：盘上正文在请求体命中 4 处，逐字节相同）——那是**内核的上下文组织**，发生在展开之后，插件观测不到也控制不了。⇒ **不得写「正文只出现一次」这类判据**（见 §5 A8）。
4. **偏向宁可漏**：宁可少识别一组重复，也不要错合并（错合并会让用户以为引 A 其实是 B）。**代价不对称**（原文第 5 点）：漏去重 = 多花预算 ＋ 两个同内容 chip（可接受、可提示）；错去重 = **模型收到错内容**（事实性错误，最坏形态）⇒ 保守不合并是可接受的方向。

### 2.5 digest 反查的可用边界

- **可作为「提示」的判定依据**：误报的后果只是多一条提示。
- **不可作为「合并」的依据**：误判的后果是错合并（见 §2.4-4）。

### 2.6 协议内部张力（已消歧）

`development-plan` §7:155（G4 验收）「正文只出现一次」与协议 S-7「引用两次各送一份」**字面冲突**。⇒ **协议 v0.7 已以 S-7 为准消歧**，并把「一次」解释为「**同一份快照**的正文只追加一次（不因内核重放/工具循环被多次追加）」；同时记入 feasibility §7 第 12 条。⇒ **P2 若立项，不必回头改 development-plan**（改写归属待 izzy 指定，见 §6）。

### 2.7 内核同生态的先例（支持「全等才折叠」）

现役内核里已有同生态的去重口径，方向与本议题的键一致：**全等才折叠**。

- 出处：现役内核 release 树 `0.2.1-rc.2` 的同生态包 `dsh-agent-instructions/README.zh.md` SHA `C31D31C892F81B53F0BB7AF409289C3868321D80B939EE7568D552B6A83088CD`（13944 B / 236 行）`:222`：「**去重在同一候选组内基于内容**：候选只有在去除首尾空白后**字节完全一致**时才折叠。」
- ⇒ 与 §2.2 的键方向一致：**不是「看起来一样」，是「同一组 ＋ 逐字节一致」**。本议题还多一层要求：键必须含**账户 / 分支 / 捕获事实**（plan §8 `:168`），比「同组内字节一致」更严 ⇒ 沿用先例的严格方向，不放宽。

## 3. PM 建议的判据方向（**尚未写**）

P2 立项后由 tester 依协议落判据；**本轮不写判据、不写夹具**。建议方向（原文第 6 点给了四条，PM 采纳并补两条工程前提）：

1. **键全等的两个不同 ref ⇒ 仍是两个不同 `snapshotId`、都落盘、都可发**（防「去重」退化成「复用旧 id」）。
2. **合并后模型可见输入里该正文出现 1 次**，**且**引用计数仍为 2，**且**有**可见的合并说明**。
3. **负例①：`capturedAt` 不同 ⇒ 不合并**（哪怕正文逐字节相同）。
4. **负例②：`accountScope` / `branch` 不同 ⇒ 不合并。**
5. **可见性（提示侧）**：重复发生时必须有**可见**提示（不能静默）。**「可见」如何判定需先定承载位**（见 §4-2）。
6. **预算预检**：引用数 × 单条正文预算逼近总预算时，**在发送前**给出可见预检信号；**不得**靠截断正文来绕过超限（截断＝静默裁掉，撞 S-7）。

**夹具形态（建议）**：新夹具 =「**去重候选对**」——两条快照 ＋ 期望是否合并，登记进 `fixtures/protocol/index.json`（**两端都读 ⇒ 双端自动跑到**）。**等 PM 拍板键的形状之后再写**：夹具的 `expected` 会把键的形状**焊死**（同 `oversized-multi` 的教训：先定「取窗口上沿」再写）。

**跨语言一致性（建议）**：若判定只单侧在 host 做 ⇒ **不必**双端一致；但**键的构成与摘要口径**建议**进协议层**（Rust 侧已有 `content_digest`：`src-tauri/src/official_chat/protocol.rs:209`；JS 侧同口径）⇒ 双端一致成本低，且夹具能钉住「什么算同一捕获事实」。

## 4. PM 建议裁定（三条）

> **状态：已拍板（izzy 22:5x 点头 P2 立项，未对三条提出异议）——下列三条生效为 P2 第一批口径。** 协议化见 [official-chat-p2-protocol.md](official-chat-p2-protocol.md) v0.1（PM 定，devloper 依此实现，tester 依此落判据）。

1. **目标 = 省预算，不动 chip 数。** 理由：§2.1 的算术是硬失败（`body_too_large`）；「少一次操作」不是硬约束。⇒ **不动引用标签的数量**（chip 数由用户操作决定）。
2. **第一步只做「重复识别 ＋ 可见提示 ＋ 预算预检」，不做消息级自动合并。** 理由：① 合并必须对用户可见，而 **P2 阶段没有可见承载位**（详情面板属 P5）；② toast 瞬态 ⇒ 判据易假红；③ §2.3 的落点在消息级没有干净落点。⇒ **没有可见方案就不做**（S-7 禁止静默裁掉）。
3. **落点 = host 命令层产出「重复组」，client 呈现；不改消息内容。** 理由：host 是**唯一**能同时看到整批快照与 id 的层（client 逐 occurrence 只看得到单 ref）；而改消息内容会与 §2.4-2 撞。⇒ **不在 `agent/pre-step` 里改消息**（那里只做引用展开，见 development-plan §7 `:149`；改它＝替内核改上下文语义）。
