# P3 协议：快照原子发布、占用关系与存储保护（v0.1）

> **状态**：冻结稿 v0.1（PM 起草，待判据与实现落地后升版）。
> **一句话**：把「快照写下来」从**直写最终路径**改成**原子发布**，把「谁还占着这份快照」
> 从**进程内计数**改成**落盘的占用记录**，把「存储保护」从**散落的 mode 参数**写成
> **一条成文的落盘策略**。
> **不做什么**：不做真实站点接入（P4）、不做消息级合并（P2 议题）、不动内核安装包。

---

## 0. 本稿的前提（先说边界，避免后面的人误读范围）

1. **本稿不放松 P1/P2 任何一条**。P1 的 S-1…S-7 与 P2 的全部条款继续有效；
   本稿只**新增** S-8…S-15，并**显式取代** P1 §4.1 第 4 条（见 [S-11](#s-11--占用记录落盘形态与释放规则)）。
2. **本稿的每条条款都标了「现状」**，现状是 PM **一手核过**的（行号当场核，见每条的证据行）。
   标「已满足」的条款**不是**本批要做的，是**要防回退**的（判据里要有一颗钉子）。
3. **本稿不声称内核能做到的事**。内核的 source 契约全集已在 [§7.1](#71-上游缺口-g1-8内核-source-契约无引用移除信号)
   逐条列出并附内核文件指纹——**内核从不对 source 说「某个引用没了」**，
   这决定了 [S-12](#s-12--引用关系的可判定边界降级口径) 的降级形态。
4. **「做不到的」写成缺口，不写成条款**。凡是内核契约里没有信号的规则，
   本稿**不**把它写成验收项（本项目已有先例：P1 的 G1-6「chip 无 `invalid` 写入口」
   按「发送时拒 ＋ 可见错误」验收，**不**降级写成节点级断言假装能测）。

## 2. 落盘物与术语

本实例根 `<root>` 下，现有**四家族**（P1 §4.1 第 2 条：`snapshots/`、`seq-claims/`、
`catalog-cache/`、`logs/`）＋ 本稿**新增两个**。

### 2.1 快照目录（既有，不变）

- `<root>/snapshots/<provider>/<snapshotId>.json`
- 目录 `mkdirSync(dir, { recursive: true, mode: 0o700 })`（`plugins/official-chat/host/index.js:344`）
- 文件 `mode: 0o600`（`plugins/official-chat/host/index.js:348`）

### 2.2 「索引」的准确定义（本稿裁定）

> **计划 §8 第 2 段的「公布索引」＝ 让这份记录出现在快照目录清单里。
> 本功能不建独立索引文件**（延续 P2 §6.6）——**目录扫描本身就是索引**。

- 现状**本已如此**：目录清单、已用序号一律从**目录扫描**得出
  （`host/index.js:405-428` 的 `listSessionSeqs` 扫 `snapshots/<provider>/*.json` 取每会话最大 `seq`；
  `host/sweep.js` 的扫盘同理），**没有 `index.json` 这类东西**。
- ⇒ 「公布」只有一个可观测动作：**该文件以最终名出现在 `<root>/snapshots/<provider>/` 里**。
- ⇒ **发布点 = `rename` 成功那一刻**。在 rename 之前，它只是**一个临时文件**，
  **不在清单里**、**不是快照**、**不可被 preview 读到**。
- **为什么必须写死**：计划 §8 第 2 段说「先完成完整文件写入并验证摘要，再公布索引」，
  若「索引」含义不清，实现就会写成「两个独立文件各自原子写就宣称事务完成」——
  那正是计划原文**明令禁止**的形状。

### 2.3 临时文件（新增，第五家族的前身）

- 形态：`<root>/snapshots/<provider>/.<snapshotId>.json.tmp-<pid>-<seq>-<attempt>`
  （**点开头**，与最终名不同 ⇒ 目录扫描时一眼能区分「已发布」与「未发布」）。
- 生命周期：写入 → 回读校验 → `rename` 成最终名；rename 失败 ⇒ 临时名留在盘上（见 S-10）。
- **临时文件不是快照**：任何按 id 读取的路径**不得**命中临时名。

### 2.4 占用记录 `refs/`（新增家族）

- 形态：`<root>/refs/<snapshotId>.json`
- 内容：`{ snapshotId, capturedAt, createdAt, sessionId }`——**只有这四个字段**，
  **不含正文、不含摘要**（日志与诊断包不收正文的纪律，§S-14）。
- 语义：**「有一份占用关系指向这份快照」的凭证**。**不是**「草稿本体」，
  **不是**引用计数，**不表达**内核草稿的真实状态（内核契约里查不到，见 S-12）。

## 3. 条款

### S-8｜快照落盘 ＝ **原子发布**

- **依据**：计划 §8 第 2 段「正文保存与索引提交采用可恢复的顺序：先完成完整文件写入并验证摘要，再公布索引；
  失败不发布半条记录」。
- **现状（PM 一手核过）**：**不满足**。`plugins/official-chat/host/index.js:348` 是
  `writeFileSync(path, \`${JSON.stringify(stored, null, 2)}\n\`, { flag: 'wx', mode: 0o600 })`
  ——**直写最终路径**。进程在写一半时死掉，目录里就留下一份**文件名已在、正文不完整**的
  `<id>.json`：它**已经出现在目录清单里**（§2.2 的「已发布」），但正文是半截。
  现状唯一的兜底是**读时**摘要校验（`host/index.js:392-395`）会把它拒掉——**拒得对，
  但「半条记录已经发布」这件事本身已经发生**。
  另外：**摘要在写前于内存算好**（`host/index.js:316-321`），**写后不回读**。
- **裁定**：
  1. 写入必须走「**临时文件 → 回读校验 → rename**」三步（临时名见 §2.3）。
  2. **回读校验**：rename 之前，把临时文件读回来，重算 `contentDigest`（口径见 P1 §1.3）
     并与盘上 `contentDigest` 比对；**不一致 ⇒ 不 rename**（失败按 `snapshot_invalid`，
     临时文件按 S-10 清理）。
  3. **rename 成功 ＝ 发布**；rename 失败 ⇒ **不得**把临时名改成最终名。
  4. **`wx` 语义保留**：最终名已存在 ⇒ `snapshot_exists`（**不覆盖**，P1 §6「同 id 不重写」）。
  5. **协议只规定性质，不规定实现形态**——用 `fs.rename` 还是别的，判据只断**可观测性质**
     （见 [§5](#5-验收判据tester-依此写)）。
- **验收口径**：见 P3-1、P3-2。

### S-9｜**发布点 = `rename` 成功那一刻**

- **依据**：同 S-8。
- **现状（PM 一手核过）**：**不满足**（因为没有 rename，见 S-8）。
- **裁定**：目录清单、序号取大、对外回报的快照数——**一律以最终名为准**；
  临时文件**不进清单、不占序号、不计入「已保存」**。
  ⇒ 「已保存」这个事实**只有一个来源：最终名的文件存在**（呼应 P1 S-3「单一事实源 = 快照文件」）。
  ⇒ **注**：实现上「临时文件不进清单」目前是**靠命名顺带成立**的
  （`host/index.js:418` 只认 `*.json` 结尾的文件，临时名以 `.tmp-…` 结尾）——
  **协议要的是性质，不是命名** ⇒ 判据断「清单里有几个最终名／几个临时名」这个**可观测事实**，
  **不得**断「文件名长什么样」。
- **验收口径**：见 P3-1。

### S-10｜崩溃残留（**第五家族**）必须被专门清理

- **依据**：计划 §8 第 2 段「崩溃残留只清本功能未引用的临时对象，恢复不得越出缓存根」。
- **现状（PM 一手核过）**：**不满足**。`host/sweep.js:20-32` 明确只扫**四家族**，
  **没有临时文件这一类**；`host/sweep.js:216-242` 的快照清理只认 `*.json`
  ⇒ 半写的 `<id>.json` 只能等**保留期到期**（7 天）按 mtime 兜底删。
  （现状之所以没爆，是因为现状**根本不产生**临时文件——S-8 落地后才会有。）
- **裁定**：
  1. 临时文件是**第五家族**：`snapshots/<provider>/.*.tmp-*`。
  2. 清理触发点沿用 P1 §4.1 的惰性口径（**只在 `catalog` 入口**、同实例至多一天一次）
     ⇒ **不新增常驻定时器**（插件不常驻，定时不可靠）。
  3. **只清本功能未引用的临时对象**：临时文件**天然未被引用**（§2.2：未发布即不是快照）
     ⇒ 清理条件 = **文件名匹配临时名形态** ＋ **在本实例根下** ＋ **超过阈值**（默认 24 小时，
     见 §4）**且** 不在「本轮刚写、正在发布」的窗口内。
  4. **不得越出缓存根**：删除路径必须由 root join 得出（沿用 `host/sweep.js:218/251/317/359`
     的既有做法），**两步法删除**（`rename` 成墓碑 → `unlink`，沿用 `host/sweep.js:80-93`）。
  5. **清理失败只记日志，不阻塞业务**（P1 §4.1 第 3 条的四可观测条件**逐条沿用**）。
- **验收口径**：见 P3-3。

### S-11｜占用记录：落盘形态与释放规则

- **依据**：计划 §8 第 4 段「草稿和在途请求持有明确引用关系，自动回收只处理未引用记录。
  恢复前应先重建草稿引用关系，不能先回收再恢复。」
- **现状（PM 一手核过）**：**不满足**。
  - `plugins/official-chat/client/client.js:523` 的 `selectedRefs = new Set()` 是
    **唯一的引用持有结构**，**只在进程内**；注释 `client/client.js:520-521` 自陈
    「**为什么放在内存而不是落盘**」。
  - `plugins/official-chat/host/sweep.js:45-49` 明写「**不保护「正在发送中的引用」**」
    「**不引入引用计数**」——⇒ **回收时没有任何引用判定**。
  - `client/client.js:517-518` 自陈：「用户在编辑器里删掉某个 chip 之后，这个 id **仍留在本列表里**
    ⇒ 预检偏保守（多算一点），**不会少报**」⇒ **无释放路径**。
- **裁定**：
  1. **占用记录落盘**（形态见 §2.4）：`capture` 成功、快照发布（S-8）之后**立即**写
     `<root>/refs/<snapshotId>.json`；**先写占用记录，再对外宣告「已保存」**。
  2. **释放规则**（**只写插件侧可判定、可测试的三条**）：
     - **R1 释放**：该快照被判定**不再可引用**时（用户显式移除、或该次 pick 被取消）⇒ 删占用记录。
     - **R2 兜底释放**：占用记录**超过占用保留期**（默认 7 天，见 §4）⇒ 视为失效，删占用记录。
       **这条是「不可判定」的兜底**，也是**当前唯一可靠的释放路径**（原因见 S-12）。
     - **R3 拒绝释放**：占用记录**写坏/读不出** ⇒ **不删**（P1 §4.1「宁可不清理，不乱删」的同款口径）——
       读不动 ⇒ 「这份快照被占着」这件事**无法证伪** ⇒ 按被占着处理。
  3. **回收只处理未引用记录**：快照清理（`host/sweep.js:216-242`）在删除前**必须**查
     `<root>/refs/<snapshotId>.json`：**存在 ⇒ 不删**（除非它自己也过期，按 R2）。
     ⇒ **「先查引用、再删快照」的顺序是硬要求**，与 P1 §4.1「先快照后认领」不冲突
     （那是**认领与快照**的次序；这是**引用与快照**的次序，**先查后删**即可）。
  4. **不引入引用计数**（延续 P1 §4.1 第 4 条的克制）：占用记录是**「有/无」的凭证**，
     **不是计数器**——同一快照被引用两次，**仍是一条**占用记录（S-7：id 唯一 ≠ 正文去重，
     两条快照各自一条占用记录）。
- **验收口径**：见 P3-4、P3-5。

### S-12｜引用关系的可判定边界（**降级口径** ＋ 上游缺口）

- **依据**：计划 §8 第 4 段「被遗弃草稿的引用如何释放、进程崩溃后如何调和，**要有可测试规则**；
  **不能仅用进程内计数保证重启安全**。」
- **现状（PM 一手核过）**：**部分不满足**。
  - **不满足的一半**：「不能仅用进程内计数」——现状**恰恰就是**进程内计数
    （`client/client.js:523` 的 `selectedRefs`）⇒ S-11 补上落盘形态即解。
  - **做不到的一半**：**内核 source 契约里没有「引用被移除 / 草稿被放弃 / 已发送成功」的信号**。
    内核 `0.2.1-rc.2` 的 `InputTriggerSource` 接口全集（**逐条核过**，见 §7.1）是：
    `candidates` / `header?` / `onPick` / `matchSpace?` / `matchEnter?` / `matchClaim?` /
    `warm?` / `lexicon?` / `subscribeLexicon?` / `openReference?` / `codec.serialize`。
    ⇒ **内核只「问」source，从不「告诉」source**。
    ⇒ 由此**三条不可判定**：
      1. **用户删掉某个 chip** ⇒ source 不知道（现状 `client/client.js:517-518` 已自陈）。
      2. **草稿被放弃 / 会话被切换** ⇒ source 不知道。
      3. **引用已被成功写进会话历史** ⇒ source 不知道；
         且 **`serialize` 会被内核重复调用**（P1 §8-5：实测同一请求里盘上正文命中 **4 处**）
         ⇒ **在 `serialize` 里释放是错的**（重放会把引用提前释放）。
- **裁定**：
  1. **本阶段不声称**「引用关系 = 内核草稿的真持有关系」。S-11 的占用记录是
     **插件侧自洽的占用凭证**，不是内核草稿的镜像。
  2. **降级口径（写进验收，不许含糊）**：**误删的后果是「该引用失效并被拒」（`snapshot_invalid`）
     ＋ 可见错误，不是错发**——这正是 P1 §4.1 第 4 条已经写明的既有语义，**继续有效**。
  3. **恢复顺序**：**先重建占用关系，再回收**（计划 §8 第 4 段原文）。
     重建的对象是**本实例根下的占用记录**（读回即重建），
     **不是**内核的草稿状态（内核侧不归本插件管，也查不到）。
     ⇒ **可测试规则**：「回收动作之前，必须先完成一次占用记录的全量扫描」——
     这条**可机检**（判据可断言「扫占用在前、删快照在后」的次序）。
  4. **不得**把「引用关系精确等于内核草稿」写成本阶段的验收项。
- **缺口**：登记为 **G1-8**（见 §7.1）。
- **验收口径**：见 P3-5。

### S-13｜跨文件提交序：认领 × 快照（**不宣称事务**）

- **依据**：计划 §8 第 2 段「**禁止依靠两个独立文件各自原子写就宣称事务完成**」。
- **现状（PM 一手核过）**：**部分满足**。
  - 认领文件（`host/seq-store.js:148-161`，`wx` 排他创建、`mode: 0o600`）与
    快照文件（`host/index.js:348`，`wx` 排他创建、`mode: 0o600`）是**两个独立文件**。
  - **次序**：认领先落（catalog 阶段）、快照后落（capture 阶段）
    ⇒ 崩在中间 ⇒ 留下**「有认领、无快照」的孤儿认领**。
  - **兜底已有**：`host/sweep.js:297-301` 删认领前**必须确认对应快照已不在**。
  - **但**：认领被删后，**该 `seq` 可被二次分配**（`host/seq-store.js:141-143` 从
    `claimedSeqs` 的空缺里取号）⇒ **7 天后同一个 `snapshotId` 可能指向另一份内容**
    ——这是 C1 缺口，**第一批只登记、不解决**（见 §6）。
- **裁定**：
  1. **不宣称跨文件事务**。本稿**不引入**两阶段提交日志、**不引入**回滚。
  2. **可恢复的顺序**＝**单向偏序**：「认领在先、快照在后」；孤儿认领**可被回收**；
     **回收后不因此产生半条记录**（快照本就不存在）。
  3. **不得**出现「两个文件各自原子写 ⇒ 宣布完成」的表述与实现；
     **「这条引用已保存」的唯一依据是快照最终名存在**（S-9）。
- **验收口径**：见 P3-6。

### S-14｜存储保护与落盘策略（**成文**）

- **依据**：计划 §8 第 5 段「存储保护先评估已有私有原子写与平台存储能力。Unix 私有权限与
  Windows 当前用户保护**分别验证**，**不把 `0600` 或已有凭据 vault（加密存储）自动等同于完整跨平台加密**。
  **落盘策略写进 P0/P1 决策记录**，日志与诊断包不收正文。」
- **现状（PM 一手核过）**：
  - **Unix 侧已有私有权限**：快照目录 `0o700`（`host/index.js:344`）、快照文件 `0o600`
    （`host/index.js:348`）、认领目录 `0o700`（`host/seq-store.js:139`）、认领文件 `0o600`
    （`host/seq-store.js:160`）。
  - **但目录缓存没有**：`host/commands.js:98` 的 `mkdirSync(rootDir, { recursive: true })`
    **无 mode**（⇒ 0755）；`host/commands.js:100-104` 的 `writeFileSync(path, …, 'utf8')`
    **无 mode**（⇒ 0666 & ~umask）。
  - **Windows 侧**：`mode` 参数在 Windows 上**是 no-op**（Node 语义）。
    仓库里 Rust 侧的权限代码是 `#[cfg(unix)]` 专属
    （`src-tauri/src/shell/atomic_write.rs:185-197`），其自述「Windows 上是 no-op：
    用户 profile 下的默认 ACL 即用户私有」（同文件 `:101-102`）；
    **全仓无任何 DACL/ACL 代码**。⇒ **Windows 侧的「当前用户保护」= 依赖用户 profile 的默认 ACL**，
    **不是**插件自己施加的 ACL。
  - **日志不收正文**：**已满足**——错误日志只写 `at`/`code`/`requestId`/`detail` 四字段
    （`host/commands.js:234-252`，**逐字核过**，无 `body`/`messages` 字段）；
    sweep 日志只写**相对路径**（`host/sweep.js:201-209` 的 `labelOf`）；
    客户端探针（`client/client.js:475-486` 的 `record`）记的是**元数据**
    （`ref`/`sessionId`/`query`/`code`/`delayMs`/`message`/`why` 之类），
    **不含正文**（事件里没有 `messages`/`body` 字段）。
    **这一条要在判据里有钉子防回退**。
  - **落盘策略未成文**：`docs/features/official-chat/` 全目录**搜不到** `0600`/`0o600`/`加密`/`vault`/
    `落盘策略` 的决策条目 ⇒ 计划 §8 第 5 段要求的「落盘策略写进 P0/P1 决策记录」**未落实**。
- **裁定**：
  1. **落盘策略条目**（本节即为该条目的正文；另在 P1 §4.1 后加指针，不复制正文）：
     - 快照与占用记录：Unix `0600`/目录 `0700`；**Windows 不声称加密**，依赖用户 profile 默认 ACL。
     - 目录缓存：**补齐** `0600`/`0700`（本批做）。
     - **不声称跨平台加密**；**不**把 `0600` 等同于「加密存储」。
     - **日志与诊断包不收正文**（已满足，钉住）。
  2. **Unix 私有权限 与 Windows 当前用户保护 分别验证**：本批**只做 Unix 侧的可机检断言**
     （mode 参数存在且正确）；**Windows 侧本批只做「如实记录」**——
     断言「插件不依赖 mode 做安全承诺」＋ 在协议里写明 Windows 的实际保护来源。
     **不做**跨平台加密实现（不在本阶段范围，理由：需求未立、且计划明确不把 `0600` 当加密）。
- **验收口径**：见 P3-7、P3-8。

### S-15｜账户维度：**服务端推导**，客户端不构成授权

- **依据**：P1 §5「服务端从**已绑定实例、壳模式、实际站点账户**推导命名空间；
  **客户端传入的会话标识用于一致性校验，不构成授权**」＋ 计划 §8 第 1 段「按壳模式、内核族、实例、
  **站点账户**隔离」。
- **现状（PM 一手核过）**：**不满足**。
  - 目录缓存的账户键 = `String(request.accountScope ?? accountScope)`
    （`host/commands.js:412`）⇒ **客户端可传** ⇒ 客户端可以换一个 `accountScope`
    去读/写**别的账户的缓存**。
  - 快照里的 `accountScope` **字段**同样是 `request.accountScope ?? accountScope`
    （`host/commands.js:489` → `:577`）⇒ **客户端可写**。
  - **真正被服务端强制的只有 `sourceFingerprint`**：`fingerprintOf(accountScope)` 用的是
    **闭包里的服务端变量**（`host/commands.js:528`/`:635`/`:699`）⇒ 换账户后指纹不符 ⇒ 拒
    （P1 S-5）。
  - ⇒ **现状是「内容层强制、键与路径层不强制」**。这与 P1 §5 的原文**冲突** ⇒
    按本项目既有纪律「协议/判据冲突默认是实现漏做」，**实现要改，不是协议要改**。
- **裁定**：
  1. **账户维度由服务端推导**：`accountScope` **不得**取自请求参数。
     客户端传的账户标识**只做一致性校验**（不一致 ⇒ `account_changed`），**不构成授权**。
  2. **目录缓存的键**：改用**服务端推导**的账户维度。
  3. **快照的 `accountScope` 字段**：写**服务端推导值**。
  4. **客户端传了不同值怎么办**：**不静默改写**——按 `account_changed` 拒，
     或按 P1 §5 的「一致性校验」语义明确「以服务端为准、客户端值不符即拒」。
     ⇒ **本稿裁定为「不符即拒」**（理由：静默改写会让用户以为切了账户其实没切）。
  5. **不建新的隔离层**：路径仍是 `<root>/snapshots/<provider>/<id>.json`——
     **账户隔离靠服务端推导的键 ＋ 指纹校验**，**不**把账户塞进目录层级
     （理由：账户可含非法文件名字符；且 P1 §5 的路径写法已冻结，不在本批改动范围）。
     ⇒ **本批只修「键的来源」，不动路径形状**——这与 P1 §5 的路径写法**不冲突**。
- **验收口径**：见 P3-9。

## 5. 验收判据（tester 依此写）

> **通用纪律**（沿用 P1/P2）：期望值**独立算**；「数字对」≠「扫的是这几个文件」；
> 红字要**分层**且能**按处豁免**；共享 helper 里**不许出现两套逻辑**；
> **子串包含会造成假绿** ⇒ 不得用「含某串」当唯一断言。

| 编号 | 条款 | 断言（可机检的**性质**，不断实现形态） |
| --- | --- | --- |
| **P3-1** | S-8 ＋ S-9 | ① **半条记录不得发布**：模拟「写到一半进程死掉」（注入一个在写正文时抛错的钩子），<br>断言**快照目录的最终名清单里没有该 id**；<br>② **发布点**：`rename` 之前，最终名**不存在**；`rename` 之后，存在**且摘要校验通过**；<br>③ **回读校验**：发布出去的快照，其盘上 `contentDigest` ＝ 重新计算值（**读回**得到，不是内存里的值）。<br>⚠️ 断**性质**（清单里有几个最终名、有几个临时名），**不断**实现里用了哪个原子写原语。 |
| **P3-2** | S-8 | **写后回读**：断言「发布前**发生过一次回读**」——可用「故意把写入内容改坏 ⇒ 发布被拒且最终名不存在」反证。 |
| **P3-3** | S-10 | ① **第五家族被清**：造一个符合临时名形态的残留文件 ⇒ 跑一次清理 ⇒ **它被删**；<br>② **不该删的不删**：造一个**不是**临时名形态的文件（以及一个在阈值内的临时文件）⇒ **不被删**；<br>③ **越界不发生**：清理后的**根目录外**文件**必须还在**（用根外的哨兵文件反证）；<br>④ **失败只记日志**：让删除失败 ⇒ 断言**有留痕**且**不抛异常**、**不拖垮整轮**（P1 §4.1 第 3 条的四可观测条件）。 |
| **P3-4** | S-11 | ① **占用记录落盘**：`capture` 成功 ⇒ `<root>/refs/<snapshotId>.json` **存在**，且**只含**四个字段（`snapshotId`/`capturedAt`/`createdAt`/`sessionId`）、**不含正文**；<br>② **发布顺序**：占用记录的写入**不早于**快照发布（快照不存在时不应有占用记录）。 |
| **P3-5** | S-11 ＋ S-12 | ① **被占用的快照不被回收**：造一份「未过期 ＋ 有占用记录」的快照 ⇒ 跑回收 ⇒ **它还在**；<br>② **无占用的照常回收**：无占用记录且过期 ⇒ 被删；<br>③ **先重建、后回收**：断言**次序**——占用记录的全量扫描**发生在**任何快照删除**之前（可断「扫描调用点行号 < 删除调用点行号」**或**用探针记录调用顺序，**不得**只断「最后结果」）；<br>④ **R3**：占用记录**写坏** ⇒ 快照**不被删**（按被占着处理）。 |
| **P3-6** | S-13 | ① **孤儿认领可回收**：认领在、快照不在 ⇒ 回收后**认领被删**；<br>② **快照还在 ⇒ 认领不被删**；<br>③ **不得宣称事务**：断言**不存在**「两个文件各自原子写就宣布完成」的路径（可断：快照最终名不存在时，**不得**有任何「已保存」对外结果）。 |
| **P3-7** | S-14 | ① **Unix 私有权限**：目录缓存文件 `0600`、目录 `0700`（快照/认领已有 ⇒ 防回退）；<br>② **日志不收正文**：错误日志/诊断包**不含**正文与 `messages`（**钉住现有行为**，防回退）；<br>③ **不假装加密**：**不得**出现「已加密」类表述或把 `0600` 当加密的注释（可断措辞）。 |
| **P3-8** | S-14 | **落盘策略成文**：本协议 §S-14 存在**可被检索到的**条目（标题/锚点命中），且**P1 协议里有指向它的指针** ⇒ 「策略写进决策记录」这条**可机检**（不是靠人肉读）。 |
| **P3-9** | S-15 | ① **账户键不得取自请求参数**：用**两个不同的** `request.accountScope` 调同一命令 ⇒ 落盘的 `accountScope` 字段**相同**（＝服务端推导值）；<br>② **目录缓存键同理**：不同请求参数 ⇒ **不落到不同缓存文件**；<br>③ **不符即拒**：客户端传的服务端推导值**不符**时 ⇒ 拒（`account_changed`），**不静默改写**。 |

**「无法判定 / 不可达」的项**（**不得**写成假断言）：
- **chip `invalid` 态**（P1 G1-6）——内核无写入口，本批**不涉及**。
- **引用被内核移除后的即时释放**（G1-8）——内核契约无信号，**按 S-12 的降级口径**验收
  （误删 ⇒ 拒发 ＋ 可见错误，**不是错发**），**不**断言「立刻释放」。
- **Windows ACL**——本批**只做如实记录**，**不做**跨平台加密断言。
