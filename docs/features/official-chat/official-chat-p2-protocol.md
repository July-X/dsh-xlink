# P2 协议：重复识别 ＋ 可见提示 ＋ 预算预检（v0.6）

上游依据：[调研载体](official-chat-p2-research.md)（结论与依据）＋ [P1 协议](official-chat-p1-protocol.md)（数据模型、13 码闭集、首版常量、命名空间）＋ [development-plan](official-chat-development-plan.md) §7（引用展开）§8（快照与回收）。

**本稿只覆盖 P2 第一批**（izzy 22:5x 点头立项时采用的建议三条）。**明确不做**的见 §6。

## 0. 一句话

P2 第一批 = **识别「同一段正文被引用多次」→ 告诉用户 → 在超预算前提醒**；**不合并、不删 chip、不改 id、不改消息**。

## 1. 重复组

### 1.1 键

重复组的判定键 = **(accountScope, sessionId, branch, capturedAt, contentDigest) 全等**。

- 五字段**任一不同 ⇒ 不是同一组**。
- `capturedAt` 不同 ⇒ 不合并（哪怕正文逐字节相同）——两次不同的捕获事实。
- 跨会话 / 跨账号 / 跨分支 ⇒ 不成组。
- **依据**：development-plan §8 `:168`「去重不能抹掉账户、分支或捕获事实」；内核同生态先例（`dsh-agent-instructions/README.zh.md` SHA `C31D31C892F81B53F0BB7AF409289C3868321D80B939EE7568D552B6A83088CD` `:222`）也是「**同一组 ＋ 字节完全一致才折叠**」——本稿沿用其严格方向。

### 1.2 组标识

`groupKey` = `sha256(五字段按 §1.1 顺序用**单个换行 U+000A**连接)` 的**前 16 位小写十六进制**。

- **（PM 23:5x 裁定 · 分隔符口径写死）**：分隔符 = **单个换行（U+000A）、不含空格**（JS `join('\n')` / Rust `join("\n")`，**两端现状即此**）。⚠️ 本稿早前版本把它写成行内代码 `sha256(accountScope \n sessionId \n …)`，**`\n` 两侧的空格只是 Markdown 的换行写法、不是分隔符的一部分** —— 现已改写，消除误读。
  - **若将来要改这个分隔符**（例如改成含空格），**必须同次改四处**：JS 的 `groupKeyOf` 1 行、Rust 的 `group_key` 1 行、两个夹具的 `expected.groupKey`（各 1 个值）⇒ 漏改任何一处，「两端逐字段相等」判据都会报红。
- 用途：client 侧把同组引用聚在一起并给稳定标识（用于提示文案与判据比对）。
- **不用于授权**：client 提交的 `snapshotId` 仍由 host 逐个核对（照 P1 `capture`/`preview` 的核对口径），**不因同组而免核对**。

### 1.3 组内成员

每个成员 = `{ snapshotId, capturedAt, contentDigest }`。**成员不合并**——组只是「这几条是同一份」的**事实分组**，不是「它们可以互换」。

## 2. 通道与命令

### 2.1 通道

与 P1 相同：host 命令层，经内核 `connection` 服务的 **exact fetch route**（`/api/xlink-official-chat`，POST，buffered）——**不得**把 `rpc.handle` 当作已通（缺口 G1-7）。

### 2.2 命令：`duplicates`

- **入参**：`{ sessionId, snapshotIds }`——`snapshotIds` = **client 传入当前草稿里已选中的引用 id 列表**（由 client 掌握草稿状态；host **不猜**草稿）。
- **出参**（成功）：

```
{
  ok: true,
  groups: [
    { groupKey, members: [ { snapshotId, capturedAt, contentDigest } ], redundantBytes }
  ],
  budget: { limitBytes, projectedBytes, wouldExceed, exceedByBytes }
}
```

  - `redundantBytes` = `(members.length - 1) × 单条正文字节`（该组若只送一份能省下的字节数；**只是数字，不真的省**）。
    - ⚠️ **`redundantBytes` 可能是 0**（PM 2026-10-21 01:0x 实测）：**捕获路径不拒空正文**（`host/protocol.js` 的 `resolveCaptureCase` 对空文本返回 `kind:'snapshot'`，0 字节快照可落盘）⇒ 同组两条若是 0 字节快照，**R = (members.length−1)×0 = 0 是可达的** ⇒ **写文案或改实现时不得依赖「R 必 > 0」**（`host/commands.js:742`）。**但这不构成措辞禁令**（PM 01:1x 更正）：R=0 时「省得下/可省 0 字节」**字面为真**（两条都空 ⇒ 少送一份确实省 0 字节）⇒ **不构成错误陈述** ⇒ 措辞按 §3.2 的「省得下/超了多少字节」口径与 **UX 定稿原文**执行（见 §3.2 的「措辞口径（PM 01:1x 更正）」）。**本条只澄清事实，不改 `redundantBytes` 的定义**。
  - **（PM 23:5x 裁定）`groups` 只返回成员数 ≥ 2 的组**——**单成员组不是重复组**，不出现（否则 client 要自己过滤，且「有没有重复」这个事实会被稀释）。
  - `budget.limitBytes` = 单次消息总预算 **262144**（P1 §4 常量）。
  - `budget.projectedBytes` = 本条消息的正文总字节（**按引用次数各送一份**计，与 P1 S-7 一致）。
  - `budget.wouldExceed` = `projectedBytes > limitBytes`；`exceedByBytes` = 超出量（未超则为 0）。
- **出参**（失败）：沿用 P1 §3 的 **13 码闭集**与错误结果对象闭集（字段集以 **P1 §3 `:161`** 为准，**本稿不复述字段个数** —— **该 8 字段闭集的两端同构已于 2026-10-21 00:1x 闭环（缺口 G-2 已销号，见 §9）**：JS `errorPayload` 的正常分支与未知码归一分支**都**产 8 个字段（含 `kind`），与 Rust `error_result` 同构，两端各有一条自测钉住）。

### 2.3 失败口径

| 情形 | 对外码 | `detail` 必须带 |
| --- | --- | --- |
| 某个 `snapshotId` 不存在 / 已过期 / 摘要不符 | `snapshot_invalid` | 具体是哪个 id / 什么原因 |
| 当前指纹不可得或与快照不符 | `account_changed` | — |
| 盘上快照不可读 | `snapshot_invalid` | **原始码 `snapshot_store_unavailable`** |
| 入参形态不对（`sessionId` 缺失、`snapshotIds` 非数组） | `snapshot_invalid` | **原始码 `invalid_request`** |

- **不新增错误码**（13 码是闭集）。
- **（PM 23:5x 裁定 · 两个码不在闭集里怎么办）**：`invalid_request` 与 `snapshot_store_unavailable` **都不在 P1 §3 的 13 码闭集内**（闭集见 P1 §3 `:144-158`），而 §6.5 又明写「不新增码」⇒ **按 P1 §3 `:167` 的既有规则处理**（**不是本稿新发明**；行号于 2026-10-21 00:4x 当场核正——原写 `:166` 指的是相邻的 `catalog_empty`/`catalog_failed` 那条）：**内部冲突码一律归入 `snapshot_invalid`，原始码保留在 `detail`**，**不新增第 14 个码**。
  - **实现现状**：devloper 23:0x 已按此实现（归 `snapshot_invalid` ＋ 原码进 `detail`）⇒ **PM 认可，无需改代码**。
  - **判据必须加严**：P2-6 须**断 `detail` 里带原始码**（`invalid_request` / `snapshot_store_unavailable`）——否则「归一」会把「入参形态错」与「快照过期」压成**不可区分**的一坨 ⇒ **假绿**。

- **`duplicates` 失败不得阻塞发送**：失败 ⇒ 提示「无法核对重复」＋ 可见错误，**不额外拦截发送**（P1 的发送语义不变）。
- ⚠️ **措辞纪律（PM 23:1x 收敛）**：本条说的是「**不额外拦截**」，**不是**「保证一定发出去」**——正文能否真发出由 **P1 S-5 / S-6** 判定（快照失效时内核会拒发，那是 P1 的语义，不是 P2 的）。⇒ **界面文案不得写「已发送」「发送失败」「发送被阻止」**；失败文案只说「无法核对是否重复」。

## 3. 可见提示（**硬要求**，界面形态由 UX 出手）

### 3.1 什么时候必须出现

1. **重复发生时**：用户**选中第二个及以后的同组引用**时（即同组成员数 ≥ 2）⇒ 立即出现提示。
2. **发送前**：若 `budget.wouldExceed` ⇒ 出现预算提示。

- **（PM 00:0x 裁定 · 内核 notice 单槽 ⇒ 「两个触发点各自独立」的真实含义）**：内核 notice 是**单槽**（§3.2 已引证：全树 `notices.set` 只有 `:15356` / `:15448` 两处，**最新一条覆盖旧条**）⇒ 当「重复」与「超预算」**同时成立**时，**用户最终只能看到最后那一条**（预算那条在后）。
  - ⇒ 「两个触发点各自独立」的**准确含义**是「**两条都要发**（任一条都不得被 early return 吃掉）」，**不是**「用户同时看到两条」。
  - ⇒ 由此得一条**硬要求**：**后发那条必须把先发那条的事实也带上**（组条数 ＋ 重复字节 ＋ 预算字节 ＋ 超限字节）⇒ 否则「重复」这个事实会被覆盖丢失。**实现现状已满足**（devloper 00:0x：两条文案都自包含）⇒ **PM 认可，无需改代码**。
  - ⇒ **不得**把「用户会同时看到两条提示」写进任何文案、验收描述或 UX 方案。
  - ⇒ **呈现形态已定（PM 01:0x 依 UX 定稿锁定）**：**两条、两个 kind** —— `duplicate-groups`（有成组时）＋ `budget-exceeded`（超限时），**任一条都不得被 early return 吃掉**，且**各自自包含全部事实**（后发那条必须把先发那条的事实也带上）。**为什么不是「合成一条」**：UX 原建议合成（理由＝在「后发那条自包含全部事实」这条锁下，两条内容必然相同 ⇒ 合成是去重而非取舍），但**核已合并的判据后自行撤回** —— 判据 P2-5 场景②**硬断两个 kind 都必须出现**（`scripts/lib/p2-protocol.mjs` 里 `waitForNotice(adapter, 'duplicate-groups', …)` 与 `waitForNotice(adapter, 'budget-exceeded', …)` 各要一条，缺任一即 FAIL）⇒ **合成一条会打红已合并判据** ⇒ 形态锁死为两条。

### 3.2 提示必须满足的约束

- **可见**：用户能看见（不接受「只写进日志」「只记进 console」）。
- **承载位 = 输入区（composer）的常驻提示条**——**P2 阶段唯一可得的承载位**。依据（现役内核 release 树 `0.2.1-rc.2`，`dsh-client-ui-conversation/lib/client.js` SHA `8554738CBEEB5218AD1BFA4773EF094363B066D052A1893D7A96797C5BC33A63`）：
  - `:18982-18986`：**只有 `notice.level === "info"` 才渲染 inline 常驻条**（`div` + `role="status"`，位于 composer card 上方）；
  - `:18807-18809`：**独立的 `useEffect`** —— `if (notice?.level === "error") showToast(notice.text)` ⇒ **`error` 档不渲染 inline 常驻条、只额外弹一个瞬态 toast**；**只有 `info` 档渲染常驻条**。
  - ⇒ **本批所有提示必须用 `info` 档**（用 `error` 档会当场违反下面「不接受瞬态 toast」）。⚠️ **P1 现有实现用的是 `error` 档**（`plugins/official-chat/client/client.js` 的失败/不可用分支）⇒ **照抄 P1 写法会直接踩坑**。
  - ⇒ **「引用发生处」（chip 旁）在 P2 阶段技术上不存在**：内核无 chip 状态写入口（缺口 **G1-6** 已登记）⇒ **不得把它写成承载位**。
  - ⇒ 内核 notice 是**单槽**（全树 `notices.set` 只有 `:15356` / `:15448` 两处，**最新一条覆盖旧条**）⇒ **每条提示的文案必须自包含**（条数与字节数写在同一条里），不依赖另一条还在。
  - **（PM 00:1x 裁定 · 六 · 内核 notice 会「顶掉」我们，不是「叠放」）**：内核 `notices.set` 有**两个**入口 —— `:15356` 的 `notify(level, text)`（供 detached command results 与内部错误用）与 `:15448` 的 `execute(fx)` 的 `case "notice"`；且内核**多处**用 `notify("error", …)`（`:15193` / `:15197` / `:15204` / `:15905` / `:16932`）⇒ **内核随时可能发一条 error notice，把我们的 inline 条整个顶掉**（单槽，最新覆盖旧条）。
    - ⇒ **所以问题不是「toast 与 inline 条的叠放顺序」，而是「互相顶掉」**：内核那条 error notice 一来，用户看到的是**内核的 toast**，我们的 inline 条**消失**。
    - ⇒ **硬要求（承接 §3.1）**：① **文案自包含**（组条数 ＋ 重复字节 ＋ 预算字节 ＋ 超限字节）；② **不得依赖内核 toast 或内核 notice 的出现时机/顺序来表达我们的状态**；③ **不得**写「提示会一直在」这类假设。
    - ⇒ **可用性推论（§4 触发点选在「每次新增引用时预演」带来的意外收益）**：内核顶掉我们的提示**不会让信息永久丢失** —— **用户再动一次引用**（再选一条/再取消一次）就会**重新触发一轮核对、重新发出一条我们的提示** ⇒ 提示是**可复现的**，不依赖单次 notice 的存续。
    - ⇒ **呈现形态**：因「单槽 + 会被顶掉」，一次写入、整体被顶掉最省事 —— 但**形态已按 §3.1 锁死为「两条、两个 kind」**（判据硬断两个 kind 都在 ⇒ 合成会打红已合并判据）；「一次写入整体被顶掉」这个优点改由**两条各自自包含**来等价满足（用户最终看到的后发那条带全部事实 ⇒ 不会「只剩半个事实」）。
    - ⇒ **补充事实（渲染侧）**：`client.js:18807-18809` 是**独立的 `useEffect`**（`if (notice?.level === "error") showToast(notice.text)`），**不是**与 inline 条互斥的 if/else 分支 ⇒ 准确说法是「**`error` 档额外弹一个瞬态 toast；`info` 档只渲染 inline 常驻条**」⇒ **本批仍必须用 `info` 档**（要常驻条、不要瞬态 toast）。
- **可复查**：**不接受瞬态 toast**（瞬态会消失、判据易假红、用户来不及读）。
- **可操作但不必可消除**：提示要说清「同组有几条」「省得下/超了多少字节」；**不得**提供「一键合并」（本批不做合并）。

- **成品文案（UX 定稿，2026-10-21 · PM 已核）**——本稿**不锁措辞**，但**成品文案已定稿**；实现侧照抄下列原文，判据只断**数字在不在**（`checkSelfContainedText` 断 `members` 与 `redundant` 这两个数字**各自独立出现**、**不接受子串包含**（PM 01:3x 授权收紧：子串包含 ⇒ `members` 的数字串出现在 `redundant` 里时（例：`members=2`、`redundant=4216`）会误判「含条数」⇒ **假绿口子**；本稿定稿文案「数字一律不加千分位」⇒ 独立数字匹配可行）、**且必须落在该组的语境片段内**（单组＝「同组 N 条」、多组＝「第 i 组 N 条」）—— PM 01:4x 授权再收紧（UX 提出、PM 复核成立）：**只做全文匹配时，「组数恰好等于条数」会误命中**（例：2 组各 2 条 ⇒ 文案即便漏写「第 1 组 2 条」，全文里的「2 组重复」那个 2 也会被当成「含条数」⇒ **又一处假绿口子**）⇒ 判据须**在组语境片段内**匹配该组条数与该组 R）；P2-5 断 `projectedBytes` 与 `exceedByBytes` 的原值出现）⇒ **数字一律不加千分位**：
  - **两条逐字相同**（因「后发那条自包含全部事实」）：`本次核对：同组 3 条内容完全相同，重复可省 4216 字节；引用正文 268435 字节，超出单次消息预算 262144 字节（超 6291 字节）。`
  - **无重复组（纯预算场景，重复分句整段省略）**：`本次核对：引用正文 268435 字节，超出单次消息预算 262144 字节（超 6291 字节）。`
  - **未超限**：`本次核对：同组 3 条内容完全相同，重复可省 4216 字节；引用正文 120000 字节，未超出单次消息预算 262144 字节。`
  - **核对失败**（kind `duplicates-failed`）：`无法核对是否重复。`
  - **数字来源**：`同组 N 条` = **该组**的 `members.length`（**多组时逐组各说一句** —— 「同组 N 条内容完全相同」必须按**组**读才为真：**组内**内容相同、**组间**不同 ⇒ 逐组列时每句都为真，不产生不实陈述）；`重复可省 X 字节` = **该组**的 `redundantBytes`；`引用正文 Y 字节` = `projectedBytes`（**只含引用正文各送一份，不含用户在输入框里自己打的字** ⇒ 用「引用正文」**不用**「消息正文」）；`262144` = `limitBytes`；`超 Z 字节` = `exceedByBytes`。**（PM 01:2x 核正 · 文案口径与判据口径对齐）**：判据 `checkSelfContainedText` 收的 `members`/`redundant` 取自 **`groups[0]`**（`scripts/lib/p2-protocol.mjs:532-538`：`const group = groups[0]`、`members = group.members`、`redundant = group.redundantBytes`；`:594-597` 的复现轮同理）⇒ **逐组列天然含第一组那两个数 ⇒ 判据绿**（单组、多组皆然）⇒ **不需要另设「总数」口径，也不需要 UX 再补多组版本**。
  - **措辞口径（PM 01:1x 更正）**：**成品文案用 UX 定稿原文**（「重复可省 X 字节」＝§3.2 要求的「**省得下/超了多少字节**」口径）⇒ **不因 `redundantBytes` 可能为 0 而改措辞**（见 §2.2 的实测事实：R=0 时「可省 0 字节」**字面为真**——两条都空 ⇒ 少送一份确实省 0 字节 ⇒ **不构成错误陈述**）。**留痕**：01:0x–01:1x 间，PM 曾越界规定「不得用『可省』」并据此把 UX 定稿原文改成事实式「重复正文共 X 字节」（提交 `e3451f6`）⇒ **该规定与协议 §3.2 自身冲突、且措辞属界面层（UX 职责）⇒ 已撤回，本条与 §2.2 同款措辞条款一并改回**。
  - **多组形态（PM 01:3x 裁定 · UX 提出、PM 核判据后定）**：`groups` ≥ 2 时**必须逐组列**，且**先说组数、再逐组编号**：
    - **多组文案形态**（**UX 正式稿已确认** · 2026-10-21 01:5x：UX 核过协议 §3.2 ／ `client/client.js` 多组渲染 ／ `host/commands.js` 的 `groups.sort()` ／ 判据 P2-H **四处落地一致、无异议**）：`本次核对：2 组重复：第 1 组 3 条内容完全相同，重复可省 4216 字节；第 2 组 2 条内容完全相同，重复可省 2108 字节；引用正文 268435 字节，超出单次消息预算 262144 字节（超 6291 字节）。`
      - **为什么不用「同组 N 条」并排**（PM 01:2x 曾采信的一版，**已改**）：两个「同组」分句并排时，读者会本能地把它们归到**同一个**组上 ⇒ 读成「同一组既是 3 条又是 2 条」⇒ **表面矛盾**（不是假陈述，但是真实的可读性缺陷）⇒ 改为「N 组重复 ＋ 第 i 组」。
      - **为什么必须逐组、不能只给汇总**：文案若只给汇总（组数＋总条数＋各组 R 之和），**判据按任一组去断就会红**（那组的数字不在文案里）⇒ 逐组列 ⇒ 判据无论命中哪一组都绿（依据见上面「数字来源」末段：判据取 `groups[0]`）。
      - **单组时文案不变**（仍是 `本次核对：同组 N 条内容完全相同，重复可省 X 字节；引用正文 …`）⇒ **主场景不受影响**。
    - **组的顺序按 `groupKey` 升序**，且**落点在 host 侧**（PM 01:3x 更正落点）：`host/commands.js` 的 `duplicates` 命令产出 `groups` 时**按 `groupKey` 升序**后再下发（PM 01:2x 曾把落点写成 client 侧排序，**已更正** —— host 是产出处，排序在产出处做 ⇒ 任何消费方都拿到稳定顺序；client 侧只照单渲染）⇒ 理由：顺序抖动会让「后发那条」的内容不稳定 ⇒ 用户两次看到的文案可能不同。
    - **备查（本次不采纳）**：若将来要改事实式措辞，用「**重复多出 X 字节**」（UX 提出）—— **不要**用「重复正文共 X 字节」（**口径有歧义**：3 条各 2108 字节时全部重复正文是 6324 字节，而 R=4216 是「**除了一份之外多送出去的那部分**」）。
    - **措辞二选一的裁定（PM 02:0x · UX 提请在「A 版 / B 版」之间裁）—— 维持 A 版（零改动）**：
      - **A 版**（本节逐字原文「重复可省 X 字节」）**继续作为定稿**；**B 版**（「重复多出 X 字节」）**不是被否决**，而是**已留档的备查口径**（见上一条）⇒ **本批零改动**：本协议原文、`plugins/official-chat/client/client.js` 的模板、钉子测试**都不动**。
      - **裁的理由**：① **措辞属界面层（UX 职责）** —— PM 只裁「要不要改」，**不代选措辞**；A 版就是 UX 定稿原文、且 UX 已正式确认（01:5x 闭环）⇒ **无新证据就不动**。② **换 B 版收益不足**：A、B 两版在 **R=0 那一格都不是漂亮句子**（R=0 要两条快照正文都为空才触发；而 R=0 时「可省 0 字节」**字面为真** ⇒ **不构成错误陈述**，见 §2.2）⇒ 为一个极端边缘格重开措辞、还要动 4 处，**收益不抵**。③ **换 B 版对判定零影响**：判据只断**数字在不在**、**不判措辞** ⇒ 换与不换，判据结果完全一样。
      - **B 版的启用条件（写死，避免再翻第三轮）**：仅当出现**「A 版措辞被读成已承诺动作」的实际证据**时启用 —— 例如用户/客服反馈把「可省」理解成「系统已自动合并」；或将来 izzy 拍板做**消息级合并**（S-7 撤除）⇒ 那时「可省」会变成真正的动作承诺，再切事实式。**在此之前一律维持 A 版。**
      - **留痕**：本条**取代** 01:0x–01:1x 那次越界的措辞规定（已撤回），并**封住第三轮措辞讨论**；本批措辞以本节 A 版原文为准。**（另：「重复正文共 X 字节」已被上一条明确排除，不要再用。）**
  - **「本次核对：」是抗 stale 的锚**：条会被内核顶掉、且撤不掉 ⇒ 文案**不得**写成「当前状态」的断言（用「本次核对」不用「现在」）。
  - **零新增控件**：内核 inline 条是纯文本 `div`（`role="status"`）⇒ **不可关闭、不可点击、不展开同组明细**（属 P5）、**不提供「一键合并」**（§3.3）；用户的动作全在既有控件上（删 chip、不点发送键）。
  - **空态**：无重复组且不超预算 ⇒ **不出现任何提示**（不写「一切正常」——那会擦掉上一条有价值的信息，且是纯噪音）；P2 **不引入**任何新的空态 UI（无徽标、无角标、无计数、无占位）。
  - **错误态**：失败提示**仍是 `info` 档常驻条**（不弹瞬态 toast）、**不阻塞发送**、文案**不含**「已发送 / 发送失败 / 发送被阻止」（判据 `forbidden` 三词）；错误码在 13 码闭集内、原始码**只进 `detail`** ⇒ **界面不显示任何码、不分档**。

## 4. 预算预检

- 触发点：**每次新增引用时预演一次**（**PM 23:5x 裁定 · 与实现的落点对齐**：内核**无「提交前草稿投影」入口** ⇒ 「发送前」在实现上等价于「**最后一次新增引用时的快照**」；与正文展开同一次 host 往返里算，**不额外起一趟**）。
- 口径：`projectedBytes` = 本条消息**各引用各送一份**的总字节（P1 S-7 口径）＋ 原生 `@session` 占用。
  - **（PM 23:5x 裁定）原生 `@session` 占用当前不可观测 ⇒ 按 0 计** ⇒ `projectedBytes` **偏小** ⇒ 方向是 **「宁可少报、不误报」**（与 P2 的「偏向宁可漏」一致：错合并比漏去重好）。
  - **少报的后果要说清**：真超限时用户仍会收到 P1 的 **`body_too_large` 可见错误**（P1 §4 常量 262144 字节）⇒ **预检是「提前告知」，不是「最后一道闸」**，**不得**写成「保证发得出去」。
- 超限时：**给可见提示 ＋ 不截断**；由用户自己决定删哪条引用。
