# official-chat 后续开发执行指南

本轮目标：先让 Windows 上 DeepSeek 的「工作台输入 @ → 选择官网会话 → 读取固定正文 → 与新问题一起发送」可靠成立，再验 MiniMax、ChatGPT。必须同时守住账户隔离、固定快照、失败拒绝发送和用户草稿保留。

本文件给接手的 agent 确定工作范围，不授权修改生产环境、使用未经许可的真实会话、推送、发布或清理用户数据。只收到“阅读、评审、写文档”任务时，不执行这里的实现任务。

## 1. 先读什么，按什么做决定

1. 仓库根 [AGENTS.md](../../../AGENTS.md)。修改 Rust 前读 [src-tauri/AGENTS.md](../../../src-tauri/AGENTS.md)，修改管理面板前读 [ui/AGENTS.md](../../../ui/AGENTS.md)。
2. [当前实现与剩余任务](official-chat-current-status.md)，再读[开发计划](official-chat-development-plan.md)：区分已交付、待验收与未实现内容。
3. [P1 协议](official-chat-p1-protocol.md)、[P2 协议](official-chat-p2-protocol.md)、[P3 协议](official-chat-p3-protocol.md)、[P4 协议](official-chat-p4-protocol.md)：理解当前实际生效的契约及已批准的降级。
4. 本文件的任务卡和验收矩阵。
5. [进度记录](official-chat-progress.md)的最新相关记录，以及当前源码、调用方和测试。

用户当前指令优先。执行时要核对协议版本、后续裁定与仓库约束，不能机械套用旧计划。若同一事项的现行约束仍相互矛盾，写明冲突条款及影响，提出需要裁定的那个具体问题；继续完成不依赖该裁定的工作。

历史调研、旧总表和旧行号只用于追溯，不能覆盖后续明确裁定。代码也不能反过来证明协议已经兑现。发现实现偏离时，先修实现；需要改变既定产品行为或协议时，先得到对应裁定，再同步契约、实现和判据。

常用术语：host 指内核进程中的插件服务端；client 指工作台网页中的插件客户端；CDP（Chrome 开发者工具协议）是壳内取数通路；IPC（进程间通信）是窗口与壳通信；API（应用程序接口）指站点或壳的接口；TTL（缓存有效期）控制缓存保鲜；profile 指浏览器档案；origin 指由协议、主机和端口组成的来源。

## 2. 当前基线：不要重复开发，也不要提前报完成

2026-10-23 发布基线为 `53bee298`（v0.5.9），包含 `e9b5806e`、`de2b66f1` 的修复及 macOS 编译补漏。接手时先读 `git log`、`git status` 和实际差异。此前的 `24145a9c`、`3aa7f92f`、`fac0a09e` 均是历史基线。当前 P1 为 v0.16，P4 为 v0.28；以后接手仍需重新核对协议版本。

本轮修复覆盖：

| 范围 | 实现与验证要求 |
| --- | --- |
| Windows 编译与静态检查 | 正文探针调用同步 `capture_in` 参数和 `PageRoute` 类型；平台专用代码按实际使用范围编译 |
| 序号分配 | 水位的读、取最大值、发布在同一跨进程互斥范围内；Windows 文件占用时有限重试。四个写进程加并发读者检查不重复、不倒退、无半截记录 |
| 固定正文 | `.body.txt` 必须逐字节等于已校验快照的正文；缺失或损坏时重建，重建失败不返回不可信文件路径 |
| MiniMax 页内旁听 | 目录与正文均从规格表传入选择规则；正文跳过带 `before` 的历史分页；fetch 与 XHR 两条路径都要恢复原钩子 |
| 协议适配器 | 真实执行顶层选站、进入站路径、选会话；夹具目录变化时同步失效自己的缓存；不能自造引用绕过客户端 |
| 正文发送判据 | 文件引入时沿模型输入中实际给出的路径读取正文，再与快照比较；不能拿文件指针文案直接比正文，也不能只读预期文件却不检查指针 |
| 残留清理 | 覆盖正文临时文件及删除中间文件；快照未能改名时保留配套正文；保持文件形态、目录和过期阈值限制 |
| 等待与错误分类 | 插件等待 180 秒，壳内取数总预算 170 秒；重试前重新确认页面就绪；明确缺少登录态时使用已有 `not_logged_in` 分类 |
| 源码判据 | 排除测试块，分别检查 Windows/macOS；识别超时包装函数后的真实调用链；坏读数文件必须产出明确结果 |

序号互斥目录为 `seq-watermark.lock`，其中的 `owner` 记录进程号。异常退出留下锁时采取拒绝分配策略，不按时间猜测锁已过期；只有确认相关分配进程均已退出后，才可清理那一个残留锁。不得自动删除水位、认领文件或整个会话目录来恢复。

早期分轮读数仅保留为历史证据。发布前已在最终提交运行 `pnpm run check`，Rust 测试 1184 通过、12 忽略；Windows 与 Intel macOS 发布构建及持续集成通过，见[当前状态](official-chat-current-status.md)。后续修改运行受影响检查，不能将发布门禁当作新代码的验收证据。

以下边界没有因本轮修复而完成验收：真实站点账户切换隔离、macOS 上的完整取数、Windows 工作台的选取到发送操作、安装版与开发版并行运行。不得把离线脚本或模拟页面中的通过写成这些场景已通过。

已有工作区改动仍需保留：

- `src-tauri/examples/official_chat_shape_probe.rs`
- `src-tauri/examples/support/profile_copy.rs`

两份文件不属于本轮修复，不得覆盖、统一格式化或夹带提交。冷档案生命周期修复已在本轮之前落库，继续补验收，勿重复改写。

## 3. 不许改掉的产品边界

### 3.1 主流程与数据

- 用户直接在工作台 @ 菜单里选官网会话，不增加前置导入、复制、强制预览或逐次确认。
- 候选查询只读目录元数据。未选中的会话不得读取正文；悬停、键盘移动和搜索不得触发正文批量抓取。
- 选中后创建固定版本快照。发送和重试从该快照读取，不重新向官网取“最新正文”。
- ref 与 snapshotId 保持同一标识。id 由 host 分配，不让客户端自造，也不因本轮修复变更现有格式。
- 落盘正文、摘要规范化口径保持稳定。模型输入首尾允许各一个换行分隔符，不能把分隔符塞进落盘正文来迁就发送路径。
- 待读取时发送必须等待或拒绝；读取失败、快照丢失、摘要不符时不得漏掉引用继续外发。保留草稿并给出可见错误。
- 正文进入目标用户消息。不得改成系统提示注入，不借修复增加自动合并、后台同步或新的记忆功能。
- 固定快照继续保持原来源归属。换账户后不得把旧快照改挂新账户，也不得通过删除全部快照实现隔离。

### 3.2 取数与权限

- 不修改已安装的内核，不改上游内核或任何 fork，不提上游修改请求，不把“等上游修复”当收口路径。
- client → host 继续走内核 connection 服务的 exact fetch route（精确路径请求路由）；host → 壳复用现役回环桥。不新增监听器，不改回不可用的 rpc.handle。
- 取数按 P4 v0.28 的平台形态执行：Windows 使用壳内 CDP 订阅自然请求；macOS 的形态 B 在页内同源取数，MiniMax 使用形态 C 旁听并恢复原钩子。凭据只在页面内使用，不回传、不记录；不能把 Windows 的页内零动作规则直接套到另两种形态。
- 桥只接受登记过的命令和受约束参数，不接受任意脚本、路径、网址或客户端指定的账户目录。
- P1 当前为 14 个稳定错误码。内部错误按既有分类映射；本轮不自行增加第 15 个码。
- 白名单以当前 P4 为准：目录项有 6 个基础键，deepLink 是已批准的可选第 7 键。不要把“不得增加新的站点专用字段”误写成“deepLink 也被禁止”。
- 冷档案可以按既有规则做字节级副本；不能解析、回传或记录其中的凭据。必须保留清理机制和清理失败记录，不能宣称“从未落盘”。
- 认证弹窗留在壳内并继承发起方档案。网页登录不使用本机 Codex 凭据代替；本机 Codex 的读取许可仍只服务既定额度功能。

### 3.3 已裁定的站点行为

| 项目 | DeepSeek | MiniMax | ChatGPT |
| --- | --- | --- | --- |
| 目录档案 | 生产档案 | 生产档案 | 生产档案 |
| Windows 正文档案 | 冷档案 | 冷档案 | 生产档案 |
| 正文请求锁定 | query 中的 chat_session_id | 路径中的会话段 | 路径中的会话段 |
| 正文多候选选择 | 响应时刻最大 | before 缺席的候选 | num_turns 更大，相同再比响应时刻 |
| 目录特殊选择 | 当前规格 | 当前规格 | 只取不带 conversation_origin 的候选 |

macOS 继续使用壳内专属 WKWebsiteDataStore，不使用 Windows 冷档案副本。三站共用规格表及取数链，不复制三套流程。目录按更新时间数值降序稳定排序，最多 6 条；sessionsLength 是站点原始条数，不能说成“用户全部历史数”。

目录保鲜、查询去抖、候选组重开判定分别遵循 P1 常量和 P4 §4.6。站点缓存已分键，不得重新添加“切站一定强刷”来掩盖缓存错误。

完整性未知时只说“已取到”，不声称“全部”或猜测“一部分”。已知省略必须按实际 omitted 事实展示；站点给出 has_more 时按事实处理，不靠消息数量推断取全。

## 4. 开工前固定动作

在仓库根运行以下只读检查，记录当次基线：

    git rev-parse HEAD
    git status --short
    git diff --stat

确认是否存在 .codegraph；有索引先查 CodeGraph，没有则使用 rg，不自行建立索引。对将改的函数查全调用方、测试、夹具、资源登记和协议约束，先列本任务涉及的文件。

一次只领取一个边界明确的任务。需要协作时先确定文件归属，尤其 client.js、commands.js、site-source.js、session_structure.rs 和协议文件；不能两人同时改同一块再让第三人盲目解决冲突。本文不要求自动创建子 agent。

实际改动不再需要时，停止改代码，转验收。发现已有修复要验证其覆盖面，不能为了保留自己的任务重新写一份。

## 5. 任务卡与执行顺序

T1 生命周期回归和 T3 账户接线已在本轮工作区补齐；T2 已落库。当前剩余重点是 T4 的真实站点操作、T5 的原生交付验证，以及[当前状态](official-chat-current-status.md)中保留的明确边界。不要重复实现已接通的链路。

⚠️ **跑 T4／T5 之前先备好两个前提**：① **认准壳的身份**（dev 壳与安装版 release 壳可以同时在跑，两者随包插件资源不同，见 §7.2）② **桥要活着** —— 取证的「目录命令实机一次」需要连上现役回环桥；没有活桥时那一格按「**未执行**」如实报，**不许拿副本读数冒充实机读数**。

### T1：冷档案生命周期 —— 实现与资源守卫回归已补，原生句柄释放待验

目标：DeepSeek、MiniMax 的冷档案从建窗前一直存活到读取结束和自建取数窗口释放，成功、失败都能清理自己的副本。

**原缺陷**：先前 `capture_for` 用消费型 `Option::map` 只取出路径，资源守卫提前释放，副本在建窗前被删。当前把路径与守卫一起交给 `with_capture_profile`，直到读取任务退出才释放；这里消费 `Option` 后仍持有守卫，不能机械地把所有 `map` 都认成同一个错误。


生产路径现在通过 `with_capture_profile` 持有“路径与资源守卫”，直到读取任务退出才释放。`body_capture_profile_survives_window_and_cleans_on_success_and_failure` 使用真实 `ColdProfile` 和该生产包装函数，覆盖建窗前、读取期间、窗口释放顺序、成功/失败回收与源文件不变。测试通过不等于实际 WebView2 的文件句柄已同步释放；那部分继续按 T4/T5 验收。此前 `0xc0000139` 的“本机不能跑 Rust 用例”判断已作废。


原实施约束仍然成立（照此复验）：

- 核对路径对应的资源守卫仍被生产包装函数持有；取数任务、自己的窗口先结束，再释放档案。
- 不用 mem::forget、泄漏对象、关闭 Drop 或永久保留副本来绕开问题。
- 核对 window.close 的实际语义和失败出口。不能只看到“调用了 close”就断言浏览器已经释放全部文件句柄；继续使用既有有限重试和残留日志机制。
- 不改变三站档案选择，不把所有站点一律改成冷档案或生产档案。

该任务不包含修登录、改目录排序、改正文解析或重做浏览器封装。

### T2：站点路径入口与失败说明 —— 已落库

顶层只列来源站，不请求会话目录。选站后进入 `@DeepSeek/`、`@MiniMax/` 或 `@ChatGPT/` 路径，第二层才请求该站目录；不存在全局“当前站”。

第二层取数失败或 host 不可达时保留明确错误说明，用户可通过面包屑回顶层。不要恢复旧的“切换当前站”状态，也不要把站点行和会话行重新混成顶层列表。接手时核对客户端路径、回包站点归属及现有用例，再补真实工作台中保留草稿、返回顶层和选另一站的验证。

### T3：实际站点账户隔离 —— 已接线，三站真机待验

目标：同一实例从账户 A 切到 B 后，旧目录不继续显示，在途旧结果不落新范围，A 的旧引用不能在 B 下继续发送。

本轮已按[用户接受的身份契约](adr-20261023-account-identity.md)接线。`instanceScope` 仍只表示实例基础范围，`currentScope` 再组合服务端确认的站点账户摘要；不能退回 `fingerprintOf(instanceScope)`。不得把当前选站、DSH_HOME、浏览器目录、会话 id 或 token 的摘要当账户标识。真实站点字段与换号读数尚未验收，身份无法确认必须拒绝。

主要调用链：

1. 壳侧站点取数和账户判定。
2. 现役桥及 site-source.js 的受约束回包。
3. commands.js 的目录缓存范围、capture、preview、duplicates。
4. index.js 的装配和 client 的错误呈现。

实施要求：

- 优先复用站点自然响应中的非凭据稳定账户标识。壳内先裁剪或计算必要标识，不把包含 token 的用户响应整包送出。
- 当前目录、正文白名单不自动授予账户数据外传权限。若需新增字段、错误语义或交互，先写明最小契约变更并取得裁定；不能偷偷扩字段。
- 保留实例、壳模式和站点维度，再加入动态实际账户维度。用户切“来源站”和切“登录账户”是不同事件。
- 捕获开始和提交快照前核对同一账户；旧账户的迟到结果必须拒绝。发送读取时也要核对当前账户，不能只在 catalog 阶段核一次。
- 当前身份无法确认时按既定 account_changed 拒绝相应受保护动作，给可见原因；不能把未知身份静默当成“同一个人”。
- 旧快照保留原来源，不改名认领、不批量删除。已有 schema、旧快照兼容和身份缺失的处置必须在契约与测试中明确。

验收：固定实例和站点，使用可切换的服务端账户源，断言 A → B 后缓存、在途捕获、preview/serialize 分别失效；B 新选的引用正常；不知道账户时拒绝；客户端伪造 accountScope 不能改变授权范围。单测不能靠传入两个不同 DSH_HOME 冒充“换官网账号”。

若某站拿不到合规身份依据，就把该站账户隔离记为未解决，并列出缺失的那个观测或裁定。可以继续其他已授权工作，不能将整个功能标成“账户隔离完成”。

### T4：核验多站点已有修复，并完成站点实跑

已有修复须保留：目录请求携带当前选择的 site；候选项绑定所属页面的站点；正文读取使用该引用绑定的站点；目录缓存键包含站点。禁止再以“客户端完全没传站点”作为当前根因。

先核四条离线用例：

- 不带 site 的既有调用维持默认行为；未知站点不读到默认站缓存。
- 相同账户范围、相同 query，DeepSeek → MiniMax → ChatGPT 各读自己的缓存；无需强制 refresh 才能正确。
- 选中 MiniMax 会话后切到 ChatGPT，再读取/发送原引用，仍使用原引用所属站点。
- 两站目录请求乱序返回、共享去抖期间切站，最终候选及其 site 不互相冒充。

然后逐站验证真实目录 → 选中一条 → 正文 → 快照 → 模型请求。每站独立出结论，一站失败不能被另两站通过掩盖。

MiniMax 的**页签地址／取数根地址**与**深链前缀**是**两个角色**，别混比：`OFFICIAL_CHAT_MINIMAX_URL`（`.com`）当**页签地址**与**取数根地址**用，**深链前缀**是 `deep_link_prefix` ＝ `https://agent.minimax.cn/?id=` ⇒ ⇒ 两者**都别改**（P4 v0.27 已把 G4-28 关掉）。目录面三格在 `.com` 入口轮与 `.cn` 直落轮上**逐项一致**。**不要**因为看到两个域名就改常量或重新登录，更不能让用户在错误档案里反复登录。

ChatGPT 必须使用壳内取数窗口的实际读数。外部浏览器成功、静态包存在端点、独立探针能解析，都不能代替该窗口的结果。认证挑战、未登录、目录空和结构变化分别归因，不编造风控绕过方案。

### T5：完成交付验证和文档收口

- 生成内嵌资源，确认实际物化的是本轮插件，随后按隔离规则重启壳并验收。
- 物化跳过条件包含插件版本、内核指纹、源码 `sourceHash` 和物化产物 `outputHash`，不能再按“版本没变就不复制”判断。仍需生成内嵌资源并重新构建壳，证据包含源码、内嵌资源、物化文件的对应指纹。
- 需要清除旧物化时，只处理已验证位于隔离实例中的该插件目录；遵守仓库对删除操作的确认要求，不碰用户生产实例，不全量清 home。
- 对照下一节逐项记录通过、失败、未执行及证据路径。没有真实工作台证据，不能写“完全打通”。
- 更新当前进度入口和新增事实记录；进度日志按既有追加规则维护，不篡改旧读数，不把旧总表继续当作现状。

## 7. 测试、构建和证据怎么跑

### 7.1 定向检查

在仓库根执行，按修改面选择，不把整套命令每轮都跑一遍：

    node --test plugins/official-chat/test/*.test.mjs
    node --test scripts/check-official-chat-p4-*.test.mjs
    npm.cmd run test:plugin
    npm.cmd run test:scripts
    npm.cmd run prep:builtin
    npm.cmd run check:builtin
    cargo check --manifest-path src-tauri/Cargo.toml --locked --lib
    cargo test --manifest-path src-tauri/Cargo.toml --locked --lib official_chat
    git diff --check

Rust 资源尚未生成时先执行 prep:builtin。改 cold_profile 时还要命中该模块自己的测试，不能只跑 official_chat 过滤后漏掉它。检查受影响文件格式；需要 Clippy（Rust 静态检查工具）时按仓库约定执行对应目标。

修改协议或判据，要跑对应协议、夹具一致性、判据自测和真实源码判据；修改资源登记，要跑已有资源登记测试。管理面板确有改动才跑对应前端测试与 build:ui；不为本次任务顺手改面板。

npm run check 是发版前全量门禁，日常不反复执行。Rust 用例使用 debug profile（调试构建配置），release（发布构建配置）只用来检查相应编译，不能用 release 测试顶替 debug 失败。

如果测试进程启动即报 0xc0000139，记录命令、退出码和“用例未执行”。编译成功不等于测试通过。排查测试程序的依赖及 Windows manifest（程序清单）；任何缓存处理遵守目录及删除规则，不把修改测试断言或绕开测试作为环境修复。（**2026-10-23：本机与 CI 均已不复现** —— 那笔修复是 `fb7e7cb1`；真撞上先按上一条走，别再当成未定位的缺口。）

### 7.2 隔离与代码新鲜度

- Rust 测试按仓库规则持有 scoped_xlink_home 或等效守卫，不裸改 HOME、DSH_HOME、DSH_XLINK_HOME，也不读取真实用户目录当测试样本。
- **先认壳的身份，再做 official-chat 验收** —— dev 壳与安装版 release 壳可以同时在跑，两者的随包插件资源不同；**安装版壳的随包资源里可能根本没有 official-chat 插件** ⇒ ⇒ 在它上面做的 official-chat 验收**一律无效**。认壳看**可执行文件路径**（dev ＝ 仓库 `target/debug/`；release ＝ 安装目录），不看窗口标题。
- 壳内探针使用隔离 DSH_XLINK_HOME、编译期 appDirectoriesOverride 和独立 DSH_XLINK_CHANNEL_SUFFIX。只改 LOCALAPPDATA 不能证明 WebView2 已隔离。
- 如需已有登录态副本，沿用当前会话已经明确授权的范围；没有授权则不执行依赖真实档案的步骤。不得写回或清理源档案。
- 插件源码改动后先重新生成资源，再在隔离实例内按规则重新物化并重启。不要在运行文件仍旧时给新代码定性。
- **引用那条链路**（挑会话 → 取正文 → 落盘 → 请求里给模型什么）在**内核层 harness** 跑：`plugins/official-chat/test/drive/run-g1.mjs`。产品装配里 host 半边**一定**注入真实源（`siteSource`）⇒ ⇒ 目录与正文都走本机回环桥 ⇒ ⇒ **壳里那两条固定夹具根本不在菜单里**（夹具只在**没有真实源**时回退，`host/commands.js` 那条分支只服务判据与单测）⇒ ⇒ 壳里跑不了那几条断言（记**未执行**，不是「失败」）⇒ ⇒ 内核层 harness 起一个**只替官网那半**的「假官网桥」（桥地址与令牌走环境变量，与壳注入内核同名同形）⇒ ⇒ **插件两侧、内核编辑器、发送门控、模型请求全是真的**。壳层那套（`test/drive/shell/`）验的是**壳的产品路径**：物化链、接线行、菜单形状与下钻面包屑。
- 负向验证在隔离副本或明确归属的工作区做；恢复后更新 mtime（文件修改时间）并确认重新构建，避免旧坏产物继续参与验证。
- 不关闭用户浏览器；使用工具创建的浏览器结束后只清理确定归属本轮的页面或进程。

## 10. ChatGPT 首次引用返回 401 的处理边界

Windows 的响应选择器遇到 ChatGPT 401 后，继续在同一次导航的原有 30 秒上限内等待后续响应。401 不参与目录或正文的候选排序，未完成的 401 也不能凭更大的 `num_turns` 阻塞成功响应。选中成功响应后仍立即取体，不延迟读取旧的 401 响应体，不增加导航或主动请求。

等到上限或事件通道关闭后仍只有已完成的 401，返回 `not_logged_in`，详情保留 HTTP（超文本传输协议）401 和确认网页登录的提示。这个错误表示站点拒绝了请求，不能据此断言用户账号已退出。403、500 及其他站点的响应选择规则保持原样。

目录成功结果继续缓存 60 秒；失败结果只缓存 2 秒，以合并连续按键触发的请求。显式刷新仍绕过历史结果，并复用请求发起后完成的同一轮取数，避免重复开窗。

修改这段逻辑时，至少保留以下回归：

- 目录先完成 401、后完成 200，最终选中 200。
- 正文的 401 带更大 `num_turns`，无论是否完成，都不能挡住 200。
- 始终只有 401，在超时或通道关闭时返回登录提示。
- 普通超时保留订阅诊断；其他站点的 401、ChatGPT 的 403/500 保持原行为。
- 失败缓存先过期，成功缓存继续有效，同轮请求仍可复用。

这些事件回归验证的是壳侧选择逻辑。真实站点是否在首次导航中自然产生后续 200，需要单独留存运行证据，不能用合成事件测试代替真机验收，也不能把首个 401 的来源直接归因于登录初始化。

## 11. 2026-10-23 定向复核后的维护要求

本轮复核覆盖近期站点取数、菜单查询、快照发布与回收代码，并修复了以下问题：

- 菜单查询按站点分批去抖，同批任一请求要求刷新，就保留该刷新要求。不能把第二次按键的 `refresh=false` 覆盖到整批，也不能把后一个站点的结果交给前一个站点的调用方。首次进入各站分别刷新；连续输入仍合并请求。
- Rust 和页内旁听都按解析后的完整路径识别端点。目录路径不能命中正文路径，正文会话编号不能靠前缀匹配，查询参数里的路径文本也不算端点命中。站点重定向仍由原流程处理。
- 页内登录态明确缺失时返回现有 `not_logged_in`；存储不可读、认证端点故障继续归为读取失败。正文失败提示须告诉用户确认网页登录，不能只剩“带不出正文”。
- 正常引用不再等待早期探针默认的 1.5 秒延迟。测试需要延迟时显式传入 `readDelayMs`，同步选中后返回待就绪句柄的契约保持不变。

客户端回归必须同时覆盖去抖刷新标记、两站并发查询和两站交替命中缓存。仅强制刷新后分别读到两站结果，不能证明缓存隔离有效。路径回归还须让错误端点返回不同正文，防止夹具内容相同造成假绿。

定向修复时相关 Rust 测试 88 项通过、2 项手动测试未执行；插件与相关脚本共 416 项通过。随后 v0.5.9 最终提交已通过全量门禁及 macOS 原生发布构建，见 §2；最新修复后的真实网页登录与原生界面验收仍未完成。不要继续沿用“macOS 未构建”或“未跑发布门禁”的旧结论。
