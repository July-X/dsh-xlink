# 记忆注入对模型上下文缓存的影响（2026-10-17 实测）

调研问题：记忆系统会不会拉低模型的**前缀缓存命中率**（DeepSeek / OpenAI 兼容接口的
automatic prefix caching，命中价差约 10 倍）？会不会是「缓存命中下降」的元凶？

**结论：不会。** 注入块出现在 10-16 / 10-17 两天，合计 84 KiB ≈ 2.8 万 tokens；这两天
prompt 总量约 2.0 亿，记忆块占 **0.014%**（放进 6 周总量 56.3 亿里是 0.0005%）。控制变量后
（同一模型、两次请求之间没有压缩）有记忆会话 96.73%、无记忆会话 96.83%，差 0.1pp，在噪声里。
真正吃掉 miss 的是**压缩**与**上游缓存过期**，不是记忆。

## 一、机制：记忆块根本进不了 system prompt

| 环节 | 事实 | 出处 |
| --- | --- | --- |
| 注册面 | 插件在 `agent/created` 里注册一条**运行上下文贡献**（`systemPrompt.context`，`order: 300`，`interpolate: false`），正文由 `text: () => box.state.text` 现取 | `plugins/memory/host/index.js` |
| 内核装配 | 内核把这条贡献与 cwd / 文件策略 / 审批策略一起 `joinContextSections`，拼成 **runtime-context 快照**，作为一条 **user 消息**追加到会话末尾（`RuntimeContextProjection.project`） | 内核包 `@deepseek-ai/dsh-system-prompt`、`@deepseek-ai/dsh-agent-loop` |
| 追加时机 | **只有拼出来的整段文本与上一次不同才追加**（`if (this.retained?.text === snapshot) return;`）；旧快照留在历史里直到压缩 | 同上 |
| 与 system prompt 的关系 | system prompt 走 `renderPrompt(assembly.sections)`，快照走 `joinContextSections(assembly.contexts)`——**两个不同的数组**，记忆块从不进入前缀最前面的系统提示 | 内核包 `@deepseek-ai/dsh-system-prompt` |

也就是说：**改记忆块只会在对话末尾追加一条新消息，不会重写前缀**。这正是前缀缓存最友好的形状。

## 二、插件自己的三道闸（只数「内容真的变了」）

- `MAX_INJECTIONS_PER_SESSION = 8`：每会话最多 8 次**内容变化**（2026-10-18 由 3 放宽，见 §6.5）；
  同一回合只检索一次（`shouldRefresh` 按 `turn` 去重），`applyResult` 只在 `next !== state.text` 时才 +1。
- `MAX_LIBRARY_REFRESHES_PER_SESSION = 2`：预算用完之后只按**数据代次**探测（批准 / 删除 /
  编辑才 +1），探到没变就一个字节都不动。
- `MAX_TOTAL_BYTES_PER_SESSION = 36 KiB`：换过几次才算几次，重复渲染不占额度。

出处：`plugins/memory/host/policy.js`。压缩成功后预算清零（`afterCompaction`），压缩失败不清零。

## 三、实测（本机 release 实例，两天窗口）

数据源：`~/.dsh-xlink/kernels/dsh/instances/default/home/sessions/**/session*.jsonl.zstd`
（`zstd -dc` 解码）。336 个会话文件里 170 个是 v3/v4（带 runtime-context 投影与
`usage` 字段），其中 159 个有可分析的请求，时间跨度 **2026-09-05 → 10-17**，
共 **25,981 次请求 / 56.3 亿 prompt tokens / 整体命中率 97.97%**
（`assistant/message.usage`：`cacheReadTokens` 命中、`inputTokens` 未命中）。

记忆注入只出现在其中的 10-16 / 10-17 两天（14 个会话）。这两天的命中率是 6 周里最低的
（10-16 **77.53%**、10-17 **91.33%**，其余各天 95~99.8%）——所以「最近命中率掉了」的观感
是真的，下面第 3.4 节说明是谁吃掉的。

### 3.1 miss token 归因

| 桶 | 请求数 | 命中率 | miss | 占全部 miss |
| --- | ---: | ---: | ---: | ---: |
| ① 会话首个请求（冷启动） | 159 | 9.80% | 2.64M | 2.3% |
| ② 间隔内有压缩（历史被重写） | 916 | **57.57%** | **30.35M** | **26.5%** |
| ③ 间隔超过 5 分钟（上游缓存 TTL） | 286 | 71.11% | 18.16M | 15.9% |
| ④ 间隔内只追加了记忆快照 | **1** | 0.32% | 0.35M | **0.3%** |
| ⑤ 正常续写 | 24,619 | 98.86% | 62.88M | 55.0% |

### 3.2 记忆块自身的体量

- 91 份含记忆正文的快照（分布在 14 个会话）：**15 份首发**（首个请求之前）、**61 份压缩后原样
  重发**（内容逐字节相同，是内核在快照被压缩掉之后重新追加的）、**10 份内容有变化**——
  逐份 diff 过，10 份全部来自库被真的改过（新增 / 删除 / `updated_at` 变更），
  **没有一次是「只是顺序变了」**。
- 记忆段（不含 cwd / 策略那几段）p50 **780 B**、max 1297 B，合计 84 KiB ≈ 2.8 万 tokens。
- 单份快照总量 p50 1725 B、max 2606 B。

不分组时「有记忆注入」的会话命中率（89.7%）确实低于其余（98.3%），**但那两个会话正是
各自发生 132 / 200 次压缩的长会话**——差距来自压缩，不是记忆。同模型、把压缩间隔去掉后，

10-16 当天 miss 的 **88.2%** 来自 `session-fbb5df89` 与 `766ada2c` 两个压缩会话；10-17 当天
前三个会话占 57.8%。这两个重压缩会话同时也是「含记忆快照最多」的两个——**相关性来自它们又长、
又反复压缩，不是记忆**：把它们的记忆段整段删掉，也只省下各自 miss 的 0.03% 不到。

## 四、优化方案（逐项，含 2026-10-17 已落地的两项）

### ① 压缩：阈值被默认值压到窗口的 12%——**壳侧改不到，需要内核侧通路**

内核的自动压缩阈值是（`dsh-compaction-basic` 的 `resolveCompactSpec`）：

```text
threshold = floor(min(window × thresholdRatio, window − 请求 maxTokens − headroomTokens))
```

`thresholdRatio` 默认 0.8、`headroomTokens` 默认 **65536**。那份压缩风暴会话的
`request/context` 是 `window = 512000`、请求 `maxTokens = 384000`（adapter 默认）——
消息预算只剩 128000，阈值被 headroom 压到 **62464**，而日志里压缩确实在 prompt
≈ 62435 处触发。**每次压缩的代价与收益严重倒挂**（该会话实测）：

| 项 | 实测 |
| --- | --- |
| 压缩次数 | 200 次（510 个请求的一条长回合） |
| 摘要调用 | 163 次，合计 6.14M tokens（重跑整段历史的 prompt） |
| 压缩后第一条请求的命中率 | 中位数 **19.9%**（前缀从摘要处整段失效） |
| 每次压缩换来的上下文削减 | 中位数 **3198 tokens** |
| 该会话压缩相关的额外成本 | ≈ 1500 万 tokens，占全部 token 约 42% |

**尝试过、并已按实测回滚（2026-10-17）**：让壳往实例 `cordis.patch.yml` 写
`compaction-basic` 的 `headroomTokens: 8192`（阈值本可 62464 → 119808）。核对与
`dsh --dump-config` 实测都表明**这条路走不通**，两种 patch 形状都落不到会话真正用的那一行：

- `- insert:` 形状：`applyEntryPatches`（`dsh-app-boot`）里**顶层无 id 的 `insert` 是
  「往列表追加一条新条目」**，不是按 id 覆盖。实测 dump 里多出第 5 条顶层
  `compaction-basic`，而根组按 id 去重是「后写赢」——于是我们这条把上游在
  `dsh-web-app/cordis.patch.yml` 里**刻意 `disabled: true`** 的 host 面引擎重新启用了。
- `- id: compaction-basic` + `config:` 形状：定向替换确实生效，但落在那条**同样
  `disabled: true`** 的 host 行上，插件根本不 mount → 完全空转。
- 会话真正使用的那条在 **preset** 里（`preset-standard` 的 `config.plugins` →
  `compaction` 组 → `compaction-basic`，无 config），而 patch 的索引只递归
  `entry.group && Array.isArray(entry.config)`，**看不见 `config.plugins` 里的行**。
  反证实测：往同一份 patch 里写一条只存在于 preset 内的 id，内核直接警告
  `patch: entry "…" not found`。

另一个被这次复核逮到的真回归（如果将来内核允许调 headroom，**必须**注意）：
`const maxTokens = config.maxTokens ?? headroomTokens` —— 只写 `headroomTokens` 会把
**摘要调用的输出预算**一起从 65536 砍到 8192，而实测那 163 次摘要有 **35 次输出超过
8192**（p90 9609、max 11852），那些摘要会被静默截断。

**因此正确的做法是内核侧改**（按「不该由壳替内核定取舍」的既有边界）：

1. 把 `headroomTokens` 从**绝对值**改成**按消息预算的比例**（今天 65536 在这条链路上
   占掉 128000 的一半，而它是为 1M 窗口设计的默认值）；
2. 或让 preset 里的行可被 profile / home 层 patch 覆盖（今天 `config.plugins` 里的行
   对 patch 不可见）；
3. 或按窗口比例钳制「保留输出量」——把 75% 的窗口当默认 `maxTokens` 本身就不合理。

**明确不做**：把模型 `maxTokens` 从 384K 降下来（例如 64K）会让阈值升到 382K、每请求
上下文翻 ~4 倍——按同一模型算，命中 token 的增量比省下的压缩成本更贵；`thresholdRatio` /
`retainRatio` 决定「压缩后模型还能看见多少」，那是内核的取舍，壳不替它定。

**口径修正**：本机当前默认模型已是 `window = 1000000`（`profiles/web/cordis.patch.yml`），
对它 headroom 65536 → 8192 只把阈值从 550464 抬到 607808（**1.10×**），不是 1.9×——
1.9× 只对 512000 窗口那个模型成立。

### ② 空闲间隔（miss 的 15.9%）

上游缓存有 TTL，间隔 > 5 分钟的请求命中率掉到 71%，> 数小时的基本全 miss。这条没有可优化项，
只能解释给用户听（「隔夜回来第一条必然贵」）。

### ③ 记忆侧

- **注入不改**：收益不到 0.02%（两天口径），而块小到看不见会让「记忆是否生效」变得不可验证。
- **不要把它挪进 system prompt**：那才会每次改记忆就废掉整段缓存。这条是给后来人的禁令。
- **自动提取的切片上限 64 KiB → 24 KiB（已落地）**：`plugins/memory/host/extract.js` 的
  `MAX_SLICE_BYTES`。一次提取调用基本全是 miss（切片每次不同、前缀缓存命不中），所以这个
  上限直接等于「每次提取的未命中 token 成本」；`buildSlice` 从最新往回取、整条丢、把丢的
  条数写在开头，收小只丢更老的对话。`MAX_EVENT_BYTES`（单条 8 KiB）不动。
- `auto_extract` 目前仍是**关闭**的（`memory.json` 的 `meta.auto_extract = false`）：它开着时
  才是记忆系统里唯一「大头 miss」的功能。将来开启前还该处理：37 个任务里 16 个失败于
  「模型没有返回任何内容（超时或连接被断）」——那是上游不稳，重试 3 次等于白烧三次调用。

## 五、复现方法

```sh
# 1. 解出一个会话，看请求用量与运行上下文快照
f=~/.dsh-xlink/kernels/dsh/instances/default/home/sessions/*/*/session.v4.jsonl.zstd
zstd -dc $f | rg -o '"usage":\{[^}]*\}' | head
# 2. 快照 = user/message 且 data.source.kind == "runtime-context"
#    含记忆 = 正文里有「以下是本机保存的」（src-tauri/src/memory/query.rs::render_context 的开场白）
```

判据是内核归一化后的 `usage.cacheReadTokens / inputTokens`；不同 provider（MiniMax / GLM /
DeepSeek）各自的口径可能不同，跨 provider 比较时只比趋势不比绝对值。

## 六、2026-10-18 复核：请求体实测 + 全窗口归因

起因：用户提出「记忆能不能会话开始时注入一次、压缩后再注入一次，现在每轮都带上，影响缓存命中率」。
复核结论：**注入频率本来就低，且只往对话尾部追加，不改写前缀——注入逻辑不需要改。**

### 6.1 请求体实测（桩探针，零模型额度）

用仓库自带的桩探针（`plugins/memory/test/probe/`，桩模型记录完整请求体）跑 8 个回合，逐请求对比
messages 数组：

| 对比 | 条数 | 第一次差异下标 | 前缀 |
| --- | --- | --- | --- |
| #0→#1 | 4→7 | 4 | 4/4 逐字节相同 |
| #1→#2 | 7→10 | 7 | 7/7 |
| #2→#3 | 10→12 | 10 | 10/10 |
| #3→#7 | 12→20 | 12/14/16/18 | 全等 |

第一次差异下标**永远等于上一次请求的消息条数**：新快照追加在新用户消息之后，旧快照逐字节留在原位。
前缀 19314 B 不动、新增尾部 799 B——记忆内容变化只花新增那几个 token。

**坑**：仓库覆盖层把 `thresholdRatio` 设成 0.001（每回合压缩），照原件直接跑会看到「每回合只剩一条
快照、像被替换」——那是压缩把历史折进 checkpoint，不是记忆。对照轮关掉压缩后 sdk 日志 0 次
`compaction/start`，才是纯追加的形状。

### 6.2 内核侧频率（已安装 0.2.1-rc.2）

- 135 个会话 307 条 runtime-context 事件，`surfaceOp` **全是 `append`**，没有一条 replace；能覆盖
  快照节点的 37 条 replace 全部是压缩整段覆盖。
- 11 个 rc.2 会话 **2916 个 step 只产生 21 次快照追加**（3 次是压缩后的重置性重发）。
- 文本与保留值逐字节相同时 `project()` 直接 return，一个事件都不落。
- 135 个会话 171 条真 `system/message` 中含记忆正文者 **0**：记忆从不进 system prompt。

### 6.3 全窗口归因（10-15 起、7 个工作区、8964 次请求、整体命中 96.67%）

| 桶 | 请求 | 命中率 | miss | 占全部 miss |
| --- | ---: | ---: | ---: | ---: |
| 间隔内有压缩 | 511 | 30.36% | 22.20M | 31.1% |
| 间隔 > 5 分钟 | 109 | 78.61% | 6.05M | 8.5% |
| 间隔内记忆内容有变 | 4 | 0.29% | 1.39M | 1.9% |
| 正常续写 | 8278 | 98.03% | 41.14M | 57.6% |

那 4 次「记忆内容有变」的低命中**全部与压缩或会话恢复同刻发生**；去掉这两个混淆变量后只剩 1 次
（0.25M tokens）。同类「整段失效」在日志里另有约 98 次不带任何伴随事件，属背景噪声。记忆块自身：
120 次追加合计 223 KiB，含记忆的请求 5109/8964，累计承载 9.7 MiB（按缓存命中价）。

### 6.4 明确不做：把 `MAX_INJECTIONS_PER_SESSION` 从 3 改成 1

按「首注入一次 + 压缩后重置」的语义，这个常量是唯一的开关。不改，三条理由：

1. **省不到东西**：真机 10-16 起每个 epoch 最多只用到 2 次，`MAX=3` 从未触顶；改成 1 两天只少约
   3 次追加 ≈ 1.7K tokens，而 miss 的大头是压缩与上游 TTL，这个常量碰不到。
2. **代价是真实的**：丢掉「后续回合按当前问题重检索」——会话 `bafa0260`（10-17 22:47）首回合检索
   `hits=0`、整回合 46 步无记忆，正是靠第二回合重检索补上。
3. **形状由内核决定**：尾部追加、不重写前缀，是内核 `RuntimeContextProjection` 的形状；壳侧调小预算
   只能减少追加**次数**，改不了「任一 section 变了就整块重发」那条。

### 6.5 反向的那一步做了（2026-10-18）：3 → 8

用户拍板把 `MAX_INJECTIONS_PER_SESSION` 放宽到 **8**，理由是「让记忆在长会话里继续跟着话题走」——
§6.4 第 2 条说的那个代价（丢掉后续回合按当前问题重检索）在长会话里就是「记忆只在开头露一次脸」。
本节的缓存测量正是这次放宽的依据：追加在尾部、前缀逐字节不动，所以多注入几次花的是**新增那几个
token**，不是整段前缀重算。

- **桩探针**（`/tmp/mem-recon/request-shape.md`，7 个回合、无压缩那一轮）：连续两次主请求之间，
  上一次请求的 messages 是下一次的**完整逐字节前缀**，第一次差异下标恰好等于上一次请求的消息条数
  ——失效点永远是「上一回合新生成的 assistant 回复」，记忆刷新没有把它提前。那一轮记忆块的增量是
  639 B 正文。
- **真机**（§三同一批日志）：120 次追加合计 223 KiB，平均约 1.9 KiB/次；8 次约 15 KiB。
- **36 KiB 字节闸仍在，且单次写得满时它先到顶**（单次上限 12 KiB，36 / 12 = 3 次）。所以这次放宽
  真正影响的是「块不大」的常态会话，不是「每次都写满 12 KiB」的极端情形——两者都由 `shouldRefresh`
  与 `shouldProbeLibrary` 里的同一道字节闸兜着。

§6.4 那条「不改小到 1」的结论不变：放宽与收紧是两个方向，它挡的是「省不到东西还丢掉重检索」。

## 七、2026-10-24 口径更新：§③「auto_extract 关着」的前提已失效

本节是对 §四之③（与 §三末尾那句「auto_extract 目前仍是关闭的」）的事实修正，不改动
上面任何测量本身：

- **`meta.auto_extract` 已全仓无读取方**（`store.rs` 仍保留该字段仅为旧文档兼容，
  `export.rs` 只把它写进导出头部）。真正的闸门自始至终是 `meta.use_approved`——
  面板上那一个「使用已批准的记忆」开关。也就是说：**开关一开，自动提取即常态化
  运行**（每段含人类消息的正常回合结束 → 30 秒去抖 → 一次提取调用）。
- 2026-10-19 起提取的**干净候选直接落地成记忆**（`auto_accept_candidate`，落为
  「未验证」）；带冲突 / 取代标记的与经验类候选留在「待确认」等用户裁决。§四之③
  说的「将来开启前还该处理：37 个任务里 16 个失败于『模型没有返回任何内容』，
  重试 3 次等于白烧三次调用」——这条遗留**现在处于生效状态**，仍是待办。
- 因此 §四之③ 的成本判断要按新前提读：「每次提取的未命中 token 成本」

  「将来才发生」的事，而是开关打开期间的常态成本。它**仍然不进用户会话的
