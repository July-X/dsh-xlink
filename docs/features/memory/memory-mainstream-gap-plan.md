# 记忆能力追赶主流 Agent：分阶段开发计划

依据：2026-11-03 本机效果报告与 `jobs.json` 取证（见 §2）、[本地记忆设计](dsh-xlink-memory-design.md)、[效果设计](effectiveness-dashboard-design.md)、[效果快照读法](agent-effect-snapshot.md)与[开发进度](memory-progress.md)。

本计划只解决「记忆能力」与「效果证据」两块；不改 dsh 内核（已安装目录只读）、不引入云端、不新增服务端进程，也不在本计划内重做记忆模型。

## 1. 目标

按优先级排列，前面的没做到不做后面的：

1. **自动提取可用**：真实工作台里稳定产生自动记忆，而不是 0 done / 队列顶满。
2. **效果读数可信**：`skip` 原因、L3 分组、工具使用计数不再误导；样本不足如实显示。
3. **自动记忆可 dogfood**：用户在一到两周真实使用中能感到「它记得我上次的做法」，自动记忆留存率与跨项目隔离可测。
4. **按触发条件升级召回**：只有当库规模/零命中率到阈值时，才评估混合检索；不在当前阶段引入向量库或图数据库。

### 不做什么（本计划的范围闸）

- 不做云同步、跨设备账号记忆、跨 Agent/跨人共享记忆。
- 不做屏幕采集、自动生成技能、主题记忆（Topic Memory）。
- 不把 PowerContext、Mem0、Letta 等作为插件或常驻服务装进来。
- 不为了「像主流」增加记忆类型 schema；当前 `memories` / `candidates` / `handoffs` / `experiences` 已够表达四类内容，先用现有字段解决。
- 不先换向量检索、不先做新面板视觉、不先做 benchmark 复刻；这些都要等 P0/P2 的可用性通过。
- 不修改已安装内核目录；需要的内核行为缺失只记录规避与上报，不依赖未来上游修复。

## 2. 现状与差距（2026-11-03 实测）

本机默认实例的效果报告生成于 2026-11-03 10:32（`history/` 4 份快照），`jobs.json` 更新到 16:33：

### 2.0 2026-11-03 复核订正（动工前重数了一遍 `jobs.json`）

表里那几行是当天上午的快照；下午重数盘上的 114 条任务，两个数字要改：

- **提取任务不是 47 条**：盘上共 114 条（done 25 / failed 72 / pending 17）。上午那 47 条是最近一批。
- **失败原因不是 32 + 6**：空模型 67 次（62 failed + 5 pending 带着上一次的旧错）、拿不到 live 会话对象 15 次。
- **done 不是 0**：有 25 条完成，只是绝大多数没有产出记忆（库里有 7 条来源为 extract 的记忆）。

**根因已定位（不是「模型坏了」）**：内核把 provider 侧的失败表达成**终结 finish chunk**而不是抛异常
（已装内核 `dsh-llm` 的 `adapterFailureChunk`），而插件 `plugins/memory/host/index.js` 的 `callExtractionModel`
**从不读 `assembler.finish`** —— 于是任何 provider 失败都变成「空正文」，被下游误判成 parse 失败、
stage 标错、失败原因丢掉。本机 313 次 claim→fail 的间隔全部在 0–29 秒之间（没有一次接近 120 秒超时），
所以那句「超时或连接被断」是**猜的**。P0-1 就是补上这一读。

| 项目 | 实测 | 设计预期 | 判断 |
| --- | --- | --- | --- |
| 会话 / 请求覆盖 | 86 会话、12,592 请求；81 个有请求、30 个有注入；解码失败 0、坏行 0 | 先看数据健康，样本不足如实标注 | 覆盖与解析健康达标 |
| 注入 | 36 个快照、39,058 B、约 12,722 token；3,749 请求（29.8%）携带记忆 | 有界注入、内容不变不重复 | 机制达标；但只来自 1 条 pinned 规则 |
| 账本 | 12 inject / 14 skip；8/12 按 turn+step 关联（66.7%） | 原因可解释、关联可复核 | 可用；原因语义有缺陷（P1） |
| 记忆库 | 1 条手动记忆（general / verified / pinned），0 经验，0 交接，0 条自动提取记忆 | 自动提取应持续积累可复用记忆 | **未达标** |
| 提取任务 | 47 条：0 done / 27 failed / 20 pending；pending 正好等于 `QUEUE_CAP=20` | done 为主、失败可重试、队列不长期顶满 | **未达标，P0 阻塞项** |
| 提取失败原因 | 32 次「模型没有返回任何内容」；6 次「拿不到 live 会话对象」；9 条无错误 pending | 失败要能归到读取 / 模型 / 解析 / 提交阶段 | 只有粗原因，无法定位根因 |
| L2 | 配对会话 2 / 需 10；exposed 3,749 vs unexposed 8,843 | n≥10 才出读数 | 样本不足，不能下结论 |
| L3 | 报告时 control 0 / treatment 0；之后账本出现 1 条 treatment | 只影响实验开始后新建会话；每组 ≥5 | 样本不足，且有分组协议缺陷（P1） |
| 工具使用 | 15,023 次工具调用；memory_read 0 / search 1 / propose 1 | 主动工具按需使用，正文注入已够时不强求 read | 注入可用，但采纳/工具面证据不足 |

三个根因，按修复顺序：

1. **提取链在真实模型/真实会话下不可用**：0 done 说明「自动记忆」还没有进入用户可见状态；先修这个，所有能力讨论才有意义。
2. **效果读数有错误信号**：`skip/budget` 混入「同一 turn 已查过」；L3 对恢复会话重新分组；扫描只数 3 个工具。它们会让下一轮判断继续跑偏。
3. **没有 dogfood 与长期样本**：1 条手动规则、L2 配对 2 个，无法回答「模型会不会照着做」；必须用修好的链路攒真实数据。

与主流的能力位置（只作方向参照，不作为本计划验收）：

- **已经接近或领先**：本地优先与隐私、显式批准、项目隔离、删除抑制再生、有界注入与成本、L1/L2/L3 效果观测。这些不要为了「像云端产品」而放弃。
- **明确落后**：跨会话自动捕获与更新（Claude Code 的自动记忆、Codex 的后台 memories、ChatGPT 的 dreaming 都是持续归纳）；大规模项目知识 RAG（Claude Projects）；长期演进与自动冲突处理（Mem0 一类）。
- **不必追赶**：Cursor 在 2.1.x 已移除原生 Memories、只留 Rules；我们的手动+静态规则已不弱于它。
- **不把「记忆条数多」当目标**：本项目更该优化「自动记忆留存率 / 注入精确率 / 跨项目零污染 / 用户纠错成本」，避免变成垃圾记忆仓库。

## 3. 阶段计划

### P0：修复自动提取链（阻塞项，预计 5 个工作日）

**进度（2026-11-03）**：改动点 1 / 4 / 5 与 P0-5（会话销毁后改读整份会话）已实现并有判据；
改动点 2（真模型复现与定向修复）**待真机**：它要生产同款的 provider / 端点 / 密钥（环境变量由使用者提供），
拿不到就只能停在「归因已修、根因待复现」，不能凭猜测改请求形态。验收里「10 个真实会话」那一条
同样要等复现。

**归因之外补的取证（同日晚）**：把「日志里查不出来的两件事」补成可查——
① 空正文带上 `finish` 与 `usage`（`输出 N tokens` / `其中 reasoning M` / `没有 usage`），
并认出内核的 `STREAM_CLOSED`（→ transport）与 `CONTEXT_WINDOW_EXCEEDED`（→ 新增 `context_overflow`），
没见过的终结原因不再当成功；② `/experiment` 多送 `source`，壳按 `memory-bridge` 标签记
`source=… created_at_ms=… now_ms=… started_at_ms=… cohort=…`——非 startup 会话出现 `created_at_ms=0`
就是「插件没读到 `header.createdAt`」的铁证。读法见 memory-progress.md 的 2026-11-03 条。

**问题**：47 条任务 0 成功，pending 顶满；失败原因只有「模型没返回内容」，无法区分 adapter 超时、provider 空流、额度/参数拒绝、解析失败。

**改动点（只在插件与诊断层，不碰内核）**：

1. 在 `plugins/memory/host/run.js` / `index.js` 的 `callExtractionModel` 外层补结构化失败信息：`stage`（read/slice/model/parse/submit）、`errorKind`（empty_stream / transport / timeout / parse / missing_route / unknown）、provider、model、耗时、输入字节数；日志与 `/jobs/fail` 带同一组字段。
2. 用一次真实会话复现：对比同一模型下普通对话请求与提取请求的差异（system、`maxTokens`、无 `purpose`、无 `sessionId`、输入大小）；确认是 provider 不支持该请求形态、adapter 超时，还是空文本被误当成功。
3. 修复后仍保持设计边界：不填 `purpose`、不写入用户会话日志、不自动换远端模型、不引入云端回退。
4. 队列健康：新增 pending 数量与最老 pending 年龄的只读指标；`pending == QUEUE_CAP` 或最老 pending > 24h 时在效果页显示降级提示。提取失败后按现有退避重试，不无限重排。
5. 失败样本保留最小事实：`jobs.json` 记 stage / errorKind / attempts / 最后错误；不记会话正文。

**验收**：

- 在至少 10 个真实会话跑出提取任务；**done 或「空切片成功」≥ 90%，failed < 10%**；pending 不长期等于 20，最老 pending < 24h。
- 至少 3 条自动记忆落库（未验证即可），来源 `source.kind=extract`，`source.session` / `start_seq` / `end_seq` 可追溯。
- 效果页「提取质量」能看到成功/失败/阶段分布，而不是只有失败数。
- `npm run test:plugin`、`cargo test --locked memory`、`npm run test:ui` 中与提取/效果相关项通过。

**风险与处理**：如果两轮修复后仍无法稳定成功，停止新增自动记忆功能，把面板文案降级为「自动提取不可用及原因」，保留手动记忆；不要用隐藏失败或伪造成功掩盖。

### P1：修正效果读数（2–3 个工作日，与 P0 并行可做）

**进度（2026-11-03）**：三处改动点已实现并有判据（桶拆分 + 旧桶兼容、L3 只收实验开始后创建的会话、
五工具计数与 `STATE_SCHEMA` 抬版）。

**问题**：效果页本身完成度高，但三处读数会误导：

1. **`skip/budget` 语义混叠**：`classifyNote` 把「同一 turn 已查过」和「会话预算用尽」都归为 `budget`（[policy.js](../../../plugins/memory/host/policy.js) `classifyNote`）；实测 10 次 `budget` 没有一次是 8 次/36 KiB 真正耗尽，报告却自动提示「预算触顶」（`effect_export.rs` 的 `budget > 0` 分支）。
2. **L3 分组协议**：设计只允许实验开始后新建会话参与（`effect/experiment.rs`），但插件在 `agent/created` 对所有来源都领取分组；账本里已有实验开始前创建的会话被打成 `treatment`。这会让恢复的旧会话中途改变行为，污染读数。
3. **工具面不完整**：效果扫描只统计 `memory_read` / `memory_search` / `memory_propose`，`memory_context` 与 `memory_effect` 不可见，无法评估主动工具的使用。

**改动点**：

- 拆分 skip 原因：`already_queried_this_turn`（同 turn 去抖）与 `budget_exhausted`（次数或字节真正到顶）；保留旧账本兼容映射，报告、自动线索、UI 原因名同步改。
- L3：`agent/created` 把 `source` 传给分组逻辑，只有 `startup` 且会话创建时间晚于实验开始才领分组；recovery/resume 会话沿用已有 cohort 或直接不参与。需要桥的 `/experiment` 响应带回 `started_at_ms`（或插件从 session header 读创建时间）；若当前内核拿不到创建时间，就只认 `startup`、resume 不参与，这是可接受的最小退化。补一条「实验开始前的会话不会领取分组」的行为用例。
- 效果扫描补 `memory_context` / `memory_effect` 计数；`memory_effect` 自己调用只读桥，不计入「工具采纳」也可以，但要在报告里说明，避免下一轮误判。
- 自动线索只在真正预算耗尽时提示；同 turn 去抖提示改为「正常去重，不是失败」。

**验收**：

- 用一份含「同 turn 多次 step」的夹具，报告显示 `already_queried_this_turn`，不再出现「预算触顶」。
- 用实验开始前已存在的会话跑 `agent/created`，不产生 experiment 账本事件；新会话才产生。
- 单测覆盖 reason 拆分、L3 source 过滤、五工具计数；现有效果历史快照可回读。

### P2：自动记忆 dogfood（2 周，P0/P1 通过后）

**目标**：让自动记忆从「能跑」变成「值得留」。不新增 schema，不做新面板，只验证现有链路能否产生用户愿意留下的记忆。

**改动点**：

1. 自动提取质量闸门：用现有提示词约束四类内容——用户偏好、用户纠正/确认过的做法、项目决策、外部参考位置；明确忽略可推导的代码结构、临时任务、一次性故障。若效果差，先调提示词与去重，不扩模型工具。
2. 候选可读性：**自动提取结果默认直接落成未验证记忆，不走逐条确认**；只有冲突/取代才进待确认队列。两类都要标题短、带来源；用户删除/停用即记录（面板已有 rejected 状态，不新建表）。
3. 真实工作流验收：每周至少 10 个新会话、跨 2 个项目；记录自动记忆落库数、删除/停用数、被注入数、memory_read/search 使用、跨项目注入次数。
4. 可选的最小增强（只在 P2 数据证明需要时做）：会话收尾时用现有 `memory_propose` 生成 handoff 草稿；不自动批准、不改交接语义。

**验收**：

- 自动记忆在 P2 期间落库的两周内留存率 ≥ 70%（落库后未被删除/停用；30 天后再复核一次）；连续两周至少 5 条自动记忆被注入。
- 冲突/取代候选有人工处理记录，且不会自动覆盖已有记忆。
- 跨项目污染 0：A 项目自动记忆不出现在 B 项目（按现有 scope/workspace 断言）。
- L2 配对会话达到 10 个；L3 每组达到 5 个后才允许读因果指标（试验期间不得改分组逻辑）。
- 用户手动删除/停用的自动记忆有记录，并能阻止同来源再生。

**停止条件**：若两周后自动记忆留存率 < 50%，或失败率仍 > 10%，停止扩大提取范围，回到 P0 修质量；不要用更多提示词或更多模型调用硬堆。

### P3：召回升级（按触发条件，不预先排期）

只有满足任一条件才启动，且先做最小实验：

- 已接受记忆 > 300 条，或连续 7 天 `skip/no_hit` 占 skip 的 50% 以上；
- 用户明确反馈「记得但搜不到」且有关联会话证据。

升级顺序：

1. 先改确定性检索：标题/关键词/正文的权重、同义词、项目范围排序；仍用现有 `query.rs`，不加依赖。
2. 仍不足再评估混合检索（本地 embedding + 关键词），必须先做离线回放：用已有 `report.json`/账本构造查询集，比较命中率与注入字节；不达到「命中提升 ≥ 20% 且延迟 p95 不超预算」不接生产。
3. 不引入图数据库、不做自动记忆网络、不做跨设备同步；这些不在本项目当前边界内。

### P4：持续测量与退出标准（随 P2 开始）

固定看板（仍用现有效果页，不加新页面）：

- 提取：成功/空成功/失败、stage/errorKind、最老 pending、队列顶满时长。
- 记忆：自动记忆落库数、留存率、删除/停用率、注入条数、memory_read/search/context/effect 使用、跨项目注入。
- 效果：L1 注入率、L2 配对会话数、L3 组样本数、注入 token/缓存成本。
- 质量：用户删除/停用/拒绝计数（已有状态，不新增采集、不记正文）。

「追上主流基础能力」的退出标准（量化、可复核）：

- 自动提取成功率 ≥ 90%，且连续 2 周有自动记忆落库并实际注入；
- L2 配对 ≥ 10 个会话，L3 每组 ≥ 5 个会话；报告能给出有样本的伴随/因果读数；
- 跨项目污染 0，自动记忆删除后同源不再生；
- 用户在一次真实会话里能复述「它记得我上次的做法/偏好」——用一次人工验收记录，不靠自评。

达不到就继续修 P0/P2，不进入「语义检索/大规模知识库」的叙事。

## 4. 验证与提交纪律

- 每个阶段先写失败判据：P0 先证明失败能复现、能归因；P1 先证明旧报告会误导；P2 先定义留存率与注入指标。
- 测试只跑相关项：`npm run test:plugin`、`npm run test:ui`、`cargo test --locked memory`；阶段完成再跑 `cargo clippy` 与 `check:invariants`。
- 改行为时同步 [memory-progress.md](memory-progress.md)；改效果口径时同步 [agent-effect-snapshot.md](agent-effect-snapshot.md) 与 `effectiveness-dashboard-design.md` 的字段说明。本计划作为「下一步做什么」的唯一入口，进度表只记已完成项。
- 不提交用户真实记忆正文、会话原文或 jobs 的完整错误上下文；计划与验收记录只留计数、阶段、原因类别。

## 5. 一句话收口

**先让自动提取在真实环境里跑通，再让效果页说得准，最后才谈召回升级。** 当前差距是可靠性与数据问题，不是缺少一个向量库；控制面与隐私已经领先，不要在追赶自动记忆时把它们换掉。
