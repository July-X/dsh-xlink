# 安全网设计：环境快照与二分定位

本文是 dsh-xlink 的**安全网**设计规划：环境坏了之后，怎么把用户捞回来，以及怎么告诉他到底哪里坏了。

沙盒预检（`precheck.rs` / `sandbox.rs`）管的是**装之前**；本文管的是**坏之后**。两者的关系见 §9。

---

## 1. 现状取证：要解决的是哪几个具体缺口

不写"可能存在的问题"，只写已经在代码里能定位到的缺口。

### 1.1 现有降级阶梯只覆盖"启动就挂"

`guard.rs:716` 的 `plugin_ladder` 是唯一的自动降级路径，它由 `guarded_start` 驱动，而 `guarded_start` 只在用户**主动点「启动工作台」**时运行。

因此下面这类故障完全落在覆盖之外：

- 启动成功、跑了几分钟、某个插件触发的异常把工作台页面搞白；
- 启动成功、用户用了两天、某次工具调用让进程崩掉；
- 启动成功但工作台一直白屏（`harness-health.js` 上报了 `HealthReport`，但归因只写进事故文件，没有对应的降级动作）。

这三类的共同点是：**内核"起来过"**。`watch_child` 判定 `Ready` 之后就再也不看它，所以阶梯不会启动。

### 1.2 阶梯是线性的，且只降插件

`guarded_start` 的三次尝试是「原接线 → 停用日志里指出的可疑插件 → 安全模式（停用全部第三方插件）」。`guard.rs:722` 的 `suspects` 只从**插件**里选，且最多 8 个（`MAX_SUSPECTS`）。

后果：

- 12 个插件里有 1 个坏的 → 归因命中它，1 次重试解决；
- 12 个插件里有 3 个坏的 → 第一个重试仍失败，归因再跑一次，可能连续命中 3 个才收敛，3 次启动；
- 坏的其实不是插件（是补丁、技能、内核版本本身）→ 三次全废，最后报一个不可恢复的事故，用户拿到的建议是"移除这些插件"，**方向是错的**。

### 1.3 配置组合爆炸，但没有组合的记录

一个实例的"环境"由四类独立可变的东西相乘决定：

| 维度 | 权威位置 | 变更入口 |
| --- | --- | --- |
| 内核版本 | `active.txt` + 实例记录 `kernel_version` | 「内核版本」页切换/安装 |
| 插件集 + 每实例物化模式 | `store.json` + 各实例 `extensions/plugins/<id>/` | 插件中心安装/卸载/切模式 |
| 技能集 | 技能中央库 + `skills/active/` 条目 | 技能页启停/安装 |
| 补丁集 | `patches/state.json` | 「设置 → 内核补丁」 |

再加上 profile 名、端口，这些是加法不是乘法。**用户在"昨天还能用，今天起不来"的时候，脑子里没有任何一份"昨天那套配置"的清单**——而这恰恰是唯一有用的信息。

现有的回滚能力都是**单点**的：

- 补丁有备份可还原（`patches.rs` 的 `backups/`，SHA-256 兜底）；
- 迁移向导有 rollback（旧源永不删除，`docs/migration-wizard-ui-proposal.md`）；
- 插件有 `quarantine.json` 记录谁被停用过。

但没有任何一处记录"整套配置曾经是好的"。

### 1.4 `reap_orphans` 这条安全网目前是失效的

`kernel.rs:1531` 的注释说它比较进程的 `cwd` 与 `data_dir`，但 `kernel_adapter.rs:385` 把内核的 `current_dir` 设成了 `record.workspace`，两者永不相等。

这条与本文第 5 章的沙盒回滚直接相关：**任何"起一批临时内核做验证"的设计，都不能依赖 `reap_orphans` 兜底**，必须自己持有 `Child` 并在所有路径上终止它。`precheck.rs` 现在的做法正是如此（`sandbox::Sandbox::shutdown` + `Drop`）。

## 2. 目标与非目标

### 目标

1. **一键回到"上一个能跑起来的组合"**，且这个动作本身可再被撤销。
2. 对**偶发**故障给出可执行的缩小范围，而不是"移除所有插件试试"。
3. 任何一次自动降级 / 自动恢复，都留下可读、可回放的证据链。

### 非目标

- 不做内核自愈（不替内核修 bug，只帮用户缩小范围）。
- 不做配置的云端同步与团队共享（涉及凭据，与本项目的信任边界冲突）。
- 不取代预检。预检防止"坏的东西进来"，安全网处理"进来的东西坏了"。
- 不承诺二分能给出**唯一**根因。二分给的是**能解释现象的最小集合**，见 §8。

## 3. 核心概念

### 3.1 环境指纹（fingerprint）

一个实例当前生效配置的可哈希摘要。用途是**快速判断"变了没有"**，不进 UI，不给人看。

```
fingerprint = sha256(
  kernel_version ‖ profile ‖ port ‖
  sorted(插件 id + 物化模式) ‖
  sorted(启用技能 id) ‖
  sorted(已应用补丁 id + 各自目标文件 sha256)
)
```

关键点：指纹**不含** `wiring.json` / profile `package.json` 的内容本身，只含"构成它的输入"。这样指纹是**可重建的**——有指纹就能算出该长什么样，而不是只能记录"曾经长什么样"。

### 3.2 快照（snapshot）

指纹 + 足以重建它的**全部输入值**。不是备份，是**声明**：

```json
{
  "schema": 1,
  "id": "snap-1f3a9c2b",
  "instance": { "family": "dsh", "id": "default" },
  "createdAtMs": 1790490000000,
  "reason": "startup-ok",
  "fingerprint": "9c2e…",
  "state": {
    "kernelVersion": "0.1.5-rc.2",
    "profile": "web",
    "port": 3090,
    "plugins": [
      { "id": "dsh-market",   "mode": "link" },
      { "id": "dsh-file-perf", "mode": "copy" }
    ],
    "skills": ["review-checklist", "commit-style"],
    "patches": [
      { "id": "dsh-session-perf", "targetSha256": "ab34…" }
    ]
  }
}
```

**绝不包含**：`credentials`、API Key、`.credentials.yaml`、任何 token。快照会落在磁盘上、会被导出、可能被贴进事故反馈——它必须能安全地给人看。凭据纪律沿用 `credentials.rs` 的既有规则（只读解析、绝不落日志）。

### 3.3 上一个已知良好（last known good）

最近一次**成功启动**的快照。这是唯一合法的"良好"来源——不能由"安装完成"或"用户点了确定"充当，因为那两件事都不代表能跑起来。

## 4. 快照：何时打、存哪、留几个

### 4.1 打点时机

| 时机 | reason | 说明 |
| --- | --- | --- |
| `guard.rs` 判定 `Ready` 且无告警之后 | `startup-ok` | **唯一**能确立 last-known-good 的时点 |
| 用户主动安装 / 更新 / 卸载 / 切模式 / 切版本**之前** | `pre-change` | 主动变更前留可回退点。这是最有价值的一类：它记的是"我改之前" |
| 手动 | `manual` | 事故面板的"打个回退点"按钮 |

`startup-ok` 快照要**节流**：同一指纹重复启动不重复打（否则用户一天开关工作台 20 次就攒 20 份一模一样的快照）。判据就是 §3.1 的指纹。

### 4.2 存放

```
<instance_dir>/snapshots/index.json          # 索引，倒序
<instance_dir>/snapshots/snap-<id>.json      # 单份快照声明
```

按实例存放，不进全局——多实例之间不共享"良好"的定义。

### 4.3 保留策略

- 最多 **10 份**，超了按权重丢最旧的：`pre-change` 权重 2 > `manual` 1 > `startup-ok` 0；
- 同指纹不重复入库（见 §3.3 的理由）；
- **永不删除当前 last-known-good**，哪怕它是最旧的、权重最低的。裁剪时先把它放进保护区再填剩余位置，这条有测试钉死（`prune_never_drops_the_last_known_good`）。

保留策略要简单到能被人记住。10 份 + 三档权重，够了。

## 5. 恢复流程

### 5.1 差异先行

点「回到上一个能跑起来的组合」，**第一件事不是恢复，是展示差异**：

```
将从：0.1.5-rc.3 / 插件 3 个（含 dsh-market）/ 技能 2 个 / 补丁 0 个
回到：0.1.5-rc.2 / 插件 2 个（无 dsh-market）  / 技能 2 个 / 补丁 0 个

将要做的变更：
  · 内核版本 0.1.5-rc.3 → 0.1.5-rc.2
  · 停用插件 dsh-market
  · 其余不变
```

用户在这里能发现"哦原来是我昨天装的那个"，这就是安全网 80% 的价值。**不要跳过这一步直接恢复**——那等于用一个不可见的动作覆盖用户当前的配置。

### 5.2 恢复的硬规则

1. **先备份当前状态**成一份 `pre-restore` 快照。恢复失败要能再恢复回来。
2. 恢复**只改差异项**，不改一致项。避免"恢复一下顺手动了别的"。
3. 恢复**不删数据**。停用一个插件 ≠ 卸载它（中央库条目留着，接线摘掉即可）；停用一个补丁走已有的备份还原；技能同理（条目移出活动视图）。
4. 恢复完**自动跑一次健康自检**并把结果并入事故面板。恢复不是终点，是"恢复之后再确认一次"。
5. 恢复期间工作台必须已停止（有既存约束：补丁操作本来就禁止在工作台运行时进行）。

### 5.3 幂等与可嵌套

恢复实现要满足：连点两次 = 恢复一次；"恢复"之后再"恢复"回到 `pre-restore` 那份，等价于没恢复过。做法是把每次恢复都建模成"应用一份快照声明"，而不是"执行一串反向操作"。

## 6. 二分定位：为什么现有阶梯不够

### 6.1 成本对比

n 个插件、其中 1 个坏：

| 方案 | 启动次数 |
| --- | --- |
| 现有线性阶梯（按嫌疑度逐个停） | 最坏 n 次 |
| 二分 | ⌈log₂n⌉ 次 |

n=12：最坏 12 次 vs 4 次。每次启动含等待就绪（`READY_TIMEOUT_SECS = 30` 最坏），线性阶梯最坏要 6 分钟，二分 2 分钟。用户不会等 6 分钟。

### 6.2 但二分有个真实的难点：偶发故障下"试一次"不算数

对**确定性**故障（启动就崩），二分是教科书做法。对**偶发**故障（10 次里挂 3 次），"跑一次没挂"完全不能证明这半边是好的。

所以必须先定义三个量：

| 量 | 含义 | 取值与代价 |
| --- | --- | --- |
| `probe` | 什么算"这次失败了" | 三选一：`startup-failed` / `crashed-within-T` / `blank-screen` |
| `k` | 判定"好"需要连续通过几次 | 默认 k=2（对抗偶发）；成本 ×2 |
| `T` | `crashed-within-T` 的时间窗 | 默认 120s；成本由用户的崩溃间隔决定 |

于是真实成本是 `⌈log₂n⌉ × k` 次启动。n=12、k=2 → 8 次。仍然远好于线性，但要**如实告诉用户预计多久**，并且允许中途放弃（放弃时保留已排除的结果，下次接着查）。

### 6.3 候选集合的排序

二分的有效性依赖于"好的一半/坏的一半"划分得足够均匀。`guard.rs` 已经有一套按日志证据给插件排嫌疑度的逻辑（`attribute` / `is_anchored_plugin_hit`），**复用它**，不要另写一套打分。

排序后的候选集：按嫌疑度降序，前一半是"最可疑的一半"。

### 6.4 集合里放什么

只放**可以单独开关**的东西，这是二分的前提：

| 可进候选 | 不可进候选 |
| --- | --- |
| 插件（中央库条目 → 摘接线） | 内核版本（切换代价高，且可能连带要求重装） |
| 技能（活动视图条目） | 凭据 / 模型设置（与启动无关） |
| 补丁（撤销，走备份还原） | 端口（与故障无关） |

内核版本放不放，是个真实的取舍：

- **放**：内核自身的 bug 就再也查不出来了，而这是最高频的"用了新版本就坏"；
- **不放**：二分次数翻倍，且切换版本会触发重装依赖，用户会疼。

建议：**默认不放，但先做一次廉价的版本二分**——先试"上一版本"，挂/不挂一次就分出「内核 vs 扩展」两大类，再决定要不要往下钻。这比把版本塞进 n 元二分便宜得多。

### 6.5 算法与产物

标准二分，但产物不是"根因"，而是**最小坏集合（minimal bad set）**：

```
候选 [A B C D E F G H I J K L]，k=2
  试 [A..F] → 失败 → 候选缩到 [A..F]
  试 [A..C] → 通过 → 坏的在 [D..F]
  试 [D..E] → 失败 → 坏的在 [D..E]
  试 [D]   → 失败 → 坏的在 [D]
最小坏集合 = { D }
```

每一步都要落盘（时间、试了哪一半、结果、连续通过计数），形成**证据链**。事故面板展示的是这条链，不是最后那个 id——因为用户真正需要知道的是"我是怎么排除掉其他 11 个的"。

### 6.6 与现有阶梯的关系

不替换，**分层**：

| 层 | 触发 | 成本 | 适用 |
| --- | --- | --- | --- |
| 阶梯（现有） | 启动就挂 | 1~3 次启动 | 确定性故障，快速止血 |
| 二分（新增） | 阶梯走完仍坏 / 偶发故障 / 手动 | ⌈log₂n⌉×k | 阶梯查不出来的 |

阶梯是快速路径，二分是兜底。两者共享同一套证据落盘与嫌疑度排序。

### 6.7 交互

- **触发**：① 阶梯走完仍失败 → 自动建议；② 事故面板上的「深入排查」按钮 → 手动；③ 概览页的入口。
- **进度**：当前在试哪一半、已排除多少个、预计还要多久。偶发故障尤其需要这个——否则用户以为卡死了。
- **可中断**：任何一步都能停，已排除的结果保留。
- **产出动作**：定位到最小坏集合后，直接给「停用这几个」的按钮（走已有的 quarantine 路径，用户点确认才改），而不是自动改。

## 7. 偶发故障的诚实表述

二分在偶发故障下有内在局限，必须在 UI 上说清楚，否则用户会被误导：

1. **"能解释现象的最小集合"不等于"罪魁祸首"**。组合效应（两个插件单独都正常，一起就炸）会让二分收敛到一个不真正可修的答案上。
2. **k 的选择会影响结论**。k=2 判"好"的两组，其中一组可能仍含偶发触发源。
3. **不收敛是可能的**。故障可能根本不在候选集合里（内核、Node 版本、磁盘、端口冲突）。此时要说"候选集合内找不到原因"，并指向更高层的原因，而不是硬凑一个答案。

UI 文案必须区分三种结束状态：**定位到最小坏集合** / **未收敛（原因在候选集合之外）** / **用户中断**。

## 8. 存储与数据结构

### 8.1 快照索引

```jsonc
// <instance_dir>/snapshots/state.json
{
  "schema": 1,
  // 存**指纹**而不是 id（与下方初稿不同）：它要表达的是"这套配置被成功
  // 启动验证过"，而不是"文档里这一行"。指纹由配置本身算出，比任何命名
  // 约定都更贴近那个不变量。P0 落地时按此实现。
  "lastKnownGood": "9c2e4b1a7f0d",
  "entries": [
    { "id": "snap-9c2e4b1a", "createdAtMs": 1790490000000, "reason": "startup-ok",
      "fingerprint": "9c2e4b1a7f0d", "kernelVersion": "0.1.5-rc.2",
      "plugins": [ { "id": "dsh-market", "mode": "link" } ] },
    { "id": "snap-77ab19d3", "createdAtMs": 1790400000000, "reason": "pre-change",
      "fingerprint": "77ab19d3e0c5" }
  ]
}
```

索引与快照内容放在**同一个文档**里（P0 落地时相对初稿的改动）：保留上限只有 10 份，单文件一次原子写就够；「一份索引 + 每份一个文件」会引入"索引指向的详情丢了"这种不一致状态，而它换不来任何好处。

### 8.2 二分会话

```jsonc
// <instance_dir>/bisect/<session-id>.json
{
  "schema": 1,
  "startedAtMs": 1790490000000,
  "instance": { "family": "dsh", "id": "default" },
  "probe": "crashed-within-T",
  "k": 2,
  "candidates": ["dsh-market", "dsh-file-perf", "review-checklist", "…"],
  "steps": [
    { "tried": ["a", "b", "c"], "outcome": "fail", "passed": 0, "at": 1790490030000 },
    { "tried": ["d", "e"],      "outcome": "pass", "passed": 2, "at": 1790490120000 }
  ],
  "conclusion": { "kind": "minimal-bad-set", "members": ["dsh-market"] }
}
```

`conclusion.kind` 三选一：`minimal-bad-set` / `not-in-set` / `aborted`。**没有"找到根因"这个取值**——那是过度承诺。

### 8.3 复用既有骨架

两份文档都走 `state.rs`（容错读 / 校验读分开、文案由 `StateCtx` 提供），不新写 JSON 读写。指纹计算放共享层（§9 的复用表），不放 `plugins.rs` / `guard.rs`。

## 9. 与既有能力的边界

| 能力 | 管哪一段 | 触发 | 改不改用户配置 |
| --- | --- | --- | --- |
| 沙盒预检（`precheck.rs`） | **装之前** | 用户点安装 | 失败时回滚，等于不改 |
| 启动阶梯（`guard.rs`） | 启动就挂 | 自动 | 改（停用插件），可撤销 |
| 环境快照 | 坏之后回退 | 自动 + 手动 | 改，但先展示差异 |
| 二分定位 | 坏之后定位 | 自动建议 + 手动 | **不改**，只给建议动作 |

复用既有资产，不重写：

| 需要的能力 | 复用 |
| --- | --- |
| 开关单个插件/技能/补丁 | `quarantine.rs` + `ensure_wiring_filtered` / 活动视图增删 / `patches.rs` 备份还原 |
| 启动一次并判定 | `guard::watch_child` 的判据（`port_open` + 退出状态 + 超时） |
| 嫌疑度排序 | `guard::attribute` |
| 事故展示 | `guard::Incident` + `IncidentModal.vue` |
| JSON 状态文档 | `state.rs` |
| 起一批临时内核 | `sandbox.rs`（**不要**依赖 `reap_orphans`，见 §1.4） |

## 10. 落地顺序

**P0 — 快照（无 UI 自动化，先只读展示）**
1. 指纹计算（共享层）+ 单元测试
2. `startup-ok` / `pre-change` 两个打点
3. 事故面板与概览页展示快照列表 + last-known-good
- 交付价值：用户能看见"昨天那套配置是什么"，这是一切其余工作的地基。

**P1 — 手动恢复**
4. 差异展示 + 二次确认
5. 恢复流程（先备份、只改差异、跑健康自检）
- 交付价值：用户已经能自己捞回来。

**P2 — 二分（确定性故障）**
6. 二分会话 + 步骤落盘
7. `probe = startup-failed`、k=1（与阶梯同判据，先不加成本）
8. 「深入排查」按钮 + 进度呈现
- 交付价值：阶梯走不完的确定性故障能收敛。

**P3 — 偶发故障**
9. `crashed-within-T` / `blank-screen` 两种 probe
10. k 可调 + 耗时预估 + 可中断续查
11. 内核版本的廉价前置二分（§6.4）

**P4 — 交接**
12. 最小坏集合 → 「停用这几个」的一键动作
13. 快照导出（不含凭据），供用户发给作者或贴 issue

---

## 11. 明确不做的事

- **不做自动修复后静默继续**。任何降级 / 恢复都要用户看得见。
- **不把凭据放进快照**。
- **不把 `reap_orphans` 的修复合进本设计**。它是独立缺陷（§1.4），该单独修单独测；安全网自己持有子进程，不依赖它。
- **不给二分结果起"根因"的名字**（§7）。
- **不把内核版本塞进 n 元二分候选**（§6.4）。

---

## 12. 遗留风险

| 风险 | 现状 | 缓解 |
| --- | --- | --- |
| 配置组合爆炸导致快照数量与体积增长 | 每份约 1 KB，保留 10 份 | 上限固定，无实际压力 |
| 二分在用户真实环境里可能触发**更多**崩溃 | 每次试探都是一次真实启动 | 崩溃都是"启动失败/白屏"级别，不会损坏会话（会话由内核自身写）；试探期间不写业务数据 |
| 偶发故障下用户等待时间不可预测 | 已知 | P3 才引入，且必须先给耗时预估与中断入口 |
| 快照声明与磁盘实际状态漂移（用户手工改过 `extensions/`） | 已知 | 恢复前先校验指纹，不一致时明确提示"当前环境已被手工修改"并要求确认 |
